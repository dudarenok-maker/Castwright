**The voice-cloning release.** Castwright can now clone a voice from a short
consented sample and cast it like any other — on **both** speech engines, in
the book's own language, with a never-substitute promise that fails loud rather
than quietly handing a character to a stand-in. Around it: a character's
identity now survives a re-analysis instead of stranding their already-narrated
lines in the narrator's voice, GPU memory reclaims itself before anything is
refused for lack of room, and the sidecar stops stalling every other request
while it frees a model. Under those: honest engine-health reporting that tells
a missing package from a broken one, a Listen view whose loudness numbers are
measured rather than restated, and a large hardening pass across the golden-audio
and release-notes gates.

> ⚠️ **Upgrade note:**
>
> - **Node 22.22 is the new floor** (was 20.19). `engines` is advisory — npm warns and installs anyway — so check `node --version` before upgrading a self-managed install. Pinokio installs now provision their own pinned Node 24, but converge one Update late (fe-56, #1859, #1878).
> - **ffmpeg 6.0 is the new minimum**, and **Ubuntu 22.04 is retired** as a supported target (its archive ffmpeg is 4.4). Every user-facing surface warns rather than blocks; only the preflight hard-fails. Snap or a PPA satisfies the floor on 22.04 (ops-35, #1877).
> - **An existing Coqui install must be Repaired to pick up the long-line clone fix.** `spacy` installs from `install-coqui.mjs`, not `requirements/base.txt`, so a version bump alone does not deliver it — press **Repair Coqui XTTS v2** in Account → Models (#2017).
> - **Existing `onnxruntime-gpu` 1.28.x installs step back to 1.27.x** on first upgrade, now that the swap is pinned instead of resolving to whatever was latest on your install date (#1846).
> - **Books already rendered against a drifted character id are not repaired in place.** The resolver fixes the join at render time, so an affected chapter needs a re-render to put the right voice back; `scripts/repair-cast-id-drift.mjs` is the offline pass for the rest (#2040).

## ✨ Headline features

### 🎤 Clone a voice — and cast it on either engine (new) — fs-38

Record or upload a short sample, attest consent, and Castwright distils a reusable cloned voice you can hand to any character in any book. The whole surface lands in this release: a book-independent voice library to keep it in, ingest/consent/recorder, the first clone on Qwen, the resolver and lifecycle that make "never silently substituted" an enforced invariant rather than a hope, and the same machinery extended to Coqui XTTS v2 so a clone works on both engines. Every follow-up below is part of that one story — consent records, language, engine routing, and the failure paths that have to fail loud.

- **fs-38 Wave 1 — book-independent voice library (`#/voices` restructure + designed-voice authoring)** (#1800, refs #624). Ships a first-class, book-independent voice-library store ("My voices"), restructuring `#/voices` into three sections — **My voices | In use | Catalogue**. Adds standalone designed-voice authoring: create a Qwen voice from a persona with a live audition, **redesign-with-compare** (A/B old-vs-new, keep or discard), **promote** a character's designed voice into the library (new uuid + byte-copy of the `.pt`), and **assign** a library voice to any character — reusable across books and series. A new `provenance` dimension (`designed`/`cloned`/`imported`) lands on the schema, and the cross-book voice matcher excludes cloned-provenance voices so a person's voice can't be offered back into a stranger's book. Local-only; deleting a library voice runs a usage report and full multi-location erasure (manifest + `.pt` + cached samples). This wave alone delivers the folded-in `fs-12`. Plan: `docs/superpowers/plans/2026-07-04-fs38-wave1-voice-library-store.md`.
- **fs-38 Wave 3a — voice-clone ingest, consent & recorder** (refs #624). Sample ingest, consent, and recorder. Real ffmpeg decode (upload or a new `VoiceRecorder`) → a pure quality gate (fatal <4s/silence, warn short/clipping) → 60s cap → a Node-written `master.wav` → Whisper transcript, via `POST /api/voice-library/clone-sample` (ephemeral candidate — no entry persisted yet). A write-time consent-structure guard on `writeEntry()` plus `POST /:uuid/revoke` (revocation orthogonal to the guard); the sample-audition route 403s a revoked/consent-absent cloned voice. My voices gains a 'Cloned' badge + Revoke action, and a capture/consent panel. Plan: `docs/features/267-fs38-wave3-voice-clone.md`. Spec: `docs/superpowers/specs/2026-07-25-fs38-wave3-clone-pipeline-design.md`.
- **fs-38 Wave 3b1 — the first voice clone, on the Qwen engine** (refs #624). Capture or upload a sample, attest consent, and Castwright distils a reusable cloned voice — auditioned, ECAPA fidelity-checked, and castable like a designed one. A cloned voice is never silently substituted: if Qwen is unavailable the chapter fails loud instead.
- **fs-38 Wave 3b2 — cloned-voice resolver + lifecycle** (refs #624). Closes the resolver/lifecycle half of the never-substitute invariant 3b1's single `applyQwenFallback` exemption only partially covered. A new `clone-voice-resolver.ts` (pure Healthy/Repairable/Broken classifier + two async orchestrators) is wired as a per-chapter pre-pass in `synthesiseChapter`, running BEFORE any synth call: it transparently re-derives a Repairable cloned voice from its retained `master.wav`, and hard-fails the whole chapter via `UnresolvableClonedVoiceError` (never a silent reroute) on a Broken one — revoked, missing-master, engine-unavailable, wrong-engine, or a persisted derive failure. The readiness gate is intersected to exactly this chapter's in-chapter characters, including both the title-beat and orphaned-`characterId` narrator paths. Transient re-derive failures (sidecar unreachable, any 5xx) collect Broken without persisting `engines.qwen.status:'failed'` — only a genuine 4xx does, so a hiccup can't brick a voice. `purgeCloneArtifacts(uuid)` gives revoke and delete one shared, total erasure routine (base `.pt`, `__1.7b.pt`, manifest, both `-preview` variants, both `__master.wav` variants, sample cache) — closing gaps where revoke erased nothing and delete missed the 1.7B cache. Revoke additionally erases the entry-dir recording itself (`{ deleteMasterClip: true }`, clearing the entry's `master` field), behind a two-step confirm dialog that spells out the consequence up front — "revoke" now means the person's original recording is gone, not retained-but-inert. Sidecar `.pt` writes for `clone_voice`/`design_voice` are now atomic (temp file + `os.replace`, absorbing #1804). A distinct `wrong-engine` `BrokenClonedVoice` reason (+ a `cloned-voice-broken` `FailureCode` with a toast + help link) diagnoses a cloned voice assigned to a character/book that doesn't route to Qwen, separately from Qwen being unavailable; an advisory `POST /:voiceUuid/assign` 409 guard (optional `modelKey` body field) catches the same case at assign time. §2.3 (designed-voice clip-persist + orphan self-heal from a retained `qwen-<uuid>__master.wav`, scoped to a missing `.pt` only and never throwing) shipped alongside. Plan: `docs/features/268-fs38-wave3b2-resolver.md`. Spec: `…clone-pipeline-design.md` §5.
- **fs-38 Wave 3c — cloned + designed voices on Coqui XTTS v2** (refs #624). Extends 268's never-substitute/total-erasure machinery to a second engine.
  - **Sidecar.** `CoquiEngine.clone_voice` (`server/tts-sidecar/main.py`) derives XTTS conditioning latents (`get_conditioning_latents`, hand-rolled rather than the built-in `CloningMixin` — the built-in's non-atomic `torch.save` to a path we don't control would defeat reliable purge), persisted via the pre-existing `_atomic_torch_save` under a `_synth_lock` shared with `/synthesize` (clone and synthesise are two serialized concurrent entry points into the model, matching Qwen's pattern — not a throughput regression). An epoch-guarded `_latents_cache` (`_evict_epoch`/`_bump_evict_epoch`) backs `POST /xtts/clone-voice` and `POST /xtts/evict-voice`, mirroring the Qwen pair; a re-clone of the same voice_id invalidates a racing render's stale latents. Six further hardening fixes in the cloned-voice path (safe tensor-only latents load, an unload race, an evict-epoch miscount, an atomic manifest write, case-folded latents lookup, and rejecting a clone stored under the wrong id prefix). `clone_voice` now marks itself in-flight the way `synthesize()` does, so an idle-driven evict or a manual unload landing mid-derive raises a clear "model was unloaded — retry" instead of a bare assertion failure.
  - **Node.** `pickVoiceForEngine`, `clone-voice-resolver.ts`'s classifier + both orchestrators, and `purgeCloneArtifacts` are engine-parametric instead of Qwen-hardcoded — the artifact set per cloned Coqui voice is three deterministic paths (`.pt`, `.json`, and a reference-audio temp WAV that is the person's actual source clip), all purged on revoke and delete via the same `evictSidecarVoice()` helper the Qwen sweep used. Crash-orphaned temp artifacts (a staging file the sidecar's atomic save leaves behind when the process is hard-killed mid-write) are swept on clone purge, closing a gap where revoke reported clean erasure while conditioning latents or the person's raw reference clip survived on disk. A **fail-soft** designed-voice-on-Coqui derive arm — the opposite policy from cloned's fail-loud — is kept in a genuinely separate code path: a designed voice isn't a real person's identity, and falling back to the stock catalogue on a bad derive is today's acceptable behaviour. A designed entry with no retained calibration clip gets no Coqui slot at all and renders byte-for-byte as before this wave; a designed Coqui slot that outlives its library entry (deleted between assign and confirm, or an unparseable manifest) also fails soft back to the catalogue rather than hard-failing the chapter. Reuse hydration no longer overrides a character's own designed Coqui slot with a source book's Qwen voice when the character carries no `qwen` override at all.
  - **Assign, unassign, delete.** `POST /:voiceUuid/assign` writes both clone-capable slots when the entry can actually render on both (cloned, or designed with a retained clip) — an unconditional dual-slot write would have let an engine switch silently drop a real person's identity to a stock catalogue voice. It now also reports `written: CloneEngine[]` (derived from the same `shouldWriteCoquiSlot` flag the write itself uses, so the two cannot disagree) instead of a bare `{ updated: 1 }`; both the profile drawer and the My-voices panel reconcile their optimistic write against it and surface an inline notice when the routed engine's slot was declined. A new `DELETE /:voiceUuid/assign?bookId=&characterId=` route gives the profile drawer a **"Remove voice" control** — the first way to take a library voice back OFF a character (`PUT /api/voices/:voiceId/override` refuses to clear a cloned slot outright and preserves cloned provenance on a set, so picking a stock voice over a clone previously still rendered the clone). Unassign never refuses: it destroys no artifact, only the character's `overrideTtsVoices` slot(s), and works against a revoked or already-deleted entry. `DELETE /:voiceUuid` no longer answers an unconditional `{ deleted: true }`: when `purgeCloneArtifacts` fails to erase every artifact the manifest entry is deliberately **retained** (`{ deleted: false, artifactPurgeIncomplete, artifactPurgeFailedPaths }`), because deleting the manifest on a partial purge would leave a surviving artifact *less* gated than before the delete — the consent checks key off that entry existing. A sibling fix keeps the manifest's `master` clip pointer intact when a revoke's clip unlink fails (Windows `EBUSY` can leave the file present with nothing naming it), so a retried revoke genuinely re-attempts the unlink.
  - **Consent, closed on every reachable path.** Fail-safe-only fixes (no clone predicate widened). A manual cast-link (`cast-link-prior.ts`) and the series-reuse chain-walk (`hydrate-reused-voice.ts`) no longer denormalise a voice onto a character carrying a cloned slot on the *target* side of the link ([#1885](https://github.com/dudarenok-maker/Castwright/issues/1885)). The wholesale `PUT /api/books/:bookId {slice:'cast'}` cast-save route keeps `voiceUuid` and any reserved clone-storage-key server-owned: `preserveClonedSlotsOnCastWrite` restores the stored slot when the incoming payload merely omits it (204) and refuses the whole write (409, not a generic 500) when the incoming value actually differs — a client that wants to *replace* a cloned slot goes through the dedicated unassign/reassign routes ([#1899](https://github.com/dudarenok-maker/Castwright/issues/1899)). A legacy cloned slot carrying a `libraryUuid` with no `provenance` field — invisible to the render-time revocation check, because only `pickVoiceForEngine`'s Qwen branch resolves a bare `libraryUuid` — is now included in the resolver pre-pass's revocation check, Qwen-only since Coqui has no such exemption ([#1891](https://github.com/dudarenok-maker/Castwright/issues/1891)). `/redesign` and `/promote` had no provenance gate at all, so editing a cloned card's persona overwrote its `.pt` in place with a stranger's synthesised voice while every cast slot still read `provenance: 'cloned'`; both now 403 outright on a cloned entry (fail-closed by owner ruling; a re-consent flow is a future decision). Both `applyOverrideToCastFiles` callers pinned `ttsEngine` to Qwen unconditionally, so a character already carrying a Coqui-cloned voice caught in a bulk "Design full cast" kept its clone marker on disk but silently rendered off it — the bulk sweep now skips a cloned character and names it in the run's terminal summary ("already cloned: Anna, Viktor"), and a single "first design" on an already-cloned character refuses (409) before any GPU work runs.
  - **Case-folding on clone keys.** The comparisons deciding whether a request lands on a real clone or falls through to a substituted catalogue voice are now case-folded at the substitution guard and inside the sidecar's own latents lookup. `POST /:voiceUuid/sample` (the profile-drawer audition route) resolved entries case-insensitively while the audition cache and the sidecar keyed off the raw string, so `xtts-<uuid>` and `XTTS-<UUID>` could each accumulate their own cached audition/latents for what a purge treats as one artifact — leaving one playable after a revoke that reported everything gone. The route now refuses a non-canonical spelling of a voice's own key (400) rather than resolving and rendering it.
  - **Preview.** The My-voices card's Preview button plays on whichever engine's artifact is actually ready rather than always requesting Qwen — a Coqui-ready/Qwen-stale entry previously 409'd on every preview despite being genuinely playable ([#1887](https://github.com/dudarenok-maker/Castwright/issues/1887)). Setting a character's voice override no longer keeps a stale `libraryUuid`/`provenance` pair on the client when the server has already dropped it (because the *previous* slot wasn't a clone), so the drawer can't preview a "cloned" voice the server no longer considers cloned; the client mirrors the server's rule exactly. The sidecar's `voice_language_unsupported` 409 (the voice IS cloned and loaded, but the XTTS model doesn't list the requested language) is mapped through both Node sample routes instead of falling through to a generic 502 whose remedy copy ("design it first") cannot work for this case.
  - **Remote-sidecar fix the engine-parametric refactor exposed.** Coqui availability used to fall back to a local disk stat that's always absent on the box the *server* runs on, aborting chapter 1 of every book on a Coqui-installed-and-working remote/LAN sidecar — fixed with a wire fact (`coqui_weights_present` on `/health`, mirroring the existing `qwen_weights_present`).
  - **Golden-audio gate.** `test:golden-audio:sidecar` now covers Coqui — `test_coqui_sanity` previously never fired on a Coqui-only box, because a Kokoro-shaped weights-path probe never matched Coqui's lazy-fetched weights — plus new `test_xtts_clone_sanity` / `test_xtts_designed_sanity` loose-check cases, including a long-sentence case for the `enable_text_splitting` crash class.
  - **`preparing-voice` phase for the resolver pre-pass.** The Wave 3b2/3c pre-pass can spend several seconds transparently re-deriving a Repairable cloned voice or self-healing a designed one before the first synth call — previously a dead pause with no UI signal. Both request interfaces (`ClonedVoiceRequest`/`DesignedVoiceRequest`) gain `characterId`; a new `onVoicePrepare` callback fires at each pre-derive call site in the cloned (fail-loud) and designed (fail-soft) arms independently, threaded through `SynthesiseChapterOpts` to a new `generation.ts` `emitPreparingVoice` tick (mirroring `emitVerifying`/`emitRecovering`) and a new `chapter_preparing_voice` `GenerationTick` type. The Generation view gains a "Preparing voice — `{character}`…" caption and pill beside `recovering`'s, with matching `ChapterProgressBar` busy-styling; a `withVoicePrepareHeartbeat` wrapper re-fires the last payload on the existing heartbeat interval so a long derive doesn't look stalled. Design: `docs/superpowers/specs/2026-07-26-resolver-prepass-progress-phase-design.md`. Closes [#1813](https://github.com/dudarenok-maker/Castwright/issues/1813).
  - **XTTS is now evicted at the end of a chapter's Coqui phase.** fs-60's mixed-engine dispatch evicted Qwen FOR the Coqui phase but never freed Coqui back — so XTTS (~3.5 GB) stayed resident for the rest of the render, including a following chapter with no Coqui work at all, which on a Qwen-default book is the common case. This is Node-side and reactive, firing at the one point in `synthesiseChapter` where "no further Coqui work is queued this chapter" is a known fact rather than a guess, and is deliberately **complementary** to the sidecar-side idle reclaim below rather than a replacement for it (consolidating the two is filed as [#1932](https://github.com/dudarenok-maker/Castwright/issues/1932)). Fail-soft: every group is already synthesised by the time it runs, so a sidecar recycle window must not destroy completed work.
  - **Smaller fixes.** A voice-library `promote` handler (both the library route and the character `design-voice` route) now `stat`s the preview artifact before deleting the live one, closing a data-loss window where a double-promote deleted the live `.pt` before discovering the preview meant to replace it was already gone ([#1804](https://github.com/dudarenok-maker/Castwright/issues/1804)). The golden-audio gate's PowerShell runner no longer crashes on the Qwen probe's benign stderr line (a `torchaudio`→`sox`-absent warning tripped under `$ErrorActionPreference = 'Stop'`), so `test:golden-audio:sidecar` reaches pytest instead of erroring out before it starts — the same guard was missing on the sibling Coqui-presence probe (`import TTS`) and is applied there too ([#1892](https://github.com/dudarenok-maker/Castwright/issues/1892)). `spawn-sidecar.ts`'s `QWEN_VOICES_DIR`/`XTTS_VOICES_DIR` env vars route through the same `paths.ts` helpers the rest of the codebase uses instead of a parallel literal `join` ([#1890](https://github.com/dudarenok-maker/Castwright/issues/1890)). The voice-library panel's "My voices" assign action surfaces a rejected `assignVoice` dispatch inline instead of swallowing it ([#1896](https://github.com/dudarenok-maker/Castwright/issues/1896)). A Wave 3a deferred-minor sweep closed nine smaller items — per-field consent-structure test coverage, a direct test for the sample route's `!entry.consent` 403 branch, a `cloneSample` thunk unit test, three OpenAPI status-code omissions, a `mockRevokeVoiceLibraryEntry` `.find()!` guard, static imports replacing a dynamic one in a test, a redundant re-spread, and an `aria-describedby` association from the clone-capture panel's attest checkbox to its sentence text ([#1808](https://github.com/dudarenok-maker/Castwright/issues/1808)). - **fs-38 — clone-wizard transcript edits now reach the derive** (#1840, closes #1836, refs #624). The wizard's transcript textarea was editable but write-only: `onReady` forwarded just `{ candidateId, consent }` and `CloneVoiceRequest` had no transcript field, so `POST /clone` always distilled against `candidate.master.transcript` — the raw Whisper output. Adds an optional `transcript` to `CloneVoiceRequest` (OpenAPI-first), forwards the edited value from the capture panel through the wizard, and prefers it as the derive's `ref_text` when non-blank. The corrected text is persisted as **`master.transcript`** as well as `sampleTranscript` — load-bearing, because the Wave 3b2 repair path re-derives from `entry.master.transcript` (`readMasterPcmDefault`), so storing it only in `sampleTranscript` would let a later repair silently revert to the Whisper text. `master.transcriptSource` now records `'user'` when the text differs from the stored Whisper transcript (previously that enum arm was unreachable), decided server-side rather than from a client flag. Blank/whitespace falls back to the Whisper text, since Whisper can legitimately return an empty transcript for a non-speech clip. As the first client-controlled value to reach the derive's `refText` — which travels to the sidecar as a base64 `X-Ref-Text` header — it is capped at 2000 chars in both the contract and the route (pinned against drift by a test deriving from the exported constant), sized so the header stays bounded in BYTES for multi-byte ja/zh/ru text rather than only for ASCII. Over-length is a 400, never a truncation: the textarea deliberately carries no `maxLength`, because a browser-side cap would silently drop the tail of a correction and persist the remainder as `transcriptSource: 'user'` — the same silent-discard shape this fixes. The wizard blocks Continue with a visible reason instead, while the field stays editable. `mockCloneVoice` mirrors the same semantics so mock/e2e mode stops reproducing the bug. Adds Invariant 12 to `docs/features/267-fs38-wave3-voice-clone.md`.
- **Cloned voices now render in the book's language, not English** (refs #1951). `QwenEngine.synthesize` accepted a `language` argument and never read it, so a voice's language came solely from its sidecar manifest. A cloned voice's manifest always reads “English” — `deriveEngineArtifact` never sent `X-Language`, so `clone_voice` computed `lang = DEFAULT_LANGUAGE` — and cloned voices are deliberately exempt from `clearMismatchedDesignedVoices` (`verify-designed-voice-language.ts:55`) so they can be reused across books, so nothing else supplied one. Measured on the box: a German sentence through the production `/synthesize` → `/transcribe` path detected `en` at `avg_logprob` **−1.303** (unintelligible); with the language corrected, `de` at **−0.366**. The failure was total, not gradual. **The primary surface is `/synthesize-batch`, not `/synthesize`**: chapter sentences batch (`QWEN_BATCH_SIZE` defaults to 32) and only the title beat is a single synth, so a fix confined to `synthesize` would have shipped a translated title over an entirely English book while passing every mechanism-level test. Node decides clone-ness (`hasClonedProvenance`) and signals it purely by whether it puts a `language` on the request — per **item**, since a batch may mix a cloned character's line with a designed narrator's. The sidecar never learns what a clone is; an omitted field falls through to the manifest language, so designed-voice behaviour is byte-identical and Coqui is untouched. An unmappable language degrades to that same fallback rather than throwing or defaulting to English. Also fixes a cache/disk divergence in the designed self-heal, where the restored manifest said one language while the sidecar's warm `_prompt_cache` said another — so a **sidecar restart silently changed the audio** — by evicting the prompt cache after the restore. The clone derive now sends `X-Language` from the reference clip's Whisper-detected language, so a clone's manifest and Voice Library label stop claiming English. Existing clone manifests keep reading “English” until re-cloned or re-derived (not migrated: recovering a distilled `.pt`'s language would mean re-transcribing the master). Two further seams carry the same pair rather than being left behind the render path: the **speaker-drift reference** (`auditionCentroid`) now renders under the book's language — it is the centroid every chapter segment is compared against, so an English reference against a German chapter would have become a fresh source of false `voice-mismatch` flags on exactly the cloned voices this change fixes — reading the language from the book's `state.json` and the provenance from `cast.json`, and passing neither when the book's language genuinely can't be read (never an English guess); and `POST /api/voices/:voiceId/sample` now marks a cloned voice as such, so a supplied `language` reaches the mapping instead of the clone's English manifest. That route forwards a client-supplied, unvalidated language, so it is protected only by `resolveWireLanguage`'s try/catch now that the mapping is reachable — pinned end-to-end (route → real provider) by `routes/voice-sample-cloned-language.test.ts`, since a 5xx there would break a Play-sample click that works today. Plan: [`docs/features/275-clone-voice-language.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/275-clone-voice-language.md).
- **A cloned voice's consent record can now name the real attester, not just the person being cloned** (#1943). `POST /api/voice-library/clone` hardcoded `attestedBy` to `consent.personName`, so a `guardian-of-minor` record asserted that the **child attested to their own voice being cloned** — inverting the relationship's whole meaning; a `family-with-permission` record had the same defect. `validateConsentDraft` now accepts a trimmed `consent.attestedBy`, persisted verbatim, and `POST /api/voice-library/clone` **rejects a non-`self` clone with 400** when it is absent or blank/whitespace (#1959) — the fallback to `personName` survives only for `relationship: 'self'`, where the person being cloned *is* the attester and the wizard deliberately omits the field. So no stored record can assert that a minor attested for themselves via any code path: the gate sits ahead of any candidate or GPU work, `/clone` is the only server-side write into `attestedBy` (`PATCH /:voiceUuid` never touches consent, `revoke` only stamps `revokedAt`), and the mock API layer carries the identical gate, having otherwise kept the pre-fix fallback and gone on reproducing the defect in mock mode. `openapi.yaml`'s `CloneVoiceRequest.consent` gains the field; the conditional requirement lives in its description, since `required` cannot express it. The clone wizard (`CloneCapturePanel`) gains an attester-name input, shown and required only for the two non-self relationships (asking someone to name themselves twice for `self` is noise), folded into the existing Continue gate; the fixed attestation sentence is now relationship-aware, since a guardian is consenting on a child's behalf rather than relaying the child's own permission. No migration for already-stored entries — they keep `attestedBy === personName`, which is exactly what they attested to at the time. ### 🪪 A character's identity now survives a re-analysis — #2040

A character's `id` is free text the analyzer mints, and it is the join key across `cast.json`, the analysis cache and every frozen chapter's `segments.json`. When a re-analysis minted a different id for the same person, an already-narrated chapter could no longer tell whose line it was reading and quietly fell through to the narrator — with nothing on screen to say so. A scan of the real 20-book workspace found drift in 18 books and 188 orphaned segments. Three staged waves close it: resolve it, stop creating it, then surface and repair what is left.

- **An orphaned `characterId` (no entry in the book's cast at all) no longer silently borrows the narrator's voice with no record of it** (#2023, found by the fs-38 Wave 3 on-box acceptance run, run sheet §5 Section C, C-05). `synthesise-chapter.ts`'s `resolveGroup` has always substituted the narrator for a sentence group whose `characterId` isn't in `cast` (a cast/analysis id drift — e.g. `mairin` vs `mayrin`, `coalfall-dragon` vs `coalfall`) — real evidence: 21 of 72 segments (60.3 s) in *Заказ Коалфолла* ch.2 rendered in the narrator's voice this way, one of five affected books. The fallback itself is unchanged (it may well be the right behaviour); what was missing was any record of it beyond a once-per-orphan-id `console.warn`. Two fixes: **(1)** the render now stamps the substitution on the segment (`ChapterSegment.renderedFallbackCharacterId`), aggregated across a book's rendered chapters into a new `orphanedCharacterFallbacks` book-state field (keyed by the orphaned id, naming who rendered it and the voice used) — hydrated into the cast slice and surfaced as an advisory banner on the Cast view naming the orphaned id(s), and published per-segment on the per-chapter audio meta endpoint alongside the existing QA `suspect`/`reasons` fields. **(2)** if the narrator resolves to a **cloned** voice, an orphaned-id line now raises `cloned-voice-broken` (`UnresolvableClonedVoiceError`) instead of substituting — mirroring the enforcement `applyQwenFallback` already gives an unavailable cloned voice, extended to a *healthy* one being borrowed for another character's line, which was safe only by luck (every affected narrator across the five books happened to be a designed, not cloned, voice). The upstream cause — cast and analysis ids disagreeing — is a separate, filed issue ([#2040](https://github.com/dudarenok-maker/Castwright/issues/2040)); this PR does not touch the drift itself.
- **A cast character's `id` can now drift between `cast.json`, the analysis cache and a frozen chapter's `segments.json` without silently substituting the narrator for that character's lines — the first of a staged fix** (#2040). A character's `id` is free text the analyzer mints, not derived from its name, and it is the join key across all three of those independently-persisted artifacts; when a re-analysis mints a different id for the same character (`the-torment` vs `the_torment`, `mayrin` vs `mairin`), the frozen render's id no longer matches any cast row and `synthesise-chapter.ts`'s `resolveGroup` fell through to the narrator with no record of it. ### 🧠 GPU memory and the sidecar now look after themselves

Two chains land together. The first stops a refusal being issued against a pessimistic reading: a finished render's stranded allocator pool is reclaimed before anything is refused, eviction stops the moment a request fits instead of unloading models it never needed to, and the readings that drive all of it stop mixing two cards' figures. The second stops the sidecar's single event loop being held hostage by a model unload — every eviction step moves to a worker thread, and every in-lock cold weights pull that could hold the Stop button off is hoisted out of the lock.

**Reclaim, admission and eviction.**

- **A finished render no longer leaves several GB of GPU memory stranded, blocking the next operation** (#1976). PyTorch's caching allocator kept a reserved-but-unallocated pool on the render card after a chapter finished and the engine reported unloaded — measured at **3968 MB** on an 8 GB card, with `/capacity` correctly reporting only 3230 MB free because the driver counts reserved cache as used. Nothing could reclaim it: every existing `empty_cache()` is a side effect of unloading a *resident* model, so with nothing resident the idle-eviction ladder had nothing to evict and fell straight through, and the watchdog's 90%-of-card recycle threshold is nowhere near tripping at ~48%. Only a sidecar restart cleared it. The memory was always **fully reclaimable** — a load/unload cycle on the same stranded state recovered it to 389 MB — it simply never got reclaimed, so later work was refused on a figure several GB pessimistic. Observed refusing an ASR `/transcribe` (`503 noCapacity`, three times, *with the model already resident*) and a voice design (`503 Not enough GPU memory for qwen (6144MB)`) while the box's second card sat with 15 GB free. Admission now performs one bare `gc.collect()` + `empty_cache()` and **one** re-probe as a final phase — only on the failure path, after the residency ladder has already failed, never in a loop — so a stranded pool can no longer by itself cause a refusal. It runs on a worker thread for the same reason every eviction step does (plan 273): `empty_cache()` can block on the allocator lock and must not stall `/health`. **Also:** `/health` gains `vram_reserved_mb_by_device`, a per-card breakdown — the existing `vram_reserved_mb` reads the *current* device only, and was measured reporting `50` while `nvidia-smi` showed 3587 MiB on `cuda:0`, which is actively misleading when diagnosing exactly this class of problem.
- **VRAM eviction now stops as soon as a request fits, and never throws away a reserved model** (#1920, PR #1930). Previously a small request (e.g. a 400 MB ASR call) ran every eviction branch unconditionally, so it could free several GB from Qwen and still unload a resident Coqui XTTS — a ~90 s reload — for no reason. Eviction is now an ordered, cheapest-reload-first step list that re-probes real capacity after each step and stops the moment the request fits. It also consults the reservation ledger and skips any engine whose operation has already been admitted, closing a window where an in-flight, already-reserved model could be evicted out from under it.
- **Idle Coqui XTTS is now reclaimed under VRAM pressure** (#1894, PR #1924) — the sidecar's admission path frees a resident-but-idle XTTS before reporting `noCapacity`, instead of failing the starved operation. Admission-time and demand-driven: it frees an idle XTTS the moment *any* starved GPU operation needs the room. Engine-aware (a Coqui op never evicts itself) and device-targeted. Tunable via `COQUI_IDLE_TTL` / `sidecar.coquiIdleTtl` (default 30 s). One accepted user-visible trade: a starved op's `NoCapacityError` no longer carries the "Coqui XTTS is loaded — Use its Stop button" line, since admission now presses that button itself. Also fixes an unguarded `CoquiEngine.unload()` that could crash an in-flight synth when the Stop button fired mid-render, and the same unguarded-unload race in the Whisper (ASR) and ECAPA speaker engines — which, unlike Coqui, were already being auto-evicted, so that one was reachable in production.
- **A failed VRAM evict no longer kills a mixed Qwen+Coqui chapter** (#1893). fs-60 partitions a chapter that mixes Qwen and Coqui into two serial phases with a sidecar `/unload` between them, so the two never co-reside on an 8 GB card. That evict call had no failure isolation: it throws on a non-ok `/unload`, `fetch` rejects on a dead socket, and no `try`/`catch` sat between it and `synthesiseChapter`'s head — so a transient sidecar hiccup aborted a chapter that would otherwise have rendered, at up to three call sites per chapter (initial body dispatch plus the segment-QA and ASR re-record rounds, which share the same wrapper). The evict is now best-effort: a failure logs a named warning and the Coqui phase proceeds, mirroring `clone-voice-resolver.ts`'s self-heal policy — an abort still propagates, so a paused or cancelled run stops here as before. The call is also bounded by the chapter's existing `callTimeoutMs` and forwards the abort signal; previously it could queue behind another book's in-flight synth on the sidecar's `_synth_lock` and stall forever, uncancellable. An abort is rethrown *as* an `AbortError` rather than verbatim, so a pause that raced a socket-death rejection can't read as a chapter failure at `routes/generation.ts`'s pause detector. Failing soft is usually cheap — `/unload` is idempotent and returns 200 even when nothing was resident, so a failure normally means an unhealthy sidecar, which the Coqui phase then surfaces itself — but not always: a wrong/proxied `SIDECAR_URL` can 5xx `/unload` while the synth path is healthy, and then Coqui really does load onto a resident Qwen. That residue is deliberately accepted, recorded as plan 249's accepted limitation #4, and owed on-box as register row A19.
- **Pressing Stop no longer reports a timeout while the model unloads anyway** (#1921, PR #1930). `POST /api/sidecar/unload` previously ran under the same 2 s budget as the sidecar health probe, so stopping a model mid-render reported an error a couple of seconds in and then unloaded for real up to a minute later. The unload route now gets its own 90 s budget (mirroring the existing `/load` route), and the UI shows a disabled "Stopping…" state for the whole wait instead of a misleading failure.
- **A Stop pressed mid-load no longer leaves Coqui XTTS pinned to a stale GPU** (#1918, PR #1930). Loading a fresh model used to publish seven fields with no lock while `unload()` took the lock and reset those same fields, so a Stop during the ~90 s cold load could have the still-running loader overwrite the unload's resets — leaving a live model whose `_device` never got restored to `_requested_device`, bypassing GPU placement on the next load. The publish is now atomic and load-epoch-guarded: `unload()` unconditionally bumps a load epoch, and a load that finishes after losing the race discards its result instead of publishing on top of a teardown.
- **The five engine in-flight counters are now lock-guarded** (#1917, PR #1930). `x += 1` on a plain attribute is not atomic — CPython can switch threads at any bytecode boundary — so a concurrent forward could lose a decrement and leave that engine's counter stuck above zero, silently disabling its idle eviction for the rest of the process's lifetime, with no error and no log line. All five counters (Coqui, Whisper/ASR, ECAPA/speaker, and both Qwen VoiceDesign and Base) now share one lock-guarded `InFlightCounter`; the lock is held only for the mutation itself, never across a forward, so eviction's fast-out stays non-blocking. **Also fixes a related pre-existing bug found in passing:** `CoquiEngine.synthesize`, `WhisperEngine.transcribe` and `SpeakerEngine.embed` all decremented their in-flight count *before* re-stamping `_last_used` on the way out, leaving a window where the admission path could see an idle-looking engine mid-forward and evict it.
- **`_cuda_vram_mb()` — the reading that feeds the VRAM recycle watchdog — no longer mixes two different cards' figures on a multi-GPU box** (#1997). `allocated`/`reserved` read torch's *current* device (no-arg calls), but `total` was hardcoded to `get_device_properties(0)` — device 0, regardless of which card was actually current. Invisible on a single-GPU box; on a multi-GPU one it could compare one card's usage against a different card's capacity, feeding the recycle watchdog a ratio that describes neither card correctly. `total` now reads the current device too. **Also fixed in passing** (the same defect shape): `/debug/memory`'s inline `cuda` block had the identical device-0-hardcoded `total_mb`, which would otherwise have disagreed with `/health`'s now-fixed `vram_total_mb` on the same box.
- **An ordinary synth can no longer silently kill an in-flight Qwen VoiceDesign session** (#2070). `unload_design()` — called unconditionally from `synthesize()`/`synthesize_batch()` whenever a design was resident — ignored `_design_in_flight` entirely, so a batch render of another voice landing mid-`design_voice()` (a race window that spans a full 0.6B cold load, seconds to tens of seconds, not a narrow edge case) nulled the model out from under it, failing the design with "VoiceDesign model was unloaded before this design could render." The eviction-policy call: **the design wins** — it is short, user-initiated and interactive (someone is watching it render in cast review), while a synth is batch/background and can absorb a wait. `unload_design()` now waits, bounded, for the design to clear before evicting — sized to 150 s, above the design's own documented ~120 s cold-design server budget (itself sized to absorb that same 0.6B cold load), so a legitimately slow design isn't killed by an impatient bound. A design still running past its own budget is wedged, not slow, and only that case now raises a new typed `DesignContentionTimeoutError`, surfaced as a non-poisoned, retry-safe 503 (`code: "design_in_flight"`) from both `/synthesize` and `/synthesize-batch`.
- **`/transcribe` no longer books a cold-load VRAM peak against an ASR model that's already resident — and that resident figure can now actually be LEARNED, closing #2094 in full** (#2094). `FootprintTable.peak_mb("asr", ...)` reserved the same figure — the 400 MB cold-load seed, or a learned p95 built from cold-load observations — regardless of whether Whisper was already loaded, which on-box measurement caught refusing a `/transcribe` (`503 noCapacity`, needing 3707 MB) with `asr_loaded: true` and room on a second card. Residency is now consulted before booking: an already-resident ASR reservation keys onto a separate `asr.warm` learned-footprint bucket (128 MB conservative seed) instead of sharing the cold-load bucket. `PlacementController.admit()` — the advisory twin `reservation()`'s binding decision must not disagree with — gets the identical residency fix (review R11); before it, a starved resident-ASR `noCapacity` from `admit()` could report the cold 400 MB figure while `reservation()` reported the resident 128 MB one for the SAME request. **The measurement mechanism itself was also fixed, not just the bucket split** (review, second pass): `_observed_mb` reads torch's own caching-allocator peak, but faster-whisper's CTranslate2 backend allocates entirely outside it, so a warm ASR forward measured that way read ~0 MB — silently dropped by `record()`'s own `<= 0` guard — and never accumulated a real `asr.warm` sample; the 400 MB seed would have stood forever regardless of real usage. `reservation()` now measures ASR specifically via a device-wide free-memory DELTA (`PlacementController._device_free_mb`, `torch.cuda.mem_get_info`) instead, which DOES see CTranslate2's allocations. Two guards keep that delta honest rather than optimistic: a reading is discarded outright when any other engine holds a concurrent reservation on the same device (the ledger's own contamination signal — narrows but cannot fully close the device-wide `torch.cuda.max_memory_allocated`-style contamination question the original on-box 3707 MB finding raised, since a foreign, non-sidecar process on the same card is still invisible to the ledger), and a WARM reading above the `asr` cold seed is discarded as implausible (a resident forward should never need more than a cold load would). Seven new pytest cases (`test_asr_footprint_measurement.py`) drive `reservation()`/`admit()` end-to-end with a scripted free-memory sequence, each independently mutation-verified.
- **The ASR (Whisper) weights load now pins an HuggingFace revision, closing the last unpinned input to the golden content-drift gate** (#2047). That gate diffs a fresh transcript against a recorded baseline at **tolerance 0** — every input has to be pinned or the gate reddens for reasons unrelated to audio, and #2045 already closed the compute-type and library-version gaps; the weights revision itself was the remaining one. `WhisperEngine` now reads an optional `ASR_MODEL_REVISION` and threads it into `WhisperModel(revision=...)` — `None` (unset, the production default) is faster-whisper's own unpinned behaviour, byte-for-byte unchanged for every caller that doesn't set it. The golden tier's `_make_whisper()` pins it outright (mirroring how it already pins `ASR_MODEL`/`ASR_DEVICE`/`ASR_COMPUTE_TYPE`) to the exact commit the venv's cached snapshot already resolves to, so this is a no-op on any box with the model already cached — no forced re-download — and stamps it into the baseline's `metadata.whisper_model_revision`. Deliberately scoped to the golden tier only, not a production config-registry knob: production ASR compares against the manuscript at a real WER tolerance, so an upstream checkpoint move is harmless there, and a pin has upgrade-path consequences (stale weights never auto-refresh) that tolerance-0 testing needs but production doesn't.

**Never stall the sidecar — plan 273 and its chain.**

- **The sidecar's `/health` check — and every other in-flight request — no longer stalls while it frees GPU memory for a new voice** (#1919, plan 273). Freeing an idle model, including the multi-second host/VRAM reclaim that follows, used to run synchronously on the sidecar's single event loop, so a contended model unload could make the whole sidecar look unresponsive for as long as a Qwen forward pass or a large `gc.collect()`. Every eviction step (and its reclaim) now runs on a worker thread instead, and the admission-decision phase is serialised so two concurrent requests can't interleave their eviction logic. This also pins an XTTS race where a second Stop press during a retried cold load could itself hang — already fixed incidentally by the fs-38 Wave 3c merge (#1925, closed as superseded; this PR adds the regression test that guards it going forward). **One accepted trade-off, narrower than the plan first framed it**: on the Qwen single-utterance path (`synthesize` — the title beat, an audition, a clone-voice preview) and on the ASR content-QA pass, a Stop press (or an automatic engine swap) landing in the narrow gap between a call confirming its model is loaded and the call actually starting now fails that one call with a clear error, instead of silently reloading and continuing as it did before. Only an explicit Stop or an automatic swap can land in that gap — ordinary VRAM pressure alone cannot reach it — and it is the same trade the XTTS engine already shipped. **It does NOT cover Qwen's batched per-sentence chapter render** (`synthesize_batch`, the actual render path a book uses) or the voice-design audition forward — those three sites still silently reload in the same gap, unchanged by this PR; tracked as a follow-up in [#1975](https://github.com/dudarenok-maker/Castwright/issues/1975). Even on the paths this PR does cover, the failure is rarely visible in practice: Node's own retry wrapper (`server/src/tts/synthesise-chapter.ts`) retries a transient sidecar error up to three times at 500ms/2s, and the retry's re-ensure succeeds. Plan: [`docs/features/archive/273-sidecar-lock-event-loop.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/archive/273-sidecar-lock-event-loop.md).
- **Closes the #1919 follow-up: `synthesize_batch` (the actual chapter-render path) and `design_voice`'s audition forward no longer silently absorb an `/unload` that lands mid-load** (#1975, plan 273 T7/T8 shape). The same re-ensure-under-`_synth_lock` defect #1919 fixed for the single-utterance `synthesize` path was still present at three more call sites: `synthesize_batch`'s 1.7B branch (`:6383`), its 0.6B branch (`:6459` — the path a book's Qwen sentences actually batch through, up to `QWEN_BATCH_SIZE` at a time), and `design_voice`'s audition-preview forward (`:5674`). Each re-ensured its Base model INSIDE `with self._synth_lock:` — normally a warm no-op, but an `/unload` (or `unload_base17()`) that won the narrow gap between the pre-ensure and the lock acquire turned it into a full cold weights pull that held the Stop button off for the pull's whole duration. All three now ensure BEFORE the lock and raise a loud `RuntimeError` naming the engine if a concurrent unload wins that gap, instead of silently reloading. **Widens the accepted trade-off from #1919**: on the batch path, a raise now fails the WHOLE batch, not one sentence — but `synthesise-chapter.ts`'s `withTtsRetry` wrapper (1 primary + 2 retries, 500ms/2s backoff) already retries a transient batch failure automatically, and the sidecar's generic exception handler classifies this `RuntimeError` as a plain, non-poisoned 500 (`transient: true` on the Node side), so the retry silently absorbs it almost every time; only an explicit Stop press or an automatic engine swap can land in the gap at all — ordinary VRAM pressure cannot. Paired event-gated regression tests for all three sites, each independently mutation-verified against the producer. Plan: [`docs/features/archive/273-sidecar-lock-event-loop.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/archive/273-sidecar-lock-event-loop.md).
- **Five more in-lock cold Qwen loads survive #1975 — three of them with no pre-ensure at all** (#2021). #1975 hoisted three `_ensure_*_loaded()` calls out of `with self._synth_lock:` in `QwenEngine`; five more remained, lexically inside a `_synth_lock` block: `clone_voice`, and `mint_variant`'s 0.6B distil + audition phases, had **no pre-ensure at all** — the entire cold weights pull ran holding `_synth_lock` deterministically on every cold call, not just in a narrow race window. `mint_variant`'s 1.7B anchoring forward and `design_voice`'s DESIGN forward (the heaviest pull in the engine — the ~4-5 GB VoiceDesign model) already had a pre-ensure but still silently re-pulled INSIDE the lock on a race. **Correction (found during #2070's investigation):** for `design_voice`'s DESIGN forward specifically, that race window is not narrow — the pre-ensure call (`_ensure_design_loaded`/`_ensure_base_loaded`) IS the multi-second cold load itself, so a concurrent unload can land anywhere across its whole duration, not just in a brief gap right before the lock; #2070 addresses the ordinary-synth-initiated instance of that race directly (the design now wins), leaving only an explicit `/unload`/Stop able to reach this raise. All five now hoist their `_ensure_*_loaded()` call before the lock. The two sites that already had a pre-ensure now capture the model under the lock and raise a typed `RuntimeError` on a losing race, extending #1975's established pattern. The three with no pre-ensure keep a silent in-lock re-ensure instead of raising: `clone_voice` and `mint_variant` are user-initiated one-shot actions with no `withTtsRetry` net on the Node side, so surfacing a rare race straight to the user would be a worse trade than the (equally rare) cost of an in-lock reload. Paired mutation-verified regression tests for all five sites.
- **Unguarded `self._base17` dereferences bypassed #1975's typed error with a bare `AttributeError`** (#2022). `_load_voice_prompt_17b` — called by both `synthesize()`'s 1.7B path and `synthesize_batch()`'s 1.7B loop, in the unguarded window between the caller's `_ensure_base17_loaded()` and the eventual `_synth_lock` forward — and `mint_variant`'s 1.7B anchoring forward both dereferenced `self._base17` directly. A concurrent `/unload {model:'1.7b'}` landing in that window surfaced as `'NoneType' object has no attribute 'device'` instead of the clear "Qwen 1.7B-Base model was unloaded … reload it and retry" `RuntimeError` #1975 established elsewhere. Both sites now capture `self._base17` into a local and raise the same typed error. **Also fixed in passing** (named in the same issue as a cosmetic follow-up): `_guarded_base_synth`'s own unload-race message leaked the raw attribute name (`"Qwen _base model…"`) — it now uses the same friendly names ("Qwen Base" / "Qwen 1.7B-Base") every other message in this engine uses.

## 🔊 Generation quality & engine health

- **A sidecar that exits while still holding its port is now replaced automatically — no manual server restart** (#2037). The respawn supervisor's `spawnOnce()` set `isRecycling = false` **unconditionally** after every `spawnSidecar()` call, including its four non-benign refusal paths — most commonly a just-exited owned child's socket still in TCP teardown, which fails the "does this listener answer as our sidecar" identity check and is refused. That refusal was silently read as "nothing to do": no further respawn was ever scheduled, and `recycling()` — what `/api/models/status`, `setup-readiness.ts`, and the queue dispatcher all read — reported TTS as ready while no sidecar was listening and none would appear again short of a manual restart. `spawnSidecar` now fires a new `onSpawnRefused` callback on exactly its four non-benign `null`-return paths (not on the two benign ones — `autoStart` disabled, or a healthy pre-existing sidecar adopted); the supervisor feeds a refusal into the SAME `consecutiveFailures` backoff budget an ordinary child exit already uses, so it retries on the existing `[2s, 5s, 15s]`-capped-at-5 schedule instead of ending supervision, and `exhaustedEvent()` only flips true once that budget is genuinely spent (unchanged: `POST /api/sidecar/restart` still recovers from exhaustion). The existing safety guard is untouched — a genuinely foreign process on the port is still never killed; a `findListenerPid` comparison against the just-reaped child's pid is used only to word the log line ("our own child, still tearing down" vs a genuinely foreign listener), never to decide recovery. Note what this does and does not promise: it converts a **silent** permanent outage into a **loud, recoverable** one. The exit itself consumes attempt 1, leaving ~52s of re-probing, so a port held longer than that still exhausts the budget — but now visibly, via `exhaustedEvent()`, with `resetAndRespawn()` as the way back. Whether 52s covers the reported incident (whose port was free "minutes later") is the open question recorded as on-box acceptance row A34.
- **A Russian (also French/Spanish) dialogue line that opens with a dash now gets a real pause on the Coqui engine, and Coqui gains its own output-degeneracy guard** (#2026, found during fs-38 Wave 3 on-box acceptance, run sheet §5 Section E, E-04). On-box measurement found a leading em-dash — the standard dialogue-opener convention in these languages (`— Кто бы это ни был...`) — produced no audible pause (+0.14s vs no dash at all), while the SAME line's mid-sentence dash was honoured normally (+1.53s). The existing wire-text `softenDashes` (`server/src/tts/text-normalize.ts`) converted every dash, leading or interior, to a comma — but a comma at the very start of an utterance has no preceding word for the pause to land after, which is exactly what makes an interior comma work. A leading dash now becomes `... ` instead, mirroring how leading-ellipsis is already the ordinary way written prose marks a beat before speech resumes. Language-agnostic by construction (the transform has no language branch), so this is not a Russian-only fix. Pinned on the wire TEXT (`text-normalize.test.ts`), not audio — the audible effect is recorded as owed on-box acceptance (`docs/testing/fs38-wave3-onbox-acceptance.md`'s new `#2026` item). **Separately**, `tts.qwen.degenGuard`'s "duration implausible for the given speakable text" idea is now mirrored on the Coqui path as `tts.coqui.degenGuard` (`server/tts-sidecar/main.py`'s `_coqui_synth_is_degenerate`, reusing the Qwen guard's own conservative 20ms/speakable-char floor and minimum-length gate) — a Coqui render that comes back implausibly short for a substantial line now retries once with a fresh stochastic sample (XTTS has no fixed seed, so this is a per-call sampling fluke, never a corrupted resident model — no reload/recycle, unlike the Qwen guard's escalation). If the retry is still degenerate, the sidecar now `raise`s (`main.py:2192`) instead of shipping the short audio, which the pre-guard code had no way to catch at all; `synthesise-chapter.ts`'s `withTtsRetry` wrapper absorbs the resulting transient failure the great majority of the time, so only a genuinely stuck line now surfaces as a failed render (documented in `docs/wiki/Troubleshooting.md`'s "A Coqui line came out silent or nearly empty" section). Known, deliberate gap: this only catches an implausibly SHORT render, not the rarer full language-collapse (fluent audio in the wrong language, at a plausible duration) the same on-box run also found — catching that would need content verification (e.g. ASR), out of scope here. A third defect the same run found — a neuter Russian adjective ending (`-ее`) consistently mispronounced as `-ая`/`-ие` — was investigated and found to be **not locally fixable**: Russian has no dedicated phonemizer/G2P step in the vendored `coqui-tts` package at all (it goes straight through the generic BPE tokenizer), so the mispronunciation is baked into the trained XTTS v2 checkpoint's learned acoustic behaviour, not a text-preprocessing bug; written up on the issue with the supporting evidence rather than forced into a workaround. Golden-tier Russian coverage added (`test_cross_engine_sanity.py`'s `test_coqui_sanity_ru`) — the existing Coqui/XTTS golden checks were English-only, which is exactly why none of this was reachable by CI.
- **Coqui/XTTS no longer 500s in a sidecar that has already run an ECAPA speaker-embed** (#1944, PR #1962). Cloning always calls `/embed` (the advisory fidelity check), so clone-then-render-on-Coqui was the natural sequence that broke: speechbrain 1.1.0 leaves several lazy-proxy modules in `sys.modules` after ECAPA loads, and CPython's `inspect.getmodule()`, reached from deep inside `TTS.api`'s own import chain, chokes on one of them with an `ImportError` in a way `hasattr` can't swallow. Fixed two ways: `SpeakerEngine._load_on` now unconditionally evicts those proxies from `sys.modules` right after the ECAPA import plants them (the actual fix, deliberately unconditional and never probing a proxy, since probing one half-imports `transformers` and breaks the following `TTS.api` import a second way); and, belt-and-braces, the sidecar can eagerly import `TTS.api` at startup, before ECAPA gets a chance to run first (new "Pin Coqui import order at startup" Advanced Settings knob, default on, but only for installs that actually have the XTTS weights on disk -- it costs about 12 seconds of startup, so Qwen-only and Kokoro-only setups skip it). Two secondary defects in the same area: `/health` used to advertise Coqui as available off a find_spec-only probe that never actually imports, so it could claim an engine was ready when a real load would fail -- a new sticky `coqui_import_ok` wire field now reflects a genuine import attempt, and the Node side reads it everywhere that matters rather than on one route only (#1963) — `voice-engine-registry`'s `livePackageImportable`, and through it `models-status`'s client-facing `importable` and `models-inventory`'s `packageInstalled`, all prefer it whenever a real import has been attempted, falling back to the find_spec value only while it is still `null` (no attempt yet, or a pre-#1962 sidecar that omits the field), so that path is byte-for-byte unchanged. And the failure message used to blame a missing PyTorch for every `TTS.api` import failure, including this one, even though torch was installed and working (Qwen was rendering on GPU in the same process) -- the diagnostic now checks torch first and stops misdirecting.
- **Kokoro, Qwen and Whisper now report a real import result too, and Model Manager offers Repair on the strength of it** (#1965, [#1986](https://github.com/dudarenok-maker/Castwright/pull/1986)). `coqui_import_ok` (#1963) gave exactly one engine a signal grounded in an import that actually ran; the other three were still described entirely by `find_spec`, which never executes the module and so reports "installed" for a package that is present on disk and genuinely cannot import — the #1944 shape. `/health` now carries `kokoro_import_ok`, `qwen_import_ok` and `whisper_import_ok` beside it, each recorded opportunistically at the single import chokepoint that engine already runs on its own cold-load path, catching `BaseException` rather than `ImportError` (the second documented shape of the #1944 collision is a duplicate-kernel-registration `RuntimeError`) and re-raising unchanged. **No eager probe is added** — Coqui's startup pin costs a measured +11.7 s of unreachable boot and paying that per engine is not worth it, so `null` (nothing has tried to load that engine yet in this sidecar process) is the *common* value and the `find_spec` probe still governs there. This narrows the window; it does not close it. On the Node side `importable` — an internal server field that never crossed the wire — splits into `importOk` (a real attempt) and `specPresent` (the probe), with the "prefer the real result, fall back to the probe" rule no longer pre-collapsed in the registry accessor every caller shared, but stated where it is actually decided: `models-status`'s `packageBroken` predicate. The split is exactly equivalent to the single collapsed field it replaces, which is what let it land as a pure refactor under the pre-existing tests. `models-inventory` keeps a composition of its own — deliberately, since it has a third fallback the other callers do not, the Node-side disk probe — but now runs all six engine rows through that single helper instead of five bare `find_spec` reads plus one corrected Coqui read. And `/api/diagnostics`' Voice-engine row — which read the raw `find_spec` booleans directly and so was the one surface no registry-level fix could reach — now goes through the same accessors, and stops describing a **missing** package as "not importable": the two faults have different remedies and are now named separately. Coqui stays deliberately out of that row, since it is opt-in and an absent Coqui is not a fault.
- **The Setup checker now tells a missing voice engine package apart from a broken one too, and points at the right fix — and Model Manager's own Install/Repair buttons can no longer contradict that copy** (#1999, follow-up to #1965/#1986). #1986 fixed this conflation on the Admin console's diagnostics row only — `server/src/routes/setup-diagnosis.ts`, the first-run Setup Wizard's own blocker copy, was left reading the already-collapsed `packageBroken` boolean and still rendered every fault as *"A voice engine package is not importable"* with a *"Repair in Model Manager"* instruction, the wrong verb for a package that was never installed. The missing-vs-broken precedence (a real import that returned wins outright; a negative `find_spec` beats a negative real import, because that combination is one fault, not two; a real import failure alone is the remaining case) is now one exported `classifyPackageFault` (`server/src/tts/models-status.ts`, `PackageFault = 'ok' | 'missing' | 'broken'`), read by all three surfaces — `diagnostics.ts`, `setup-diagnosis.ts`, and Model Manager's `engineInstallLabel` plus its three install cards (`kokoro-install.tsx`, `coqui-install.tsx`, `qwen-install.tsx`) — so none of them can disagree about which fault an engine has, or offer a button that contradicts the message next to it. A missing package now names itself as missing and points at installing it in Model Manager; a present-but-unimportable one still names itself and points at repair. When Kokoro and Qwen have *different* faults at once, a live-confirmed broken package always outranks a merely-missing one when the Setup checker picks which engine to name — a broken package is the fault the user cannot infer on their own, a missing one is self-evident from Model Manager's own inventory. `importOk === null` — nothing has attempted the import yet, the common case for Kokoro/Qwen — still reads as healthy on all surfaces, unchanged. **This also widens four of the eighteen input combinations from a false "a voice engine is ready" to a correctly-failing blocker** — not only the single `importOk === false` shape named in the original commit, but also the everyday shape where nothing has attempted the import yet (`importOk` unknown) and the package is confirmed absent (`specPresent === false`), whichever of the two axes the disk probe itself already knew about. No new false positive: `anyEngineUsable` was already `false` in every one of the newly-failing cases, so each one was silently reporting success for a book that could not actually render.
- **An ASR content-QA hiccup (a misconfigured `qa.asr.model`, a wedged transcribe call) no longer aborts an otherwise-complete chapter render** (#2011, v1.15 correctness sweep). `synthesise-chapter.ts`'s ASR content-QA pass had no `try`/`catch` around its `verifySegmentTranscript` call, unlike the structurally identical SPK speaker-embed pass 60 lines below it, which is explicitly documented as non-fatal — so a `/transcribe` rejection (e.g. an unresolvable Whisper model repo) propagated straight out of `synthesiseChapter` and killed the whole chapter, discarding real GPU time already spent on synthesis. A transcribe/classification failure is now caught narrowly (independent review of PR #2126, R2 — only the `verify()` call itself is wrapped, not the surrounding re-synth, so an unresolvable cloned voice or a real sidecar capacity error inside a re-record still aborts the chapter exactly as before) and logged rather than thrown, leaving the affected segment's QA verdict "unavailable" (its `asr` field comes out `undefined`, same as a chapter rendered with ASR off). A genuine cancellation, and the sidecar-thrashing `RecycleStormError` signal, both still propagate — those are deliberate whole-chapter stop conditions, not "this one gate didn't run." A related review finding (R1) closed a narrower hazard in the same pass: the best-of-N re-record loop used to defer committing a group's shipped PCM to a single pass run after every round, so one sibling group's swallowed verify failure could leave a DIFFERENT group's shipped audio disagreeing with its own stamped verdict; the commit now happens in lockstep with the verdict, at the same point, so that can no longer happen. Whether an unresolvable model name should also fail *early* (at settings-save or sidecar start, via a cheap probe) is deferred to [#2131](https://github.com/dudarenok-maker/Castwright/issues/2131) rather than folded into this fix.
- **`gpu/sidecar-vram-sample.ts` no longer reaches a route module by a dynamic `import()`, closing the last `gpu/` → `routes/` reach-through** (#2052, v1.15 correctness sweep). CLAUDE.md's "gpu/ reaches a route module through a leaf gate, never an import" convention had one live exception: the VRAM sampler dynamic-`import()`ed `routes/sidecar-health.ts` on every sample instead of going through `gpu/sidecar-health-gate.ts` like every other reader. It now goes through that gate (widened with two additional optional fields — `qwenDesignEverLoaded`, `vramReservedMb` — both already present on the registered provider's real return shape, so the existing `capacity-retry.ts` consumer is unaffected) and fails closed the same way the gate already does: nothing registered yet → no sample recorded, not a crash. The layering guard in `gpu/engine-device-state.test.ts`, previously scoped to one file specifically to dodge this line, now sweeps every `gpu/*.ts` source file. `npx madge --circular --extensions ts server/src` confirms the documented 15-cycle baseline still holds (this file was never part of the cycle count — the hazard was latent, not active). Two follow-on review fixes (PR #2126): the "fails closed" test was itself a placebo — asserting an empty stats file couldn't tell "returns early by design" apart from "throws and is silently swallowed by the surrounding best-effort catch," and two follow-on spy attempts (on `recordVramSample`, then on the same-module `sampleSidecarEngineVram` export) were each proven placebo in turn by mutation-verifying against the deleted guard line before a one-line debug log on the fail-closed branch itself gave the test something to assert that the mutation genuinely removes. That log doubles as the second fix: nothing previously signalled when this path silently drops a VRAM sample because nothing has registered with the gate yet (safe in the real server, since `app.ts` mounts the router before any generation call reaches here — but a future entry point that doesn't would otherwise lose fs-45 footprint data with zero signal).
- **The `withDesignLock` per-book voice-design serialization primitive's series-branch double-mint property now has real test coverage** (#2088/srv-85, v1.15 correctness sweep). `tts/design-lock.test.ts` already covered the primitive in isolation, but `qwen-voice.test.ts` — its only real caller under test — had none of it: neutralising the lock to a no-op left that file's other ~76 tests fully green, because `ensureCharacterVoiceUuid`'s book-scoped path is tight enough (one read, one synchronous loop, one write) to self-serialize even unlocked in practice. The property the lock actually buys there shows up on the SERIES branch, where the mint decision precedes a multi-`await` cross-book workspace fan-out — a real race window where two concurrent calls for the same book can both see "no voiceUuid yet" and mint two different ones. A new regression test races two concurrent series-branch calls and asserts they agree on one uuid; verified by neutralising the lock and confirming the test reddens (a different uuid on each side) across five separate process runs, then restoring it green. Independent review of PR #2126 (R5) found a genuine pre-existing bug while covering the primitive: `withDesignLock`'s tail-cleanup check compared the wrong promise object and so never fired, leaking one settled promise per book into the module's chain map for the life of the process — small in practice (a Map entry, not a resource), but dead code masquerading as cleanup. Fixed, and covered by two new tests that assert on the chain map's size — which a follow-on review pass (F1) found were themselves a retry-hazard placebo (module-level mutable state, no `{ retry: 0 }`, so a reverted fix still read green under the suite's default `retry: 1`): reverting the fix now reddens deterministically (2 failed / 6 passed) under both `--retry=0` and the default config, and the primitive's `describe` block runs under `{ retry: 0 }` so that stays true going forward.
- **A Coqui/XTTS language-collapse (fluent audio in the WRONG language, at a plausible duration) can now be caught by the ASR content-QA gate instead of slipping past it** (#2055, follow-up to #2050's duration-only guard). #2050's `_coqui_synth_is_degenerate` only catches a render that comes back implausibly *short* — it cannot catch #2026's actual reported collapse, a fluent multi-word utterance at a normal, plausible duration; a duration ceiling for the hallucinated-tail variant was considered and deliberately not attempted (no safe healthy-duration baseline). The per-sentence ASR content-QA gate (`segment-asr-qa.ts`) already runs uniformly across every engine including Coqui — no engine-specific gap there — but its own "untrustworthy transcript" backstop (low avg_logprob / high no_speech_prob → `inconclusive`, never a re-record, so the gate can't be trained into chasing every mangled invented name) was exactly what let this shape through: forcing Whisper to decode a wrong-language clip in the book's configured language routinely looks low-confidence even though the render is genuinely broken, and that's indistinguishable from "hard to transcribe but correct" on confidence signals alone. `classifyTranscript` now computes the word-error-rate even for an untrustworthy transcript and only overrides the `inconclusive` verdict to `drift` when BOTH: (1) the WER is at or above `Math.max(catastrophicWer, maxWer)` — never a fixed bar that could sit BELOW an operator-raised per-language `maxWer` (#1084's whole scaffold exists to let one language's cap rise, and a fixed catastrophic bar would have made the untrustworthy branch stricter than the confident one at the identical WER, review R2); and (2) the transcript looks like a genuine full-length collapse, not a filler-padded near-silence or a short reference where "both words wrong" is unremarkable — a reference of at least 6 words (review R3: on a 2-word reference like #2055's own repro lines, a wholesale collapse is statistically indistinguishable from two ordinary mishearings), a heard transcript at least half the reference's length, and a deletion run under `maxDeletionRun` (review R1: a near-empty/filler-padded transcript — `'um'`, `'um uh'`, and critically a Russian Whisper near-silence hallucination like "Продолжение следует…", invisible to the English/Latin-only `HALLUCINATION_PATTERNS` list — reaches WER 1.0 too, but is TRUNCATION, `maxDeletionRun`'s job, not a content collapse). The threshold (`CATASTROPHIC_WER`, default 0.85) is now a live registry knob, `qa.asr.catastrophicWer` — a judgement call already written into an on-box acceptance row (A37) needs to be retunable from real false-positive-rate evidence without a release. 8 new/updated regression tests, each gate independently mutation-verified.
- **A Content-QA (Whisper) device chosen in Advanced Configuration now actually reaches GPU capacity-admission retry — before this it only worked if `ASR_DEVICE` was hand-set in `server/.env`** (#2178). `asrRunsOnGpu()` (`transcribe-client.ts`), the one gate deciding whether a `/transcribe` call is wrapped in the evict-and-retry path a busy card needs, read `process.env.ASR_DEVICE` directly instead of resolving `qa.asr.device` through the config registry (env → override store → default) like its sibling knobs — so a device picked in the UI never reached this one call site, and ASR silently skipped capacity retry on a card that genuinely needed it. Now resolved through `configValue('qa.asr.device')`; an `.env`-set `ASR_DEVICE` still takes precedence over a UI override, unchanged.
- **Saving a Content-QA (Whisper) device / compute-type pair that would fail every transcription is now refused when you save it, not the next time a chapter renders** (#2180). CTranslate2 supports a different set of compute types per device (measured on this box, ctranslate2 4.8.0: `cpu` → float32/int8/int8_float32; `cuda` → bfloat16/float16/float32/int8/int8_bfloat16/int8_float16/int8_float32) and nothing previously checked the two settings together — changing just one of them in Advanced Configuration, leaving the other at whatever it already was, could silently leave an incompatible pair in place. Saving now checks the pair you'd actually end up with (not only whichever field the request touched) and, if it's incompatible, refuses with a message naming both settings and what IS supported for the device you picked. The sidecar's own auto-negotiating sentinel values are always accepted on every device. The device field is also now restricted to `cpu`/`auto`/`cuda`/`cuda:<n>` — a typo like `cuda1` used to be silently accepted. Corrected here (independent review of PR #2205, finding F5): it did NOT fall back to CPU — `_parse_device` (`server/tts-sidecar/main.py`) matches on the `cuda` prefix first and only the trailing index parse fails, so the malformed value kept the `cuda` family with a `None` index and Whisper silently ran on the sidecar's default GPU instead of CPU or the card the typo was presumably meant to pin.
- **A rejected Content-QA (Whisper) device value in `server/.env` no longer still reaches the sidecar process** (#2207, found by the independent review of PR #2205; narrows and reintroduces #2178's server/sidecar disagreement through a different door). #2180 taught the resolver to reject an out-of-pattern `ASR_DEVICE` (e.g. `cuda1`, missing the colon) and fall through to the registry default — but `buildSidecarEnv` started from the parent's full environment and only ever *overwrote* a restart-sidecar knob's env var when the server resolved something other than its default, so a rejected value survived verbatim in the child process's environment while the server itself had already resolved `cpu`. The sidecar's own device parser is more permissive than the resolver's pattern (it accepts anything starting with `cuda` as that family), so Whisper could silently load on the default CUDA card, skipping capacity-retry on a card the server believed was idle. `buildSidecarEnv` now deletes a restart-sidecar knob's env var outright when the resolver rejected the ambient value, before applying any resolved override — so a UI override for the same knob still reaches the sidecar, and a knob left at its registry default is still left unset for the sidecar's own Python default to apply, matching every other knob's existing convention. `server/tts-sidecar/main.py`'s parser is unchanged; the server just stops sending it garbage. A blank/whitespace-only ambient value (e.g. a half-restored `GPU_RESERVE_MB=` line) is treated the same as a rejected one and deleted too — `main.py`'s `int(os.environ.get("GPU_RESERVE_MB", 500))` has no guard against an empty string and would otherwise raise at capacity-admission time.
- **A Voice-QA (speaker-embedding) device chosen in Advanced Configuration now actually reaches GPU capacity-admission retry — the same #2178 defect, on its other twin** (#2224). `spkRunsOnGpu()` (`embed-client.ts`) read `process.env.SPK_DEVICE` directly instead of resolving `qa.speaker.device` through the config registry, so a UI-set override never reached it and the speaker embed silently skipped capacity retry on a busy card. Now resolved through `configValue('qa.speaker.device')`, mirroring `asrRunsOnGpu`'s #2178 fix; an `.env`-set `SPK_DEVICE` still wins over a UI override, unchanged. Its doc comment's claim that it read "the SAME `SPK_DEVICE` env the sidecar reads" was already false before this fix (the two only agreed when nothing but `.env` was ever used) — corrected to describe the actual resolution order. **Also fixed, found in passing:** `qa.speaker.device` had no validated `pattern` at all before this — a malformed `SPK_DEVICE` (e.g. `cuda1`) was silently accepted at the coercion layer, unlike `qa.asr.device` since #2180. It now shares `qa.asr.device`'s exact `^(cpu|auto|cuda|cuda:\d+)$` pattern (a widening to also accept `mps`/`rocm` was considered and explicitly rejected — checked against `main.py`, `rocm` is a *derived reporting label* the sidecar produces for an already-`cuda` value, never a value an operator sets, and CTranslate2/speechbrain-on-ROCm cannot actually place either literal string; accepting them would have been a regression, not a fix).

## 🎧 Listening & revising

- **Re-recording one character's lines can no longer render another character's lines in their voice** (#1972). The per-character re-record (splice) picked *which* segments to replace from the chapter's `segments.json` — written at the last render — but resolved those segments' sentences, and therefore the voice, from the **current analysis cache**, matching by sentence id. Once analysis had run since that render the two disagreed, and the re-record synthesised whoever the analysis now says owns the sentence, in the requested character's voice, spliced into their old time slot. Measured on a real book: the re-recorded lines scored **0.888** speaker-similarity against the *narrator's* lines in the same chapter and **0.196** against the character's own assigned voice. It reproduced with a perfectly healthy voice, and on two books that had diverged for unrelated reasons — one from stale attribution, one from ordinary re-segmentation — so **the only precondition was "analysis has run since the last render."** A splice now compares the two sources first and **refuses** rather than reconciling silently, naming how many segments changed owner and pointing at re-running analysis or a full chapter generation; deciding for the user would have been just as likely to destroy correct data as to fix it. **Full chapter generation was never affected** — it reads one source and stays self-consistent. Separately, `characterSnapshots.<id>.resolvedVoiceName` is now recorded from the voice actually sent to the engine instead of being re-derived from the cast record afterwards, so it can no longer report a voice that was never used — which is exactly why this went unnoticed for as long as it did.
- **fs-10 — chapter-title segment on the Listen timeline** (#412). `ChapterAudio.segments[]` gains an optional `kind: 'title'` discriminator and the chapter-audio route stops filtering the synthetic title beat out of both `/audio` and `/audio/previous`. The mini-player scrubber paints it as a non-interactive labelled band; the Generation view's "Narrative order" strip fills it neutrally rather than in the narrator's colour. **Also fixes a latent off-by-one:** because the published array was short one leading row, `resolveSegmentForSec`'s index no longer matched the on-disk index the splice route addresses, so Listen-view "Fix this line" targeted the line before the marked one.
- **The audio-QA repair endpoint finally has a frontend consumer** (plan 179). `POST …/chapters/{id}/audio-qa-repair` shipped with its "Scan & repair" affordance listed as a follow-up and never got one — a grep for the path or any `qaRepair`-shaped symbol across `src/` and `e2e/` hit only the generated types. That also meant the `voice_language_mismatch` advisory the route emits went nowhere at all. Adds `api.streamQaRepair` (real + mock), `qa-repair-slice`, and `qa-repair-runner-middleware` — deliberately mirroring `splice-runner-middleware` rather than inventing a third SSE-consumption idiom, since the repair runs through the fs-26 splice engine server-side anyway — plus a repair button on the Listen view's chapter row, gated on the srv-27 `suspect` verdict so it can't invite a pointless GPU pass on healthy audio. The middleware toasts the stream's `warning` frame the way `generation-stream-runner` toasts its own, refreshes the row's duration + cache-bust stamp on completion, and reports failures. It does NOT enqueue an A/B revision: a repair spans whichever characters owned the flagged sentences and `revisions` is keyed by a single characterId. Coverage: `qa-repair-runner-middleware.test.ts`, `listen-player-region.test.tsx`, and `e2e/qa-repair.spec.ts` walking row → middleware → mock stream → rendered toast. No OpenAPI change was needed — the QA-repair response schema already carried every field consumed.
- **A background QA repair or splice can no longer stamp the wrong book's chapter, or strand its spinner.** Both runner middlewares dispatched their chapter-updated action keyed only by chapter id — which repeats across every book — with no check that the user was still looking at the book the repair/splice belonged to, so one finishing after a book switch could mark a different book's same-numbered chapter as freshly rendered. Both now guard on the currently-open book before dispatching. Separately, an unexpected error during the repair stream (a network drop, a bad frame) used to reject past the cleanup step entirely, leaving `Repairing…` showing with no way back short of a reload; the stream call is now wrapped so any failure runs the same cleanup and summary toast a normal finish does. The QA-repair control also collapsed to 32 px at `md:` widths — squarely the tablet range — and now meets the 44 px touch target.
- **The splice stream's `warning` frame no longer falls on the floor.** `chapter-splice.ts` has always emitted a `warning` frame when `clearMismatchedDesignedVoices` drops a reused designed voice whose baked manifest language differs from the book's — but `warning` was in neither the splice endpoint's OpenAPI `type` enum nor the hand-written `SpliceTick` union, so `splice-runner-middleware`'s `onTick` parsed the advisory and silently discarded it. Adds the member to both (plus the `code`/`message` fields it carries, mirroring the QA-repair stream's) and toasts it the way `generation-stream-runner` toasts its own, deduped by `code` so a multi-chapter batch raises one advisory rather than one per chapter.
- **A correctly-normalised chapter could show a false "off target" loudness pill — fixed** (srv-67/fe-58, #1922, #1923). The chapter QA verdict and the Listen-view loudness badge used to read two different numbers for the same chapter: QA judged loudnorm's self-reported `output_tp` (in dynamic mode, the requested ceiling restated, not a measurement) or, when the real re-measurement failed, loudnorm's *pre-filter* input loudness — which could bucket a chapter that actually normalised fine as several LU "off target." The single real `ebur128` measurement is now taken once, immediately after the chapter's audio is written, and feeds both the QA verdict and the Listen-view badge — they can no longer disagree. A new optional `measurementSource: 'ebur128' | 'loudnorm'` field on the loudness sidecar distinguishes an attested measurement from a fallback; a pre-change sidecar (no field at all) renders exactly as it did before, so no existing chapter loses its badge. **Both of these are true, and neither cancels the other:** the chapter QA true-peak clip check now consumes this same real measurement instead of a fabricated ceiling, AND it still cannot fire under shipped defaults — dynamic loudnorm pins the encoded peak at roughly the requested ceiling +0.1…+0.3 dB, and the default ceiling (`-1.5` dBTP) sits 1.4 dB below the default clip threshold (`-0.1` dBTP). Making the check active is a threshold/ceiling decision, deliberately left to [#1909](https://github.com/dudarenok-maker/Castwright/issues/1909) rather than retuned here. Also established: loudnorm's `output_tp` under-reports the real measured peak by 4.15 dB in linear mode (requested `-1.5`, reported `-5.85`, measured `-1.7`) — nothing downstream should read it as a peak figure, in either mode. #1923, as originally filed, described unreachable behaviour (`twoPass` is hardcoded `true`, so single-pass output never ships) and closes as not-reproducible; this fixes the real, reachable version of the same underlying defect — a measurement-failure fallback rendering as trusted ground truth. `scripts/relufs-existing.mjs`'s backfill now stamps `measurementSource: 'ebur128'` on its rewrite, so it remains the way to upgrade a pre-change chapter to a genuinely attested one. Plan: [`docs/features/archive/274-loudness-measurement-provenance.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/archive/274-loudness-measurement-provenance.md).
- **The Listen-view loudness badge no longer trusts an unrecognised future `measurementSource` value as if it were a legacy pre-plan-274 sidecar** (#1949). `classifyDrift` grandfathered a genuinely *absent* `measurementSource` field to the old `twoPass`-only rule — but an unrecognised value (a closed enum today, but nothing stops a future member) fell through the same path, which would have rendered an unattested measurement as ground truth. Added an explicit guard so only `undefined` reaches the grandfather branch; any other unrecognised value renders as "No measurement," matching the existing `'loudnorm'`-fallback treatment.
- **A re-recorded line's "this used a substituted voice" diagnostic no longer goes stale after a repair** (fs-38 Wave 3c follow-up, `[ADV-H6]`, #1888). `voiceSubstitutedFrom` — the per-segment flag surfacing a silent fallback-voice substitution — was always computed correctly by the repair's own re-synth (`synthesiseChapter`), but got dropped before it ever reached the persisted segment: both repair routes' inline `synth` closures (`chapter-splice.ts`, `chapter-qa-repair.ts` — the latter also in its local best-take tracker) never read it off the fresh render, and `buildSynthReplacements`'s `freshVerdict` never carried it into the `SegmentReplacement` the splice engine (`splice-chapter.ts`) merges back into `segments.json`. Fixed by threading the field through all four sites, and — unlike `voiceName`/`baseVoiceName`'s omit-when-absent convention — **unconditionally**: a re-record always has a definite substitution answer, so an omitted key would let a clean repair's merge silently preserve a stale substitution flag from before the repair. Diagnostics/observability only — this does not change which voice actually renders or how substitution itself is decided. Plan: [`docs/features/271-fs38-wave3c-xtts.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/271-fs38-wave3c-xtts.md), "Known limitations (g)".
- **The re-record merge's `voiceSubstitutedFrom` field is now required (not optional) on `SynthOutput`, and `SegmentReplacement.freshVerdict`'s `Pick<>` now lists `baseVoiceName`** (#2034). `build-synth-replacement.ts:71` declared the field optional while `:127` wrote it unconditionally (deliberate, #1888: omitting the key is how a merge preserves a stale substitution flag). That inverted the field's hazard — a future `buildSynthReplacements` caller that forgot to thread it would now silently *wipe* a genuine substitution flag, with no type error and no failing test. ## 🗣️ Analyzer, script review & manuscript

- **The analysing-view analyzer pill's Load/Stop lifecycle no longer briefly reports a residency it doesn't have** (#1929). `handleStopAnalyzer` set the optimistic pending state straight to `'idle'` — inviting a Load click — before `api.unloadAnalyzer()` had actually resolved, and the screen's own 30s health poll cleared `pendingAnalyzerPill` unconditionally on every tick with no in-flight guard, so a tick landing mid-unload (or mid-load) reverted the pill to a stale reading while the real operation was still running. - Detect emotions can now be scoped to the current chapter — the header button runs the emotion + reaction passes on just the chapter you're viewing, with whole-book still available from its ⌄ menu. (fs-35, #592)
- **The dialogue-structure aligner no longer strands a whole chapter on one ambiguous short line** (#2187). `locateSentenceOffsets`/`alignSentences` walked sentences with a single monotonic cursor; a miss never moved it, but a *wrong hit* did — `findMatch`'s unbounded `indexOf` fallback let an ultra-common short line (`"- Да."`) bind thousands of characters downstream, dragging the cursor with it and stranding every later sentence. Because chapters below the hardcoded 80% alignment floor disable correction chapter-wide, this silently reduced the shipped engine to flag-only on exactly the book class it was built for: Russian paragraph-leading dash dialogue. Replaced with anchor-first, two-pass, interval-bounded location — Pass A anchors only needles ≥ 24 normalised chars on an exact match, Pass B resolves everything else against the haystack *sliced* to `[prevAnchor.end, nextAnchor.start)`, so a short line structurally cannot match outside its bounding anchors. Measured by replaying the 15,069 cached stage-2 sentences from the 2026-08-06 *Ночной дозор* on-box run through the production parser and aligner: per-chapter 3.7→94.6, 1.7→92.7, 66.4→92.0, 73.5→95.7, 63.9→99.7%, book 67.7→96.0%, with the before-column reproducing the on-box report to within rounding. Every chapter now clears the floor. Exported signatures and normalisation are unchanged; no existing test needed modifying.
- **Dialogue lines in badly-converted EPUBs no longer silently become narration.**
  When a source file loses its paragraph breaks, the structure engine loses the
  speech spans it reasons from and used to rewrite every affected dialogue line
  to `narrator` as an unflagged correction — 879 lines on the reference book.
  A line that opens with the language's own dialogue marker now keeps its
  speaker and is surfaced as low-confidence instead. (#2253, PR #2266)
- **`structureReport` splits `flagged` into `flagged` and `unresolved`** so a
  genuine model-vs-structure conflict is countable separately from "no evidence
  either way", which was 99.9% of the old bucket. Additive optional field on
  `analysisProvenance.report`; no schema bump. (#2253, PR #2266)
- **`isSpokenLine` is now conventions-driven instead of a language-blind regex bundle, and an unsupported language no longer demotes an entire book to the narrator** (#2245). The old bundle carried only one of German's four `de.quotePairs` forms (`„…“`) and recognised no CJK quote glyphs at all — three of four German forms and every zh/ja quote-only line were silently missed. `isSpokenLine(text, conventions)` now reads the same per-language `dialogueOpen`/`quotePairs` tables the dialogue-structure engine uses: a leading dialogue marker, a leading quote opener, or an embedded `open…close` span (matched via `indexOf`, not a built regex). Measured over the live 20-book/109,609-sentence corpus: **-83/+226** net **+143** — the 83 lost English lines are a leading-dash rule going away (`en.dialogueOpen` is `null`; all 83 are name credits, stage directions, headings and split-sentence continuations, zero of them dialogue) and the +226 gained are the previously-unrecognised zh/ja quote-only dialogue and the fixed German forms. Separately, `analysis.ts`'s conventions resolution is split off the `analyzer.structure.enabled` knob — it used to be `knob ? conventionsFor(lang) : null`, so turning the structure engine off also discarded the book's language; the fallback branch then ran the language-blind heuristic on every book regardless of what language it was. It is now `conventionsFor(lang)` unconditionally, with the knob gating only the engine, so the fallback gets the book's own quote rules. The no-table case is handled in `applyNarratorDefault` alone (`isSpokenLine` now requires a non-null table, so "no table ⇒ no demotion" is structural rather than a regex accident): with `conventions === null` the sentence list is returned by reference, untouched, rather than getting the most aggressive rewrite available — which is the shape of two historical near-total attribution collapses. `forceNarratorOnNonSpokenLines` is retained with no production caller, per its existing "do not delete" note.
- **`POST /api/books` now rejects an unsupported book language at the import boundary** (#1955). The confirm-screen language dropdown only constrained the browser — `normaliseBookLanguage` lower-cased whatever BCP-47 tag it was handed with no support check, so a direct API call could persist e.g. `'pt'` onto `state.json` even though the language registry has exactly seven entries (en/ru/es/fr/de/zh/ja). Pre-fix, an unsupported language surfaced only at render time as an opaque `chapter_failed` (`sidecarLanguageName`'s existing throw in `generation.ts`), several expensive steps — analysis, casting — after the user chose it. The route now checks `isSupportedLanguage()` before any disk write and returns 400 `unsupported_language` naming the supported set; nothing is persisted and the staging entry survives for a corrected retry. The render-time throw is unchanged and still the backstop for any other write path.

For that one input, detection falls through to the single-chapter path over the whole document, front matter included — but **not** "the way it used to": the prose floor now runs on that path too, so a headingless 675-word German `.txt` that used to resolve `{language: 'de', fallback: false}` now resolves `{language: 'en', fallback: true}`.

### The release-notes gate

- **A release can no longer be cut from a mojibake-corrupted notes file, and the v1.15.0 draft has been repaired** (#1956). `docs/release-notes-next.md` is fed verbatim as the annotated-tag message by `bump-version.mjs` → `release.yml` and **is** the GitHub release body, so its 242 double-UTF-8-encoded spans were queued to publish as the public notes for this release. Correct UTF-8 had been read as windows-1252 and re-encoded, mangling every em/en dash, ellipsis and arrow, every emoji section header, `§`, `↔`, `≥`, `∩`, `⇒`, and the Cyrillic endonym `Русский`. Repaired by a targeted per-span scan, **not** a whole-file round-trip — the corruption is span-local, so a blanket latin1→UTF-8 pass emits `U+FFFD` and destroys the parts that were already correct. `release-notes-gate.mjs` gains `findMojibake`/`checkMojibake`, wired into both of its existing enforcement points (`bump-version.mjs`'s pre-flight and `release.yml`) and covering `RELEASE_NOTES.md` as well; `scripts/tests/release-notes-gate.test.mjs` asserts the two real committed files are clean, so `npm run test:hooks` catches a recurrence at commit time rather than at tag time. Nothing in the repo writes to that file — `bump-version.mjs` and the gate only read it, no `.ps1` touches it, and there is no `.editorconfig` or `.vscode/settings.json` — so there is no call site to correct and the guard is the fix.
- **A legitimate accented word can no longer block a release publish, and an allowlist marker can no longer over-suppress or arm itself silently** (#1973, #1985, #1990, #2025). The mojibake gate's acceptance rule — cp1252-mappable characters whose byte values form valid UTF-8 with a lead byte >= 0xC2 — is satisfied by some genuinely correct text: any Latin-1 letter mapping to 0xC2-0xF4 sitting immediately adjacent, with no space between, to one to three characters mapping to 0x80-0xBF. Measured shapes include `CAFÉ` followed by `™`, a `groß` + em-dash construction, and `Ålesund` beside punctuation. `bump-version.mjs`'s pre-flight already honoured `--force`, but `release.yml`'s CLI path exits 1 with no bypass at all, so a false positive there blocked the publish outright and the only way out was editing the prose. The notes file can now name the exact literal to accept, in a `release-notes-gate: allow` HTML comment carried by the file itself — chosen over an env-var kill switch because it is span-scoped, travels in the same commit as the text that needs it, and is auditable in the diff, and because an HTML comment renders as nothing on the releases page, which matters when this file ships verbatim into the tag annotation. (The exact syntax, with a copy-pasteable example, lives in CONTRIBUTING.md's "Release notes" section rather than here, because this file is one of the two the gate reads and a realistic example written into it would allowlist itself.) A marker does **not** expire on its own: this file is cleared by hand in the first PR after a cut, which happens to take any marker in it along. `RELEASE_NOTES.md` is cumulative and never reset, so the gate refuses any marker found there outright (#1985) — the failure names the file and points at re-encoding the text or `bump-version.mjs --force`, rather than letting a marker sit there silently excusing its literal for every future release. **Suppression is positional, not by substring.** The span the detector reports for a flagged `CAFÉ`+`™` is just the two-character tail, so excusing every span whose characters merely appear somewhere inside an allowlisted literal would silently swallow the same two characters genuinely corrupted elsewhere in the same file — quietly reintroducing #1956, which is the whole reason the gate exists. A span is dropped only when it sits wholly inside a real occurrence of an allowlisted literal in that same text; the marker line's own copy of the literal is self-excusing as a consequence of that rule rather than as a hand-coded special case. Applied inside `checkMojibake`, so both enforcement points inherit it with no change at either call site, and `--force` is untouched. **An allowlisted literal must be a single whitespace-free word that contains the span and extends past it.** A literal is excused at *every* occurrence, so one naming just the flagged characters would silence them file-wide — the same hole positional suppression exists to close; a literal carrying any whitespace at all (space, tab, non-breaking space) is rejected outright and excuses nothing, not even its own copy in the marker line. That rule encodes why a false positive is legitimate in the first place: the detector only fires on a Latin-1 letter adjacent to punctuation, so genuinely-legitimate text always carries the surrounding characters that made it legitimate, and a span with nothing around it is by construction a real mangle. Measured against the 242-span file this gate was built for, the bar is tight: the best single hand-written marker suppresses **4** spans, only **30 of the 242** are suppressible by any marker at all, and a green gate is **not reachable** — **212** spans always remain, whatever is allowlisted. So the failure message prints a paste-able marker line only when a valid literal genuinely exists, and otherwise names which of three reasons applies — the span stands alone, with no surrounding word to name; the word around it carries a `"` or a `-->` that cannot go inside the marker's own quoting; or the flagged span itself straddles a whitespace character, so no literal containing it can be whitespace-free (a doubly-encoded non-breaking space is `Â` + NBSP, and a doubly-encoded Cyrillic `Р` is `Ð` + NBSP, so a corrupted Russian endonym is un-allowlistable by construction) — and points at re-encoding instead. It never prints a line that would not work or would over-suppress, and it states outright that a marker naming only the span suppresses nothing. That three-reasons diagnostic applies to `docs/release-notes-next.md` only; a `RELEASE_NOTES.md` failure short-circuits straight to the re-encode / `--force` advice, naming none of the three, since a marker cannot be used there at all (#1985, #2025). **There is no fence exemption** (#1990): a marker anywhere in the file — inside a backtick or `~~~` fence, a four-space-indented block, a fence nested in a blockquote — is honoured exactly like plain prose, because proper fence tracking is a markdown-parsing problem this gate has no business owning. What stands in for it: the gate **echoes every marker it honours on every run that reaches the file, pass or fail** (`[allow] <file> honoured N literal(s): …`), so an accidental arming is visible rather than silent — and that echo's ordering relative to the failure branch, which is the entire property, is pinned by a failing-run spawn test at both call sites (#2025). Two fail-closed bounds land alongside: the mangled length of a span is measured from the reversed bytes at match time rather than inferred from the decoded lead code point (a greedy four-character match can hold two mangles rather than one mangle plus context, and inferring the length judged only the first half and dropped the genuinely-corrupted second half with it); and a marker must be complete on a single line, where before it ran on to the next comment terminator anywhere in the file and harvested every quoted phrase in between as a literal. Two bounds are recorded in the gate's own header comment: the false-positive trigger above, and the **lossy** double-encode it silently misses, where the corrupting round-trip normalised a mojibake character away (`Â` plus a non-breaking space flattened to `Â` plus a plain space) so the reverse bytes are `C2 20`, not valid UTF-8, and the span never decodes and is never reported. Inherent to the reverse-decode approach: a green gate is evidence, not proof, that a file is clean.

### Test harness & suite hygiene

- **The `test:hooks` completeness guard now sees the whole dependency graph, not just direct imports — and two files it was blind to are now declared** (ops-20, #2120). That guard is what stops a hooks test reading a file nobody declared as an input: when that happens the cache prints `[cached]`, and the test never re-runs on the change that breaks it. It found direct imports by regex, so anything one hop further away was invisible. It now walks the graph transitively.
  - **Three things had to be true for a transitive walk to be shippable at all.** *Parsing:* two hand-rolled comment-stripping lexers were written for this and both were defective — the second could read `return /a\/*b/;` as division, let `/*` open a phantom comment that a later `*/` closed, and swallow every import in between while its own desync detector reported clean. That fail-open is unobservable by any test, so the approach was deleted rather than patched a third time; `acorn` parses all 63 hooks tests with zero failures and correctly ignores a specifier sitting inside a comment or a string literal. *Scope:* a naive walk demands **24 new declarations, 22 of them gitignored `server/dist/**` build artifacts** that would rot on the next rebuild, so the walk stops at gitignored paths — batched through one `git check-ignore --stdin` call (**3430 ms → 52 ms** versus spawning per path), fail-closed on exit 128 or a spawn failure rather than guessing. *TypeScript:* `acorn` is a JavaScript parser, and one of the two genuinely-missing files is `server/src/handoff/schemas.ts`, which it cannot parse — so an unparseable file is recorded as a **leaf**: still a dependency the guard demands be declared, not recursed into, and reported in its own list so the un-followed edges stay visible.

Two latent defects in the guard went with them — it used to `continue` past a producer it could not resolve (an unresolvable dependency read as "clean"), and its anti-vacuity floor was set to 30 against a measured 60 that counted *occurrences* while the guard compares *unique files*. Both units are now named in the comment beside the floor, so that particular confusion cannot recur silently.

Separately, `"404s for an unknown book"` — a bare request with no shared state, so not the same defect — now polls its own assertion (`expect.poll(..., { timeout: 10_000 }).toBe(404)`) instead of trusting one shot, absorbing the same full-suite contention `vitest.config.ts`'s `maxForks` tuning already targets without weakening what it checks; mutation-verified (forcing the route to answer 200 still reddens, just after the poll times out). The test is no longer flaky, so no `docs/testing/flaky-register.md` row is needed.
- **`epub.test.ts`'s two "no temp dir created" assertions now spy on `mkdtemp` instead of scanning the filesystem afterward** (#2100). The original before/after `readdirSync(tmpdir())` count (and a later per-test-directory variant) could only ever detect a *leaked* temp dir — `parseEpub`'s own `finally` removes any directory it creates before returning, so by the time either version inspected the filesystem the evidence was already gone; injecting exactly the named defect (a temp dir created even when `sourcePath` is provided, cleanup untouched) passed 27/27 either way. A `vi.mock('node:fs/promises', …)` spy wrapping the real `mkdtemp` (passthrough for every other call) observes the call directly, so it now catches creation, not just leakage — mutation-verified against that same one-part defect. This needed no production change: `server/src/parsers/epub.ts` stays unmodified. (An earlier version of this fix threaded an optional `tempDirBase` through `parseEpub` on the theory that the filesystem-scan approach was unavoidably vacuous without it; a second, more careful mutation showed threading it made no difference to that specific defect, so the parameter was dropped along with the assertion style that seemed to need it.)
