## 🧱 Internals

- **A finished render no longer leaves several GB of GPU memory stranded, blocking the next operation** (#1976). PyTorch's caching allocator kept a reserved-but-unallocated pool on the render card after a chapter finished and the engine reported unloaded — measured at **3968 MB** on an 8 GB card, with `/capacity` correctly reporting only 3230 MB free because the driver counts reserved cache as used. Nothing could reclaim it: every existing `empty_cache()` is a side effect of unloading a *resident* model, so with nothing resident the idle-eviction ladder had nothing to evict and fell straight through, and the watchdog's 90%-of-card recycle threshold is nowhere near tripping at ~48%. Only a sidecar restart cleared it. The memory was always **fully reclaimable** — a load/unload cycle on the same stranded state recovered it to 389 MB — it simply never got reclaimed, so later work was refused on a figure several GB pessimistic. Observed refusing an ASR `/transcribe` (`503 noCapacity`, three times, *with the model already resident*) and a voice design (`503 Not enough GPU memory for qwen (6144MB)`) while the box's second card sat with 15 GB free. Admission now performs one bare `gc.collect()` + `empty_cache()` and **one** re-probe as a final phase — only on the failure path, after the residency ladder has already failed, never in a loop — so a stranded pool can no longer by itself cause a refusal. It runs on a worker thread for the same reason every eviction step does (plan 273): `empty_cache()` can block on the allocator lock and must not stall `/health`. **Also:** `/health` gains `vram_reserved_mb_by_device`, a per-card breakdown — the existing `vram_reserved_mb` reads the *current* device only, and was measured reporting `50` while `nvidia-smi` showed 3587 MiB on `cuda:0`, which is actively misleading when diagnosing exactly this class of problem.
- **`_cuda_vram_mb()` — the reading that feeds the VRAM recycle watchdog — no longer mixes two different cards' figures on a multi-GPU box** (#1997). `allocated`/`reserved` read torch's *current* device (no-arg calls), but `total` was hardcoded to `get_device_properties(0)` — device 0, regardless of which card was actually current. Invisible on a single-GPU box; on a multi-GPU one it could compare one card's usage against a different card's capacity, feeding the recycle watchdog a ratio that describes neither card correctly. `total` now reads the current device too. **Also fixed in passing** (found by review, same defect shape): `/debug/memory`'s inline `cuda` block had the identical device-0-hardcoded `total_mb`, which would otherwise have disagreed with `/health`'s now-fixed `vram_total_mb` on the same box.

- **The `/api/setup/*` surface is now in the API contract** (fe-57, #1883). `openapi.yaml` described 91 `/api/` paths and **none** of the setup surface, so the frontend types for all 8 setup endpoints were hand-written with no mechanical guard — and had already drifted (`info.vramTotalMb` is sent by `setup-readiness.ts:99` and was absent from the frontend type). Describes all 8 endpoints + 14 schemas, regenerates `src/lib/api-types.ts`, and deletes **both** hand-mirrored blocks in `src/lib/api.ts` — the `SetupReadiness` family and the `ModelsStatus` family — replacing them with generated aliases under identical names, so no consumer import changed. **This does not make server↔frontend drift a compile error**: the server does not consume `src/lib/api-types.ts` (`workspace/voice-library.ts:9-10`), so describing the contract alone would have *relocated* the duplicate rather than removed it. The guarantee is `server/src/routes/openapi-setup-parity.test.ts`, which asserts the contract's enums equal the server's TypeScript unions — via `satisfies Record<Union, 1>` over type-only imports, so a member added to a server union fails `npm run typecheck` inside the test file. Copy count goes three → two. **Fixed a live bug found on the way:** `venv-bootstrap.tsx` declared `status: 'installing'`, a value the venv endpoint never emits, so its progress card never rendered during a real multi-minute bootstrap — and its own tests mocked the fictional status, keeping the suite green. Plan: [`docs/features/270-openapi-setup-surface.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/270-openapi-setup-surface.md).
- **The sidecar's `/health` check — and every other in-flight request — no longer stalls while it frees GPU memory for a new voice** (#1919, plan 273). Freeing an idle model, including the multi-second host/VRAM reclaim that follows, used to run synchronously on the sidecar's single event loop, so a contended model unload could make the whole sidecar look unresponsive for as long as a Qwen forward pass or a large `gc.collect()`. Every eviction step (and its reclaim) now runs on a worker thread instead, and the admission-decision phase is serialised so two concurrent requests can't interleave their eviction logic. This also pins an XTTS race where a second Stop press during a retried cold load could itself hang — already fixed incidentally by the fs-38 Wave 3c merge (#1925, closed as superseded; this PR adds the regression test that guards it going forward). **One accepted trade-off, narrower than the plan first framed it**: on the Qwen single-utterance path (`synthesize` — the title beat, an audition, a clone-voice preview) and on the ASR content-QA pass, a Stop press (or an automatic engine swap) landing in the narrow gap between a call confirming its model is loaded and the call actually starting now fails that one call with a clear error, instead of silently reloading and continuing as it did before. Only an explicit Stop or an automatic swap can land in that gap — ordinary VRAM pressure alone cannot reach it — and it is the same trade the XTTS engine already shipped. **It does NOT cover Qwen's batched per-sentence chapter render** (`synthesize_batch`, the actual render path a book uses) or the voice-design audition forward — those three sites still silently reload in the same gap, unchanged by this PR; tracked as a follow-up in [#1975](https://github.com/dudarenok-maker/Castwright/issues/1975). Even on the paths this PR does cover, the failure is rarely visible in practice: Node's own retry wrapper (`server/src/tts/synthesise-chapter.ts`) retries a transient sidecar error up to three times at 500ms/2s, and the retry's re-ensure succeeds. Plan: [`docs/features/archive/273-sidecar-lock-event-loop.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/archive/273-sidecar-lock-event-loop.md).
- **Closes the #1919 follow-up: `synthesize_batch` (the actual chapter-render path) and `design_voice`'s audition forward no longer silently absorb an `/unload` that lands mid-load** (#1975, plan 273 T7/T8 shape). The same re-ensure-under-`_synth_lock` defect #1919 fixed for the single-utterance `synthesize` path was still present at three more call sites: `synthesize_batch`'s 1.7B branch (`:6383`), its 0.6B branch (`:6459` — the path a book's Qwen sentences actually batch through, up to `QWEN_BATCH_SIZE` at a time), and `design_voice`'s audition-preview forward (`:5674`). Each re-ensured its Base model INSIDE `with self._synth_lock:` — normally a warm no-op, but an `/unload` (or `unload_base17()`) that won the narrow gap between the pre-ensure and the lock acquire turned it into a full cold weights pull that held the Stop button off for the pull's whole duration. All three now ensure BEFORE the lock and raise a loud `RuntimeError` naming the engine if a concurrent unload wins that gap, instead of silently reloading. **Widens the accepted trade-off from #1919**: on the batch path, a raise now fails the WHOLE batch, not one sentence — but `synthesise-chapter.ts`'s `withTtsRetry` wrapper (1 primary + 2 retries, 500ms/2s backoff) already retries a transient batch failure automatically, and the sidecar's generic exception handler classifies this `RuntimeError` as a plain, non-poisoned 500 (`transient: true` on the Node side), so the retry silently absorbs it almost every time; only an explicit Stop press or an automatic engine swap can land in the gap at all — ordinary VRAM pressure cannot. Paired event-gated regression tests for all three sites, each independently mutation-verified against the producer. Plan: [`docs/features/archive/273-sidecar-lock-event-loop.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/archive/273-sidecar-lock-event-loop.md).
- **`ASR_MODEL` is now a registry knob, and it reaches every reader — not just the sidecar** (#1988). The WhisperEngine content-QA gate had two registered siblings — `ASR_DEVICE` and `ASR_IDLE_TTL` (both `server/src/config/registry.ts`) — but `ASR_MODEL` was read straight from the environment in `server/tts-sidecar/main.py`, invisible to the Advanced Configuration UI and to `.env.example` sync. Registered as `qa.asr.model` (string, default `"base"` — matching the sidecar's own fallback, `restart-sidecar`, same risk tier as `ASR_DEVICE`); no sidecar code change was needed since `main.py` already read it via the identical `os.environ.get(...).strip() or default` shape its siblings use, and the existing `spawn-sidecar.ts` restart-sidecar knob loop now forwards it automatically. **The server's own Node-side Whisper-model readers now resolve the same knob**, closing a divergence this PR would otherwise have introduced: `whisperRepoDir()` / `whisperModelPresent()` / `detectWhisperInstallStateOnDisk()` (`model-paths.ts`, `whisper-install-detect.ts`) previously cached `process.env.ASR_MODEL` in a module-load-time constant, so a UI-set override reached the sidecar but not Model Manager — sizing, install-state, and **Remove** all still targeted `base` regardless of the model actually configured and loaded, so Remove could delete the wrong model's directory and leave the one in use untouched. All three now resolve `qa.asr.model` per call, and the in-app Whisper installer is spawned with an explicit `--model` flag carrying the live value. Documented the "Content-QA (Whisper) model" row in `docs/wiki/Advanced-Settings.md`, alongside `ASR_DEVICE`'s and `ASR_IDLE_TTL`'s pre-existing rows (#1989).
- **A Russian (also French/Spanish) dialogue line that opens with a dash now gets a real pause on the Coqui engine, and Coqui gains its own output-degeneracy guard** (#2026, found during fs-38 Wave 3 on-box acceptance, run sheet §5 Section E, E-04). On-box measurement found a leading em-dash — the standard dialogue-opener convention in these languages (`— Кто бы это ни был...`) — produced no audible pause (+0.14s vs no dash at all), while the SAME line's mid-sentence dash was honoured normally (+1.53s). The existing wire-text `softenDashes` (`server/src/tts/text-normalize.ts`) converted every dash, leading or interior, to a comma — but a comma at the very start of an utterance has no preceding word for the pause to land after, which is exactly what makes an interior comma work. A leading dash now becomes `... ` instead, mirroring how leading-ellipsis is already the ordinary way written prose marks a beat before speech resumes. Language-agnostic by construction (the transform has no language branch), so this is not a Russian-only fix. Pinned on the wire TEXT (`text-normalize.test.ts`), not audio — the audible effect is recorded as owed on-box acceptance (`docs/testing/fs38-wave3-onbox-acceptance.md`'s new `#2026` item). **Separately**, `tts.qwen.degenGuard`'s "duration implausible for the given speakable text" idea is now mirrored on the Coqui path as `tts.coqui.degenGuard` (`server/tts-sidecar/main.py`'s `_coqui_synth_is_degenerate`, reusing the Qwen guard's own conservative 20ms/speakable-char floor and minimum-length gate) — a Coqui render that comes back implausibly short for a substantial line now retries once with a fresh stochastic sample (XTTS has no fixed seed, so this is a per-call sampling fluke, never a corrupted resident model — no reload/recycle, unlike the Qwen guard's escalation). If the retry is still degenerate, the sidecar now `raise`s (`main.py:2192`) instead of shipping the short audio, which the pre-guard code had no way to catch at all; `synthesise-chapter.ts`'s `withTtsRetry` wrapper absorbs the resulting transient failure the great majority of the time, so only a genuinely stuck line now surfaces as a failed render (documented in `docs/wiki/Troubleshooting.md`'s "A Coqui line came out silent or nearly empty" section). Known, deliberate gap: this only catches an implausibly SHORT render, not the rarer full language-collapse (fluent audio in the wrong language, at a plausible duration) the same on-box run also found — catching that would need content verification (e.g. ASR), out of scope here. A third defect the same run found — a neuter Russian adjective ending (`-ее`) consistently mispronounced as `-ая`/`-ие` — was investigated and found to be **not locally fixable**: Russian has no dedicated phonemizer/G2P step in the vendored `coqui-tts` package at all (it goes straight through the generic BPE tokenizer), so the mispronunciation is baked into the trained XTTS v2 checkpoint's learned acoustic behaviour, not a text-preprocessing bug; written up on the issue with the supporting evidence rather than forced into a workaround. Golden-tier Russian coverage added (`test_cross_engine_sanity.py`'s `test_coqui_sanity_ru`) — the existing Coqui/XTTS golden checks were English-only, which is exactly why none of this was reachable by CI.
- **A cloned Coqui/XTTS voice no longer 500s on a long line** (#2017). `CoquiEngine._infer_from_latents` passes `enable_text_splitting=True` (config-faithful, mirrors `Xtts.synthesize`'s own build) so a cloned-voice render at or above `tokenizer.char_limits[lang]` doesn't hard-crash the bare low-level `Xtts.inference()` assert instead — but that path reaches upstream's `get_spacy_lang`, which raises `ImportError` when spacy isn't installed, and spacy was never declared as a sidecar dependency. Reproduced with a 245-char Russian string against `char_limits['ru']` (182): every render past the limit 500'd (`{"detail":"Internal error."}"`) instead of returning audio. Fixed two ways: **belt-and-braces**, `_infer_from_latents` catches an `ImportError` from the inference call, logs it loudly, and retries with `enable_text_splitting=False` rather than 500ing outright; and plain `spacy` (not `spacy[ja]` — measured 22.3 MB/16 packages vs. 92.5 MB/18, of which 68.9 MB is `sudachidict-core` alone, needed only for Japanese) is now installed. Japanese cloned-voice text-splitting stays broken on purpose — tracked separately (#2038) since fixing it means pulling in the 70 MB Sudachi dictionary, a call for the `fs-59` CJK workstream, not this fix. Plain spacy was verified to cover ar/en/es/hi/zh (zh confirmed working, despite the upstream error message naming `spacy[ja]` generically) — only `ja` needs SudachiPy. **Where spacy installs from, and the operator action that follows:** it does NOT live in `requirements/base.txt` — spacy is reached only via the opt-in Coqui/XTTS path, so a CPU-only or Kokoro-only install would otherwise pay 22.3 MB / 16 packages for a library it never imports. It installs from `server/tts-sidecar/scripts/install-coqui.mjs`'s third pip step instead, alongside the existing CJK phonemizers (`pypinyin`/`cutlet`/`unidic-lite`), guarded by `test_spacy_is_explicit_and_not_the_ja_extra` (`server/tts-sidecar/tests/test_requirements.py`, now re-pointed at the new invariant: absent from every manifest/overlay, present in the installer, never `[ja]`). **This means the fix does NOT reach an existing Coqui install automatically on upgrade** — unlike a `base.txt` dependency (covered by `reqHash`, which re-pips on every version bump), `install-coqui.mjs` runs only when a user explicitly (re-)installs or Repairs Coqui from Model Manager. Anyone who installed Coqui before this ships still hits the #2017 500 until they press **Repair Coqui XTTS v2** (or reinstall) from Account → Models.

## 🔧 Setup & prerequisites

- **Castwright now declares a minimum ffmpeg version — 6.0 — and checks it** (ops-35, #1877). The audio pipeline doesn't merely invoke ffmpeg; `server/src/tts/loudnorm.ts` **parses** ffmpeg's two-pass loudnorm JSON summary, which makes the version a contract we were relying on without ever stating. `castwright.ffmpeg.minimum` in root `package.json` is the single source of truth, read by `scripts/preflight-ffmpeg.cjs` (which previously spawned `ffmpeg -version` and discarded the output), by `server/src/diagnostics/ffmpeg.ts`, and by `pinokio-scripts/lib/ffmpeg-pin.test.js` — never restated anywhere. This is a **support** floor, not a capability floor: loudnorm's JSON shape has been stable since ffmpeg 3.1, so an evidence-derived floor would sit near 4.x and never fire. 6.0 is anchored to Ubuntu 24.04 LTS (6.1.1). **This retires the previously-claimed Ubuntu 22.04**, whose archive ffmpeg is 4.4 — a deliberate, user-visible support reduction; snap or a PPA satisfies the floor on 22.04. Only the preflight hard-fails (it is `server/package.json`'s `pretest`, so it gates pre-commit, pre-push and all three `release.yml` legs — every gate channel was measured at ≥ 6.1.1 first). Every user-facing surface **warns without blocking**: a new `ffmpeg-too-old` `BlockerCause` at `status: 'warn'`, which `setup-readiness.ts:96` already counted toward `ready`. The Setup Wizard gains a third card — before this, a below-floor ffmpeg rendered "ffmpeg isn't installed yet" to a user who has it installed. Pinokio's conda env moves from bare `ffmpeg` to `"ffmpeg>=6"` on **both** `install.js` and `update.js`, unblocking #1876. Rollback without reverting: set the floor to `null`. Plan: [`docs/features/269-ffmpeg-version-floor.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/269-ffmpeg-version-floor.md).

- **Cloned voices now render in the book's language, not English** (refs #1951). `QwenEngine.synthesize` accepted a `language` argument and never read it, so a voice's language came solely from its sidecar manifest. A cloned voice's manifest always reads “English” — `deriveEngineArtifact` never sent `X-Language`, so `clone_voice` computed `lang = DEFAULT_LANGUAGE` — and cloned voices are deliberately exempt from `clearMismatchedDesignedVoices` (`verify-designed-voice-language.ts:55`) so they can be reused across books, so nothing else supplied one. Measured on the box: a German sentence through the production `/synthesize` → `/transcribe` path detected `en` at `avg_logprob` **−1.303** (unintelligible); with the language corrected, `de` at **−0.366**. The failure was total, not gradual. **The primary surface is `/synthesize-batch`, not `/synthesize`**: chapter sentences batch (`QWEN_BATCH_SIZE` defaults to 32) and only the title beat is a single synth, so a fix confined to `synthesize` would have shipped a translated title over an entirely English book while passing every mechanism-level test. Node decides clone-ness (`hasClonedProvenance`) and signals it purely by whether it puts a `language` on the request — per **item**, since a batch may mix a cloned character's line with a designed narrator's. The sidecar never learns what a clone is; an omitted field falls through to the manifest language, so designed-voice behaviour is byte-identical and Coqui is untouched. An unmappable language degrades to that same fallback rather than throwing or defaulting to English. Also fixes a cache/disk divergence in the designed self-heal, where the restored manifest said one language while the sidecar's warm `_prompt_cache` said another — so a **sidecar restart silently changed the audio** — by evicting the prompt cache after the restore. The clone derive now sends `X-Language` from the reference clip's Whisper-detected language, so a clone's manifest and Voice Library label stop claiming English. Existing clone manifests keep reading “English” until re-cloned or re-derived (not migrated: recovering a distilled `.pt`'s language would mean re-transcribing the master). Two further seams carry the same pair rather than being left behind the render path: the **speaker-drift reference** (`auditionCentroid`) now renders under the book's language — it is the centroid every chapter segment is compared against, so an English reference against a German chapter would have become a fresh source of false `voice-mismatch` flags on exactly the cloned voices this change fixes — reading the language from the book's `state.json` and the provenance from `cast.json`, and passing neither when the book's language genuinely can't be read (never an English guess); and `POST /api/voices/:voiceId/sample` now marks a cloned voice as such, so a supplied `language` reaches the mapping instead of the clone's English manifest. That route forwards a client-supplied, unvalidated language, so it is protected only by `resolveWireLanguage`'s try/catch now that the mapping is reachable — pinned end-to-end (route → real provider) by `routes/voice-sample-cloned-language.test.ts`, since a 5xx there would break a Play-sample click that works today. Plan: [`docs/features/275-clone-voice-language.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/275-clone-voice-language.md).
- **fs-38 Wave 3b1 — the first voice clone, on the Qwen engine** (refs #624). - **fs-38 Wave 3c — cloned + designed voices on Coqui XTTS v2** (refs #624). Extends 268's never-substitute/total-erasure machinery to a second engine.
  - **Sidecar.** `CoquiEngine.clone_voice` (`server/tts-sidecar/main.py`) derives XTTS conditioning latents (`get_conditioning_latents`, hand-rolled rather than the built-in `CloningMixin` — the built-in's non-atomic `torch.save` to a path we don't control would defeat reliable purge), persisted via the pre-existing `_atomic_torch_save` under a `_synth_lock` shared with `/synthesize` (clone and synthesise are two serialized concurrent entry points into the model, matching Qwen's pattern — not a throughput regression). Crash-orphaned temp artifacts (a staging file the sidecar's atomic save leaves behind when the process is hard-killed mid-write) are swept on clone purge, closing a gap where revoke reported clean erasure while conditioning latents or the person's raw reference clip survived on disk. Reuse hydration no longer overrides a character's own designed Coqui slot with a source book's Qwen voice when the character carries no `qwen` override at all.

- **A failed VRAM evict no longer kills a mixed Qwen+Coqui chapter** (#1893). fs-60 partitions a chapter that mixes Qwen and Coqui into two serial phases with a sidecar `/unload` between them, so the two never co-reside on an 8 GB card. That evict call had no failure isolation: it throws on a non-ok `/unload`, `fetch` rejects on a dead socket, and no `try`/`catch` sat between it and `synthesiseChapter`'s head — so a transient sidecar hiccup aborted a chapter that would otherwise have rendered, at up to three call sites per chapter (initial body dispatch plus the segment-QA and ASR re-record rounds, which share the same wrapper). The evict is now best-effort: a failure logs a named warning and the Coqui phase proceeds, mirroring `clone-voice-resolver.ts`'s self-heal policy — an abort still propagates, so a paused or cancelled run stops here as before. The call is also bounded by the chapter's existing `callTimeoutMs` and forwards the abort signal; previously it could queue behind another book's in-flight synth on the sidecar's `_synth_lock` and stall forever, uncancellable. An abort is rethrown *as* an `AbortError` rather than verbatim, so a pause that raced a socket-death rejection can't read as a chapter failure at `routes/generation.ts`'s pause detector. Failing soft is usually cheap — `/unload` is idempotent and returns 200 even when nothing was resident, so a failure normally means an unhealthy sidecar, which the Coqui phase then surfaces itself — but not always: a wrong/proxied `SIDECAR_URL` can 5xx `/unload` while the synth path is healthy, and then Coqui really does load onto a resident Qwen. That residue is deliberately accepted, recorded as plan 249's accepted limitation #4, and owed on-box as register row A19.
- **Idle Coqui XTTS is now reclaimed under VRAM pressure** (#1894, PR #1924) — the sidecar's admission path frees a resident-but-idle XTTS before reporting `noCapacity`, instead of failing the starved operation. Admission-time and demand-driven: it frees an idle XTTS the moment *any* starved GPU operation needs the room. Engine-aware (a Coqui op never evicts itself) and device-targeted. Tunable via `COQUI_IDLE_TTL` / `sidecar.coquiIdleTtl` (default 30 s). One accepted user-visible trade: a starved op's `NoCapacityError` no longer carries the "Coqui XTTS is loaded — Use its Stop button" line, since admission now presses that button itself. Also fixes an unguarded `CoquiEngine.unload()` that could crash an in-flight synth when the Stop button fired mid-render, and the same unguarded-unload race in the Whisper (ASR) and ECAPA speaker engines — which, unlike Coqui, were already being auto-evicted, so that one was reachable in production.
- **The five engine in-flight counters are now lock-guarded** (#1917, PR #1930). `x += 1` on a plain attribute is not atomic — CPython can switch threads at any bytecode boundary — so a concurrent forward could lose a decrement and leave that engine's counter stuck above zero, silently disabling its idle eviction for the rest of the process's lifetime, with no error and no log line. All five counters (Coqui, Whisper/ASR, ECAPA/speaker, and both Qwen VoiceDesign and Base) now share one lock-guarded `InFlightCounter`; the lock is held only for the mutation itself, never across a forward, so eviction's fast-out stays non-blocking. **Also fixes a related pre-existing bug found in passing:** `CoquiEngine.synthesize`, `WhisperEngine.transcribe` and `SpeakerEngine.embed` all decremented their in-flight count *before* re-stamping `_last_used` on the way out, leaving a window where the admission path could see an idle-looking engine mid-forward and evict it.
- **A Stop pressed mid-load no longer leaves Coqui XTTS pinned to a stale GPU** (#1918, PR #1930). Loading a fresh model used to publish seven fields with no lock while `unload()` took the lock and reset those same fields, so a Stop during the ~90 s cold load could have the still-running loader overwrite the unload's resets — leaving a live model whose `_device` never got restored to `_requested_device`, bypassing GPU placement on the next load. The publish is now atomic and load-epoch-guarded: `unload()` unconditionally bumps a load epoch, and a load that finishes after losing the race discards its result instead of publishing on top of a teardown.
- **VRAM eviction now stops as soon as a request fits, and never throws away a reserved model** (#1920, PR #1930). Previously a small request (e.g. a 400 MB ASR call) ran every eviction branch unconditionally, so it could free several GB from Qwen and still unload a resident Coqui XTTS — a ~90 s reload — for no reason. Eviction is now an ordered, cheapest-reload-first step list that re-probes real capacity after each step and stops the moment the request fits. It also consults the reservation ledger and skips any engine whose operation has already been admitted, closing a window where an in-flight, already-reserved model could be evicted out from under it.
- **Pressing Stop no longer reports a timeout while the model unloads anyway** (#1921, PR #1930). `POST /api/sidecar/unload` previously ran under the same 2 s budget as the sidecar health probe, so stopping a model mid-render reported an error a couple of seconds in and then unloaded for real up to a minute later. The unload route now gets its own 90 s budget (mirroring the existing `/load` route), and the UI shows a disabled "Stopping…" state for the whole wait instead of a misleading failure.
- **Assigning a designed voice now warns — never blocks — when its baked language doesn't match the book's** (fs-38, #1953). `clearMismatchedDesignedVoices` already caught a designed voice's language mismatch, but only at render time and only for non-English books (its callers gate it behind `isNonEnglish`), so a designed Russian voice assigned to an English book sailed through assign-time with no signal at all, right up until a full chapter rendered wrong-language audio. Measured on the dev box via the production `/synthesize` + `/transcribe` path: a mismatched-language render transcribed at `avg_logprob` **-1.303** (unintelligible) vs. **-0.201** for the same text correctly languaged — a mismatch destroys the audio, it doesn't merely degrade it. `POST /:voiceUuid/assign` now returns **200 with a non-fatal `warning`** naming both languages and the character (e.g. *"Ada's voice was designed in Russian but this book is English — the audio will be unintelligible. Re-design the voice in English to fix it."*) whenever a **designed** voice's manifest language disagrees with the book's, on an English book as well as a non-English one; a cloned voice (no baked design language) is unaffected, and the existing cloned-voice wrong-engine 409 at the same route is unchanged — a 409 for designed voices was deliberately rejected as a regression (spec §2.3: a designed voice has always been free to route anywhere). The profile drawer and the cast-view voice-library panel both surface the warning inline, in the same slot that already carries the partial-success "assigned on Qwen only" notice. The render-time gate (`clearMismatchedDesignedVoices`) is unchanged — this is an earlier, softer signal on top of it, not a replacement.
- **Emotion variants are now refused for a cloned voice instead of being minted against the wrong identity** (#1954). The variant path computed its sidecar anchor as `qwenStorageKey(character, characterId)` (`server/src/routes/qwen-voice.ts`), which only ever produces a DESIGNED-voice key (`qwen-<voiceUuid|voiceId>`); a cloned voice's artifact lives at `qwen-<libraryUuid>`, which that helper cannot produce. So a mint anchored to a different voice's `.pt` (or to none) and wrote the variant under a key the render path never looks up — `pickVoiceForEngine` resolves a cloned qwen slot to `qwen-<libraryUuid>`, so `pickEmotionVariantVoice` asks for `qwen-<libraryUuid>__<emotion>`. Reachable because the clone gate existed on the BASE-design branch (`cast-design.ts`, GATE 2 fix-lane-1b) and not the variant branch, whose only check was `overrideTtsVoices?.qwen?.name` — which a cloned slot carries. Same `qwenStorageKey`-vs-`libraryUuid` confusion recorded at `tts/verify-designed-voice-language.ts:45-47`. **Resolved by refusing, not by re-anchoring**: the sidecar's `mint_variant` would accept a cloned `.pt`, but the resulting variant is a *re-performance* of a real person that (a) no consent record has a dimension for, (b) `purgeCloneArtifacts` cannot erase — its sweep anchors on `key` / `key + '.'`, and `qwen-<uuid>__angry.pt` matches neither — and (c) loses its clone provenance at the sidecar, since `mint_variant` never writes `"clone": true`. Three gates land: a 409 `clone_protected` at the design route (mirroring `single-design.ts`), a throw at the shared `designQwenVoiceForCharacter` choke point where the bad anchor was computed, and a skip-and-report in `cast-design.ts`'s variant branch through the existing `clonedSkips` channel. The frontend derives the gate from `character` rather than a prop, so no render site can omit it. Tests: `server/src/routes/qwen-voice.test.ts`, `server/src/routes/cast-design.test.ts`, `src/components/emotion-variant-designer.test.tsx`.
- **A cloned voice's consent record can now name the real attester, not just the person being cloned** (#1943). `POST /api/voice-library/clone` hardcoded `attestedBy` to `consent.personName`, so a `guardian-of-minor` record asserted that the **child attested to their own voice being cloned** — inverting the relationship's whole meaning; a `family-with-permission` record had the same defect. `validateConsentDraft` now accepts a trimmed `consent.attestedBy`, persisted verbatim, and `POST /api/voice-library/clone` **rejects a non-`self` clone with 400** when it is absent or blank/whitespace (#1959) — the fallback to `personName` survives only for `relationship: 'self'`, where the person being cloned *is* the attester and the wizard deliberately omits the field. So no stored record can assert that a minor attested for themselves via any code path: the gate sits ahead of any candidate or GPU work, `/clone` is the only server-side write into `attestedBy` (`PATCH /:voiceUuid` never touches consent, `revoke` only stamps `revokedAt`), and the mock API layer carries the identical gate, having otherwise kept the pre-fix fallback and gone on reproducing the defect in mock mode. `openapi.yaml`'s `CloneVoiceRequest.consent` gains the field; the conditional requirement lives in its description, since `required` cannot express it. The clone wizard (`CloneCapturePanel`) gains an attester-name input, shown and required only for the two non-self relationships (asking someone to name themselves twice for `self` is noise), folded into the existing Continue gate; the fixed attestation sentence is now relationship-aware, since a guardian is consenting on a child's behalf rather than relaying the child's own permission. No migration for already-stored entries — they keep `attestedBy === personName`, which is exactly what they attested to at the time. Found during the fs-38 Wave 3 on-box acceptance run (register row A1).
- **Coqui/XTTS no longer 500s in a sidecar that has already run an ECAPA speaker-embed** (#1944, PR #1962). Cloning always calls `/embed` (the advisory fidelity check), so clone-then-render-on-Coqui was the natural sequence that broke: speechbrain 1.1.0 leaves several lazy-proxy modules in `sys.modules` after ECAPA loads, and CPython's `inspect.getmodule()`, reached from deep inside `TTS.api`'s own import chain, chokes on one of them with an `ImportError` in a way `hasattr` can't swallow. Fixed two ways: `SpeakerEngine._load_on` now unconditionally evicts those proxies from `sys.modules` right after the ECAPA import plants them (the actual fix, deliberately unconditional and never probing a proxy, since probing one half-imports `transformers` and breaks the following `TTS.api` import a second way); and, belt-and-braces, the sidecar can eagerly import `TTS.api` at startup, before ECAPA gets a chance to run first (new "Pin Coqui import order at startup" Advanced Settings knob, default on, but only for installs that actually have the XTTS weights on disk -- it costs about 12 seconds of startup, so Qwen-only and Kokoro-only setups skip it). Two secondary defects in the same area: `/health` used to advertise Coqui as available off a find_spec-only probe that never actually imports, so it could claim an engine was ready when a real load would fail -- a new sticky `coqui_import_ok` wire field now reflects a genuine import attempt, and the Node side reads it everywhere that matters rather than on one route only (#1963) — `voice-engine-registry`'s `livePackageImportable`, and through it `models-status`'s client-facing `importable` and `models-inventory`'s `packageInstalled`, all prefer it whenever a real import has been attempted, falling back to the find_spec value only while it is still `null` (no attempt yet, or a pre-#1962 sidecar that omits the field), so that path is byte-for-byte unchanged. And the failure message used to blame a missing PyTorch for every `TTS.api` import failure, including this one, even though torch was installed and working (Qwen was rendering on GPU in the same process) -- the diagnostic now checks torch first and stops misdirecting.
- **Cloned-voice derive on Coqui/XTTS no longer routes through torchcodec, so it works on a static-FFmpeg install** (refs #1967, found by the fs-38 Wave 3 on-box acceptance run 2026-07-31, blocking all nine items of Section E). `CoquiEngine.clone_voice`'s `get_conditioning_latents` call reached XTTS's own reference-audio loader (`TTS.tts.models.xtts.load_audio`), which routes through torchaudio's loader — and torchaudio >=2.9 dispatches `.load` unconditionally to `torchcodec`, which needs FFmpeg's **shared** libraries. `winget install Gyan.FFmpeg` — the normal Windows install, and the one this repo's own docs steer deployers to — is a static build with no `avcodec-*.dll` at all, so every cloned-voice derive on Coqui failed there, surfaced as `derive-failed` wrapped in copy that told the user to "Re-enable **Qwen**" after a **Coqui** failure. New `server/tts-sidecar/xtts_audio_io.py` decodes the reference WAV itself with the stdlib `wave` module + NumPy (the same pair `main.py` already uses everywhere else) and swaps the replacement in for `TTS.tts.models.xtts.load_audio` via a scoped `contextlib.contextmanager`, `patched_xtts_load_audio()`, for the duration of the derive only — inside the existing `_synth_lock`, so the process-global mutation can't race a concurrent synth. The context manager raises rather than silently falling through if `load_audio` is missing or its signature drifts, naming the installed `coqui-tts` version. `install-coqui.mjs` gains a post-install verification step — round-trips a generated WAV through the same patched loader — that fails the Coqui install outright (before the ~1.8 GB weights prefetch) if a future `coqui-tts` release moves or reshapes the loader this patches, closing the gap left by having no version pin on `coqui-tts`/`torchcodec` (neither is pinned anywhere in the manifest). Separately, `UnresolvableClonedVoiceError.fromList`'s `derive-failed` remedy copy stopped inventing "Re-enable Qwen" on a Coqui failure: it only names an engine to re-enable when one was actually reported `engine-unavailable`, `derive-failed` gets its own "re-run the clone for {engine} and check the sidecar log" clause, and all four `derive-failed` producers (three catch-path `broken.push` sites plus the classifier path that fires on every run after the first, once a derive failure has persisted `status: 'failed'`) now tag the entry with its engine. Design: [`docs/superpowers/specs/2026-07-31-xtts-clone-torchcodec-ffmpeg-design.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/superpowers/specs/2026-07-31-xtts-clone-torchcodec-ffmpeg-design.md). Plan: [`docs/superpowers/plans/2026-07-31-xtts-clone-torchcodec-ffmpeg.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/superpowers/plans/2026-07-31-xtts-clone-torchcodec-ffmpeg.md).
- **Kokoro, Qwen and Whisper now report a real import result too, and Model Manager offers Repair on the strength of it** (#1965, [#1986](https://github.com/dudarenok-maker/Castwright/pull/1986)). `coqui_import_ok` (#1963) gave exactly one engine a signal grounded in an import that actually ran; the other three were still described entirely by `find_spec`, which never executes the module and so reports "installed" for a package that is present on disk and genuinely cannot import — the #1944 shape. `/health` now carries `kokoro_import_ok`, `qwen_import_ok` and `whisper_import_ok` beside it, each recorded opportunistically at the single import chokepoint that engine already runs on its own cold-load path, catching `BaseException` rather than `ImportError` (the second documented shape of the #1944 collision is a duplicate-kernel-registration `RuntimeError`) and re-raising unchanged. **No eager probe is added** — Coqui's startup pin costs a measured +11.7 s of unreachable boot and paying that per engine is not worth it, so `null` (nothing has tried to load that engine yet in this sidecar process) is the *common* value and the `find_spec` probe still governs there. This narrows the window; it does not close it. On the Node side `importable` — an internal server field that never crossed the wire — splits into `importOk` (a real attempt) and `specPresent` (the probe), with the "prefer the real result, fall back to the probe" rule no longer pre-collapsed in the registry accessor every caller shared, but stated where it is actually decided: `models-status`'s `packageBroken` predicate. The split is exactly equivalent to the single collapsed field it replaces, which is what let it land as a pure refactor under the pre-existing tests. `models-inventory` keeps a composition of its own — deliberately, since it has a third fallback the other callers do not, the Node-side disk probe — but now runs all six engine rows through that single helper instead of five bare `find_spec` reads plus one corrected Coqui read. And `/api/diagnostics`' Voice-engine row — which read the raw `find_spec` booleans directly and so was the one surface no registry-level fix could reach — now goes through the same accessors, and stops describing a **missing** package as "not importable": the two faults have different remedies and are now named separately. Coqui stays deliberately out of that row, since it is opt-in and an absent Coqui is not a fault.
- **The assign-readiness gate now checks the engine a cloned voice will actually render on, not always Qwen's** (#1933). `POST /:voiceUuid/assign` used to 409 any cloned voice whose Qwen slot wasn't `ready`, even when the character was routed to Coqui and would never touch that slot — and, in the other direction, let a cloned voice through whenever Qwen happened to be ready even if the character's own (Coqui) slot was terminally broken. The new rule is symmetric on the artifact axis (either engine's slot can be `ready`, or repairable from a retained reference clip on disk) and asymmetric on the transcript axis (a Qwen derive needs a transcript; Coqui's is purely acoustic and needs none) — so a Qwen-only requirement no longer over-blocks a Coqui-routed assign, nor under-blocks a Qwen-routed one riding a broken Coqui slot. Both clone-capable slots are still written unconditionally for a cloned entry regardless of which one the assign routed to (unchanged from Wave 3c); the response's existing `warning` field now also carries a non-fatal advisory naming the OTHER engine and the reason when that other slot is left unusable, so the user learns about it at assign time rather than only when the character is later switched onto it. `openapi.yaml`'s 409/`warning` prose is updated to match; no schema shape changed. The mock API mirrors the identical rule, so `npm run dev` and every e2e/Playwright run see the same behaviour as the real server.
- **The Setup checker now tells a missing voice engine package apart from a broken one too, and points at the right fix — and Model Manager's own Install/Repair buttons can no longer contradict that copy** (#1999, follow-up to #1965/#1986). #1986 fixed this conflation on the Admin console's diagnostics row only — `server/src/routes/setup-diagnosis.ts`, the first-run Setup Wizard's own blocker copy, was left reading the already-collapsed `packageBroken` boolean and still rendered every fault as *"A voice engine package is not importable"* with a *"Repair in Model Manager"* instruction, the wrong verb for a package that was never installed. The missing-vs-broken precedence (a real import that returned wins outright; a negative `find_spec` beats a negative real import, because that combination is one fault, not two; a real import failure alone is the remaining case) is now one exported `classifyPackageFault` (`server/src/tts/models-status.ts`, `PackageFault = 'ok' | 'missing' | 'broken'`), read by all three surfaces — `diagnostics.ts`, `setup-diagnosis.ts`, and Model Manager's `engineInstallLabel` plus its three install cards (`kokoro-install.tsx`, `coqui-install.tsx`, `qwen-install.tsx`) — so none of them can disagree about which fault an engine has, or offer a button that contradicts the message next to it. A missing package now names itself as missing and points at installing it in Model Manager; a present-but-unimportable one still names itself and points at repair. When Kokoro and Qwen have *different* faults at once, a live-confirmed broken package always outranks a merely-missing one when the Setup checker picks which engine to name — a broken package is the fault the user cannot infer on their own, a missing one is self-evident from Model Manager's own inventory. `importOk === null` — nothing has attempted the import yet, the common case for Kokoro/Qwen — still reads as healthy on all surfaces, unchanged. **This also widens four of the eighteen input combinations from a false "a voice engine is ready" to a correctly-failing blocker** — not only the single `importOk === false` shape named in the original commit, but also the everyday shape where nothing has attempted the import yet (`importOk` unknown) and the package is confirmed absent (`specPresent === false`), whichever of the two axes the disk probe itself already knew about. No new false positive: `anyEngineUsable` was already `false` in every one of the newly-failing cases, so each one was silently reporting success for a book that could not actually render.
- **The offline Help view's "cloned voice can't be used as itself" entry now names the derive-failed fix** (#1979, follow-up to #1967/[#1978](https://github.com/dudarenok-maker/Castwright/pull/1978)). #1978 added "re-run the clone and check the sidecar log" to the LIVE `derive-failed` message (`UnresolvableClonedVoiceError.fromList`), but the static fallback copy the Help view shows when nothing has actually failed yet (`server/src/routes/failure-remediations.ts`) still only listed re-upload / restore consent / switch engine / reassign — the one surface that omitted the fix for the failure someone is most likely to open Help about.
- **An orphaned `characterId` (no entry in the book's cast at all) no longer silently borrows the narrator's voice with no record of it** (#2023, found by the fs-38 Wave 3 on-box acceptance run, run sheet §5 Section C, C-05). `synthesise-chapter.ts`'s `resolveGroup` has always substituted the narrator for a sentence group whose `characterId` isn't in `cast` (a cast/analysis id drift — e.g. `mairin` vs `mayrin`, `coalfall-dragon` vs `coalfall`) — real evidence: 21 of 72 segments (60.3 s) in *Заказ Коалфолла* ch.2 rendered in the narrator's voice this way, one of five affected books. The fallback itself is unchanged (it may well be the right behaviour); what was missing was any record of it beyond a once-per-orphan-id `console.warn`. Two fixes: **(1)** the render now stamps the substitution on the segment (`ChapterSegment.renderedFallbackCharacterId`), aggregated across a book's rendered chapters into a new `orphanedCharacterFallbacks` book-state field (keyed by the orphaned id, naming who rendered it and the voice used) — hydrated into the cast slice and surfaced as an advisory banner on the Cast view naming the orphaned id(s), and published per-segment on the per-chapter audio meta endpoint alongside the existing QA `suspect`/`reasons` fields. **(2)** if the narrator resolves to a **cloned** voice, an orphaned-id line now raises `cloned-voice-broken` (`UnresolvableClonedVoiceError`) instead of substituting — mirroring the enforcement `applyQwenFallback` already gives an unavailable cloned voice, extended to a *healthy* one being borrowed for another character's line, which was safe only by luck (every affected narrator across the five books happened to be a designed, not cloned, voice). The upstream cause — cast and analysis ids disagreeing — is a separate, filed issue ([#2040](https://github.com/dudarenok-maker/Castwright/issues/2040)); this PR does not touch the drift itself.

## 🎧 Listening & revising

- **Re-recording one character's lines can no longer render another character's lines in their voice** (#1972). The per-character re-record (splice) picked *which* segments to replace from the chapter's `segments.json` — written at the last render — but resolved those segments' sentences, and therefore the voice, from the **current analysis cache**, matching by sentence id. Once analysis had run since that render the two disagreed, and the re-record synthesised whoever the analysis now says owns the sentence, in the requested character's voice, spliced into their old time slot. Measured on a real book: the re-recorded lines scored **0.888** speaker-similarity against the *narrator's* lines in the same chapter and **0.196** against the character's own assigned voice. It reproduced with a perfectly healthy voice, and on two books that had diverged for unrelated reasons — one from stale attribution, one from ordinary re-segmentation — so **the only precondition was "analysis has run since the last render."** A splice now compares the two sources first and **refuses** rather than reconciling silently, naming how many segments changed owner and pointing at re-running analysis or a full chapter generation; deciding for the user would have been just as likely to destroy correct data as to fix it. **Full chapter generation was never affected** — it reads one source and stays self-consistent. Separately, `characterSnapshots.<id>.resolvedVoiceName` is now recorded from the voice actually sent to the engine instead of being re-derived from the cast record afterwards, so it can no longer report a voice that was never used — which is exactly why this went unnoticed, and why three earlier on-box acceptance results had to be retracted once it was understood.

- **fs-10 — chapter-title segment on the Listen timeline** (#412). `ChapterAudio.segments[]` gains an optional `kind: 'title'` discriminator and the chapter-audio route stops filtering the synthetic title beat out of both `/audio` and `/audio/previous`. The mini-player scrubber paints it as a non-interactive labelled band; the Generation view's "Narrative order" strip fills it neutrally rather than in the narrator's colour. **Also fixes a latent off-by-one:** because the published array was short one leading row, `resolveSegmentForSec`'s index no longer matched the on-disk index the splice route addresses, so Listen-view "Fix this line" targeted the line before the marked one.
- **The audio-QA repair endpoint finally has a frontend consumer** (plan 179). `POST …/chapters/{id}/audio-qa-repair` shipped with its "Scan & repair" affordance listed as a follow-up and never got one — a grep for the path or any `qaRepair`-shaped symbol across `src/` and `e2e/` hit only the generated types. That also meant the `voice_language_mismatch` advisory the route emits went nowhere at all. Adds `api.streamQaRepair` (real + mock), `qa-repair-slice`, and `qa-repair-runner-middleware` — deliberately mirroring `splice-runner-middleware` rather than inventing a third SSE-consumption idiom, since the repair runs through the fs-26 splice engine server-side anyway — plus a repair button on the Listen view's chapter row, gated on the srv-27 `suspect` verdict so it can't invite a pointless GPU pass on healthy audio. The middleware toasts the stream's `warning` frame the way `generation-stream-runner` toasts its own, refreshes the row's duration + cache-bust stamp on completion, and reports failures. It does NOT enqueue an A/B revision: a repair spans whichever characters owned the flagged sentences and `revisions` is keyed by a single characterId. Coverage: `qa-repair-runner-middleware.test.ts`, `listen-player-region.test.tsx`, and `e2e/qa-repair.spec.ts` walking row → middleware → mock stream → rendered toast. No OpenAPI change was needed — the QA-repair response schema already carried every field consumed.
- **A background QA repair or splice can no longer stamp the wrong book's chapter, or strand its spinner.** Both runner middlewares dispatched their chapter-updated action keyed only by chapter id — which repeats across every book — with no check that the user was still looking at the book the repair/splice belonged to, so one finishing after a book switch could mark a different book's same-numbered chapter as freshly rendered. Both now guard on the currently-open book before dispatching. Separately, an unexpected error during the repair stream (a network drop, a bad frame) used to reject past the cleanup step entirely, leaving `Repairing…` showing with no way back short of a reload; the stream call is now wrapped so any failure runs the same cleanup and summary toast a normal finish does. The QA-repair control also collapsed to 32 px at `md:` widths — squarely the tablet range — and now meets the 44 px touch target.
- **The splice stream's `warning` frame no longer falls on the floor.** `chapter-splice.ts` has always emitted a `warning` frame when `clearMismatchedDesignedVoices` drops a reused designed voice whose baked manifest language differs from the book's — but `warning` was in neither the splice endpoint's OpenAPI `type` enum nor the hand-written `SpliceTick` union, so `splice-runner-middleware`'s `onTick` parsed the advisory and silently discarded it. Adds the member to both (plus the `code`/`message` fields it carries, mirroring the QA-repair stream's) and toasts it the way `generation-stream-runner` toasts its own, deduped by `code` so a multi-chapter batch raises one advisory rather than one per chapter.
- **Series-memory's hardcoded-dark surfaces no longer borrow the theme's accent** (#1832). The three `src/components/series-memory/` surfaces pin a `#1b1714` background that never follows the app theme, but their accent resolved through the theme-flipping `--magenta` — `#A43C6C` on light, **2.918:1** on that surface, failing WCAG AA as text. New pinned `--color-magenta-on-dark` token (the accent counterpart to the existing pinned `--color-cream`), applied to the share card's label/glyph/separators/footer, the reveal's carried-badge and section label, and both gradient CTAs. The reveal's per-book dots are included because they encode which books a character appears in — meaningful graphics under WCAG 1.4.11 (3:1), also missed. Pinning their gradient forced the CTA ink off flipping `text-ink` (near-white on light pink under dark) onto the already-pinned `text-peach-ink`, 5.3–5.8:1 across the gradient. **Matters more than a normal contrast bug because the card is exported as a PNG** — a light-theme user shipped the failing version rather than merely seeing it. Regression cases live in Playwright, not vitest (jsdom doesn't resolve these tokens) and assert *identity across themes* rather than a literal, since the defect was a colour that moved when its surface didn't. Trade-off: the card no longer responds to `[data-contrast='high']` — ~11:1 → a fixed 7.6:1 for high-contrast dark, but it also stops high-contrast light resolving to a near-invisible `#7A1B49`.
- **A correctly-normalised chapter could show a false "off target" loudness pill — fixed** (srv-67/fe-58, #1922, #1923). The chapter QA verdict and the Listen-view loudness badge used to read two different numbers for the same chapter: QA judged loudnorm's self-reported `output_tp` (in dynamic mode, the requested ceiling restated, not a measurement) or, when the real re-measurement failed, loudnorm's *pre-filter* input loudness — which could bucket a chapter that actually normalised fine as several LU "off target." The single real `ebur128` measurement is now taken once, immediately after the chapter's audio is written, and feeds both the QA verdict and the Listen-view badge — they can no longer disagree. A new optional `measurementSource: 'ebur128' | 'loudnorm'` field on the loudness sidecar distinguishes an attested measurement from a fallback; a pre-change sidecar (no field at all) renders exactly as it did before, so no existing chapter loses its badge. **Both of these are true, and neither cancels the other:** the chapter QA true-peak clip check now consumes this same real measurement instead of a fabricated ceiling, AND it still cannot fire under shipped defaults — dynamic loudnorm pins the encoded peak at roughly the requested ceiling +0.1…+0.3 dB, and the default ceiling (`-1.5` dBTP) sits 1.4 dB below the default clip threshold (`-0.1` dBTP). Making the check active is a threshold/ceiling decision, deliberately left to [#1909](https://github.com/dudarenok-maker/Castwright/issues/1909) rather than retuned here. Also established: loudnorm's `output_tp` under-reports the real measured peak by 4.15 dB in linear mode (requested `-1.5`, reported `-5.85`, measured `-1.7`) — nothing downstream should read it as a peak figure, in either mode. #1923, as originally filed, described unreachable behaviour (`twoPass` is hardcoded `true`, so single-pass output never ships) and closes as not-reproducible; this fixes the real, reachable version of the same underlying defect — a measurement-failure fallback rendering as trusted ground truth. `scripts/relufs-existing.mjs`'s backfill now stamps `measurementSource: 'ebur128'` on its rewrite, so it remains the way to upgrade a pre-change chapter to a genuinely attested one. Plan: [`docs/features/archive/274-loudness-measurement-provenance.md`](https://github.com/dudarenok-maker/Castwright/blob/main/docs/features/archive/274-loudness-measurement-provenance.md).
- **The Listen-view loudness badge no longer trusts an unrecognised future `measurementSource` value as if it were a legacy pre-plan-274 sidecar** (#1949). `classifyDrift` grandfathered a genuinely *absent* `measurementSource` field to the old `twoPass`-only rule — but an unrecognised value (a closed enum today, but nothing stops a future member) fell through the same path, which would have rendered an unattested measurement as ground truth. Added an explicit guard so only `undefined` reaches the grandfather branch; any other unrecognised value renders as "No measurement," matching the existing `'loudnorm'`-fallback treatment.
- **Eight Listen-view and mini-player controls that had shrunk below the 44px touch target across the tablet range now hold it** (#1935). The chapter row's rename/regenerate/share-clip buttons (`listen-player-region.tsx`), and the chapter play/pause button, the marker "Fix this line"/kind-toggle/delete controls (also `listen-player-region.tsx`), and the mini-player's Next-issue button all used the superseded `sm:`/`md:` width-breakpoint shrink, which drops the WCAG 2.5.5 target for the entire >=640px tablet range rather than only for a mouse. - **A legitimate accented word can no longer block a release publish outright** (#1973). The mojibake gate's acceptance rule — cp1252-mappable characters whose byte values form valid UTF-8 with a lead byte >= 0xC2 — is satisfied by some genuinely correct text: any Latin-1 letter mapping to 0xC2-0xF4 sitting immediately adjacent, with no space between, to one to three characters mapping to 0x80-0xBF. Measured shapes include `CAFÉ` followed by `™`, a `groß` + em-dash construction, and `Ålesund` beside punctuation. `bump-version.mjs`'s pre-flight already honoured `--force`, but `release.yml`'s CLI path exits 1 with no bypass at all, so a false positive there blocked the publish and the only way out was editing the prose. The notes file can now name the exact literal to accept, in an HTML comment carried by the file itself — a `release-notes-gate: allow` comment naming the literal in double quotes. (The exact syntax, with a copy-pasteable example, lives in CONTRIBUTING.md's "Release notes" section rather than here, because this file is one of the two the gate reads and a realistic example written into it would allowlist itself.) That shape was chosen over an env-var kill switch because it is span-scoped, travels in the same commit as the text that needs it, and is auditable in the diff — and an HTML comment renders as nothing on the releases page, which matters because this file ships verbatim into the tag annotation. A marker does **not** expire on its own: this file is cleared by hand in the first PR after a cut, which happens to take any marker in it along. `RELEASE_NOTES.md` is cumulative and never reset, so the gate refuses any marker found there outright instead (#1985) — the failure names the file and points at re-encoding the text or `bump-version.mjs --force`, rather than letting a marker sit there silently excusing its literal for every future release. **Suppression is positional, not by substring.** The span the detector reports for a flagged `CAFÉ`+`™` is just the two-character tail, so excusing every span whose characters merely appear somewhere inside an allowlisted literal would have silently swallowed the same two characters genuinely corrupted elsewhere in the same file — quietly reintroducing #1956, which is the whole reason the gate exists. A span is dropped only when it sits wholly inside a real occurrence of an allowlisted literal in that same text; the marker line's own copy of the literal is therefore self-excusing as a consequence of that rule rather than as a hand-coded special case. Applied inside `checkMojibake`, so both enforcement points inherit it with no change at either call site, and `bump-version.mjs`'s `--force` is untouched. **And an allowlisted literal must extend beyond the span it excuses, not merely cover it.** A literal is excused at every occurrence, so a marker naming just the flagged characters would silence them file-wide — the same hole positional suppression exists to close. Widening the gate's printed suggestion is not a fix for that: the dominant corrupted shape is a mangled dash, arrow, ellipsis or emoji sitting between spaces, which is already its own whole word, so there is nothing to widen to and the printed literal is the bare span. Measured against the 242-span file this gate was built for, replaying the gate's own suggestions — paste what it prints, re-run, repeat — reached a **green gate in 24 pastes**. Replaying the gate's own suggestions is not the whole threat model, though, because an operator writes markers by hand — and requiring only that a literal extend one *character* past the span left `" —"`, a single space plus the flagged pair, perfectly legal. That one marker excused **155 of the 242** spans by itself; all 242 were suppressible, and green was reachable in **31** hand-written markers. So the rule is now enforced the way it has always been described: **a literal must be a single whitespace-free word that contains the span and extends past it**, and a literal carrying any whitespace at all — space, tab or non-breaking space — is rejected outright and excuses nothing, not even its own copy in the marker line. Re-measured against the same 242-span file: the best single hand-written marker suppresses **4** spans, only **30 of the 242** are suppressible by any marker at all, and green is **not reachable** — **212** spans always remain, whatever is allowlisted. The rule encodes why a false positive is legitimate in the first place: the detector only fires on a Latin-1 letter adjacent to punctuation, so genuinely-legitimate text always carries the surrounding characters that made it legitimate, and a span with nothing around it is by construction a real mangle. So the failure message prints a paste-able marker line only when a valid literal genuinely exists, and otherwise names which of the three reasons applies — the span stands alone, with no surrounding word to name; the word around it carries a `"` or a `-->` that cannot go inside the marker's own quoting; or the flagged span itself straddles a whitespace character, so no literal containing it can be whitespace-free (a doubly-encoded non-breaking space is `Â` + NBSP, and a doubly-encoded Cyrillic `Р` is `Ð` + NBSP, so a corrupted Russian endonym is un-allowlistable by construction) — and points at re-encoding — it never prints a line that would not work or would over-suppress, and it states outright that a marker naming only the span suppresses nothing. This three-reasons diagnostic applies to `docs/release-notes-next.md`; a `RELEASE_NOTES.md` failure never reaches it — that label short-circuits straight to the re-encode / `--force` advice, naming none of the three reasons, since a marker can't be used there at all (#1985, #2025). Two fail-closed bounds land alongside it: the mangled length of a span is measured from the reversed bytes at match time instead of inferred from the decoded lead code point (a greedy four-character match can hold two mangles rather than one mangle plus context, and inferring the length judged only the first half and dropped the second half — a genuinely corrupted sequence — with it); and a marker must be complete on a single line, where before it ran on to the next comment terminator anywhere in the file and harvested every quoted phrase in between as a literal. (A marker inside a fenced code block used to be skipped too; that exemption did not hold up and is gone — see the entry below.) Two bounds are also now recorded in the gate's own header comment: the false-positive trigger above — the header previously claimed outright that it "doesn't false-positive on real accented characters or emoji", which #1973 disproves — and the **lossy** double-encode it silently misses, where the corrupting round-trip normalised a mojibake character away (`Â` plus a non-breaking space flattened to `Â` plus a plain space) so the reverse bytes are `C2 20`, not valid UTF-8, and the span never decodes and is never reported. Inherent to the reverse-decode approach: a green gate is evidence, not proof, that a file is clean.

- **`golden-audio` Suite A now asserts the RIGHT WORDS, not just the right length** (ops-45, #1911). `kokoro-baseline.json` gains a per-line `transcript` (the sidecar's own in-process Whisper output) and `text_edits` (its edit distance from the fixture text); a fresh transcribe of each line must match the recorded `transcript` at **tolerance 0** — a single substituted, dropped, or repeated word now fails on its own, independent of the existing duration/RMS/voice-substitution checks. The anti-tautology mechanism is two bless-time guards, not a WER floor — a flat floor was shown by direct computation to refuse none of the regressions a tolerance-0 gate can detect. **G1** refuses to silently overwrite a DIFFERING recorded transcript unless `GOLDEN_REBLESS_CONTENT=1` is also set, closing a wider hole where a duration-only re-bless after a weights bump would otherwise launder any content regression that bump introduced while the reviewer's eyes are on durations. **G2** caps a bless's edit distance from the fixture text at `recorded + 1`, protecting a perfectly-transcribing line (0 recorded edits) that no flat floor can reach. `GOLDEN_ASR=0` opts a run out of the check, checked FIRST — before the Kokoro engine is even constructed, so the opt-out can't be defeated by a check-order regression; the check adds Whisper's `base`-model weights (~145 MB, fetched from HuggingFace on first run) as a new network prerequisite and ~+50% wall-clock to a Suite A run. `-rs` added to `run-golden-tests.ps1` so a skip's reason is no longer invisible (previously a bare `s`). - **The server suite's `retry:1` can no longer silently turn a genuine red-phase test green without anyone noticing** (ops-46, #2028). A test asserting on module-level mutable state keyed by a fixed string (a `Map`/`Set`/counter at module scope, or fixture state on disk keyed by a fixed path) doesn't get a clean second attempt from `server/vitest.config.ts`'s `retry: 1`: attempt 1 fails and leaks its mutation, attempt 2 reads the already-mutated state and passes for the wrong reason — found landing #2001, where a genuine red-phase test only went red with an explicit `--retry=0`. #2028's Acceptance offered two deliberate options, Narrow or Global, and this ships **Narrow**: `server/src/workspace/file-lock.test.ts`'s `describe('withKeyLock', ...)` — the module-level `chains` Map #2028 names — now sets `{ retry: 0 }`, so a red-phase test against that shared state is never silently rescued by the suite-wide retry. Global was surveyed rather than assumed and rejected on the evidence: `npx vitest run --retry=0` against the unmodified suite reddens `src/routes/voices.test.ts` deterministically on the first attempt, so at least one existing, unrelated test is currently green in every gating run purely because the retry papers over it — dropping the retry suite-wide would have reddened every lane's CI on a file this change doesn't own until that's root-caused (filed as #2046). A new `retryHazardReporter` layers additive observability on top of Narrow, for every OTHER file the suite-wide `retry: 1` still covers: any test that fails on attempt 1 and only passes after a retry prints a `[retry-hazard]` line naming the file and test, so the hazard can no longer pass silently there either — a human then re-runs with `--retry=0` to judge genuine transient (`quarantinedIt`, `docs/testing/flaky-register.md`) vs. red-phase-hidden-by-retry. `CONTRIBUTING.md` documents the `--retry=0` mutation-verification convention this exists to surface.
- **The release-notes gate now catches unresolved git conflict markers** (#2018). `scripts/release-notes-gate.mjs` read `RELEASE_NOTES.md` and `docs/release-notes-next.md` for a version match and mojibake, but not for `<<<<<<<`/`>>>>>>>` markers — not hypothetical: three landed inside `RELEASE_NOTES.md`'s own v1.15.0 section on PR #2010 with every gate green, caught only because a reviewer read the merge commit's diff by hand. `checkConflictMarkers` anchors on the `<<<<<<< `/`>>>>>>> ` pair (each with git's mandatory trailing space) rather than also matching a bare `=======`, which can be a legitimate markdown setext heading — so it can never false-positive on real prose, and unlike the mojibake check it has **no allowlist and no `--force`/`--dry-run` downgrade**: a marker found in either gated file dies unconditionally, in both `release-notes-gate.mjs`'s CLI and `bump-version.mjs`'s two pre-flights.

- **The golden content-drift gate no longer scores a dropped or added contraction as zero edits** (#2005). `compare.normalize_words` stripped `'s` off the whole token stream to mirror `segment-asr-qa.ts`'s possessive strip, but that production line only ever strips a genuine possessive because a prior step (contraction expansion) already ran first; `normalize_words` never had that prior step, so the strip also silently collapsed `'s` **contractions** — `he's` == `he`, `it's` == `it` — on a gate whose whole advertised purpose is single-word drift (live on the committed `abbreviations` fixture, `Aldric's`). - **`instruct-baseline.json`'s identity/loudness_dbfs bless guard is now noise-tolerant, not exact-equality — and the guard that decides WHICH fields count as "previously blessed" was fixed three times before landing** (#2035, #2045, hardened again by independent review after #2045 merged). `bless_guard_thresholds` originally applied the same exact-equality bar to `identity`/`loudness_dbfs` as to the quantised `tolerances` block — but both are raw stochastic measurements (`instruct-baseline.json`'s own `metadata.notes`: ~0.0014 run-to-run identity spread), so exact equality refused on every honest re-bless, training an operator to reach for the shared `GOLDEN_REBLESS_THRESHOLDS=1` flag on a ROUTINE bless and silently re-opening #1995's `tolerances` hole one level down. The guard now accepts a move within a field-specific epsilon — `compare.LOUDNESS_DBFS_EPSILON` (10% of the ±`loudness_dbfs_abs` window the field is diffed against) and `compare.IDENTITY_COSINE_EPSILON` (0.005, ~3.6x the baseline's own observed 0.0014 noise floor — recalibrated off that noise rather than 10% of `identity_cosine_max`, a ceiling `identity` doesn't actually feed as a diff target, which independent review found made the original 0.015 arbitrary and 1.2x the entire committed identity value) — and PRINTS a `[golden-bless] <field> moved …` line so the move stays loud rather than silent, per #2035's original acceptance criterion. That line initially mislabelled every echoed move "within epsilon … (noise)" unconditionally, including one only written because the flag forced it through despite being well beyond epsilon; it's now derived from the actual leaf diff and reads `BEYOND epsilon … (FORCED by GOLDEN_REBLESS_THRESHOLDS)` when that's what happened. Separately, `_bless()`'s `previously_blessed` probe — which decides whether a missing guarded key is a genuine first bless or a previously-blessed baseline that lost a key (e.g. a hand-resolved merge conflict) — went through three shapes: `bool(baseline.get("identity"))` was circular for `label="identity"` itself; `bool(baseline.get("rtf"))` fixed the circularity but left a single-key blind spot (losing `rtf` alone, as likely in a merge conflict as losing `identity`, failed all three guards open at once); `any(k in baseline for k in (...))` closed that but checked presence, not truthiness, so it read `instruct-baseline.json`'s own documented never-blessed scaffold (all four guarded keys present but explicit `null`, per the file's `description` field) as "previously blessed" and refused a genuine first bless. The shipped probe is `any(baseline.get(k) is not None for k in (...))`. Test-tier only, no production code changed; every fix is mutation-verified against the defect it closes.
