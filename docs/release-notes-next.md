## 🔊 Generation quality & engine health

- **Learned VRAM footprints count only a cold load's own allocation (#4163).** `_reset_peak_mb` reset the CUDA peak to the memory already allocated. As a result, `_observed_mb` learned every tensor resident on the card, other engines' weights included, as the op's footprint, and the learned bookings for `qwen*`, `coqui`, `kokoro` and `spk` drifted up whenever another engine was co-resident. Each reservation now records `memory_allocated` at the reset as its own baseline and learns `max_memory_allocated - baseline` (floored at 0; no baseline, no sample). It does this only when the engine had no model resident at admission (for Qwen, none of its four models; new `any_model_resident` predicate). Warm ops record nothing, so warm synths can no longer shrink the cold-load booking that shares their key, and co-resident engines can no longer inflate it. An engine whose model is loaded counts as warm whatever device it sits on, so a `kokoro` synth on the CPU provider records nothing either. Two residuals remain: (1) torch's peak counter is per device, so an overlapping op on the same card can still truncate or inflate a sample; (2) memory another op frees during the window can push a sample below the op's own weights (down to 0), which `main` could not do because its sample always included the op's own resident allocation. ASR (device-wide free delta, #3266) is unchanged. Learned values are held in memory only, so nothing is migrated; the over-booking has been present since learned footprints shipped, so it affected v1.15.0.


- **A chapter render that fails after its audio was encoded no longer leaves a chapter-sized temp file in the book's audio folder.** `finalizeChapterAudioWrite` wrote `<slug>.<ext>.tmp-<pid>-<ts>` before its fallible steps and only renamed it at the end, so any throw in between (the temp write itself, embeddings or segments write, the rename) leaked the file. The exported function is now a wrapper that removes the temp file on any exit before a successful rename, logs and swallows a failed removal, and rethrows the original error. Covered by `finalize-chapter-write.tmp-cleanup.test.ts`. Temp files leaked by earlier failures are not swept; that is #3456's boot sweep, not this fix (#4211, closes #4167).
- **Reopening an Opus book no longer shows every chapter as unmade, and a chapter with only an earlier take no longer shows as done.** The book-state GET's `completedSlugs` used a `.mp3/.m4a/.opus` regex plus `startsWith(slug)`, so Opus (`.ogg`) books never showed a chapter as done and a lone `<slug>.previous.mp3` counted as done; it now asks `chapterAudioExists` (the same live-take finder exports use), which also stops `ch-1` matching `ch-10.mp3`. The library scan's `completedChapters` had the same regex and counted files rather than chapters, so a fully rendered Opus book sat at `voices_pending` (the "Cast ready" badge, 0 of 2 counted) on its Library card, and opening it from the Library went to Cast instead of Listen; it now counts non-excluded chapters with a live take. Covered by `server/src/routes/book-state.completed-slugs.test.ts` and `server/src/workspace/scan.test.ts` (#4166).

- **Admission no longer evicts the model the admitting request itself needs (#4079 follow-up: mint, design, GPU ASR, GPU SPK).** Four cases still threw away and reloaded their own resident model through the GPU admission ladder. A `mint` with the 1.7B-Base resident now keeps it: the `qwen.base17` step is protected, the request is restricted to the card the base is on, and the resident base's weights (measured at load, fallback 3400 MB) are credited in its own fit check only, while the ledger books the FULL `qwen.1.7b.mint` peak (as for the plain synth), so a second admission nested inside a mint is refused. A `design` with VoiceDesign resident protects `qwen.design` the same way, and also credits the resident 0.6B audition base that every design leaves loaded (measured at load, fallback 1200 MB; a mint does not get this credit, #4237), so back-to-back base-voice designs on an 8 GB card with little else on it (at most about 1.2 GB in use besides the sidecar's own models) are admitted without reloading VoiceDesign or waiting for the idle watchdog; with more in use, up to about 1.6 GB, the design waits for the watchdog (~120-150 s at the default idle TTL). A credited model freed during an admission ladder step is no longer counted twice in the later re-probes. Node's capacity lever gets a `mint` purpose that keeps the 1.7B tier, so a mint's capacity retry never posts `/unload {model:'1.7b'}`. GPU ASR and GPU SPK with their model resident likewise protect their own ladder step, target the resident card for the ladder, the reclaim and the `noCapacity` `deviceKey`, and book the warm amount: `asr.warm` (128 MB, existing) and the new `spk.warm` (128 MB, an unmeasured prior that is not learned, because #4163's cold-only gate records nothing for a warm op). On an 8 GB card, minting emotion takes with the 1.7B-Base loaded no longer unloads and reloads it per take, and with `ASR_DEVICE`/`SPK_DEVICE` set to `cuda` a busy card answers `noCapacity` (and the server retries) instead of evicting the check's own model (#4102).

## 🎭 Cast and re-analysis

- **A re-analysis no longer leaves a book without a narrator row when `cast.json` was rewritten during the run** (a first-upload job that was never registered, a tab without an analysis era, a hand edit on disk): the persist re-creates the narrator from the run's roster (no voice restored) and keeps its lines on it, drift-refused persists included. Every other row deleted mid-run still stays deleted (rule 13). (#4196)
- **An analysis no longer orphans the audio of a rendered chapter whose title changed.** A chapter-title parser version bump retitles a rendered chapter in `state.json` while keeping its slug; the next analysis persist (main and subset job) then recomputed the slug from the new title. The persist now keeps a chapter's existing slug whenever a live take (`<slug>.mp3`, `.m4a` or `.ogg`) exists at it, so only the title changes and the chapter still reads as rendered with its audio, segments and peaks at the original slug; a chapter with no take still gets the recomputed slug. Previously `state.json` pointed at a slug with nothing under it and the take was left behind (#4306, closes #4230).

## 🐛 Other fixes

- **A chapter's previous take keeps its real file type, and takes now have an identity (#3456, #4319).** The take Reject restores was always named as an mp3, whatever the book's format, so an M4A or Opus book could get a misnamed original back. - **An interrupted restructure no longer leaves the saved script keyed to the old chapters (#4227).** `applyRestructureClaimed` wrote `state.json`, then `manuscript-edits.json`, and a crash between the two (or a throw from the edits write) left the new chapter list beside sentences still keyed to the old chapter ids; the GET reconciliation filter in `book-state.ts` drops edits by sentence-id range and never re-keys a renumbering, so nothing recovered it. A merge, split, reorder, exclude/include, rename or refresh-titles now writes `<book>/.audiobook/restructure-edits-journal.json` (the edits file's sha256, the new chapter list as `id` + `uuid`, and the sentence remap) before `state.json`, and clears it after the edits write lands; no journal is written when the book has no edits file. `replayRestructureEditsJournal` (`workspace/restructure-edits-journal.ts`) re-keys the edits from the remap and refreshes the analysis cache, and runs at the start of the next restructure of the book and at server start (never on a read). It replays only under two guards: `state.json`'s chapter `[id, uuid]` sequence must be the journal's, and `manuscript-edits.json` must still be byte-for-byte the input the journal was taken from (its sha256); in every other case the journal is discarded. Residuals: an edits-write failure with no crash leaves the old-keyed edits until the book's next restructure or the next server start, and a client save of `manuscript-edits.json` in that window changes the sha, so the journal is discarded rather than applied; the in-memory manuscript record, the audio renames, the pending-entry reconcile and the analysis cache after an interruption are not recovered by it. No `state.json` field is added. A replay re-keys `manuscript-edits.json` behind any open client, and a client that applied the response's `sentenceRemap` to its own old-keyed copy dropped every line the remap did not name and then saved that over the repaired file (PR #4313 review pass 1). Every restructure response (merge, split, reorder, exclude/include, refresh-titles) now carries `editsRevisionBefore`, the manuscript slice token (`sliceRevision('manuscript', …)`, the salt `GET /state` uses) of the edits the request read after its own replay and before its own rewrite; `RestructureView` compares it with the token the persistence middleware last learned (`knownSliceRevision`) and, when they differ, takes the sentences of its book-state re-read instead of applying the remap (with no re-read it leaves its copy alone and keeps the edit lock up for Layout's marked full read). A token comparison rather than a flag covers both triggers, the replay inside the request and a boot-sweep replay a tab left open across a restart never saw. Not covered: (1) a rename answers no remap, so a replay it triggers leaves an open tab's old keys until the tab's next read or save, and a restructure the route refuses after replaying does the same; (2) a stale tab's first save, which carries no base, after a replay writes its whole old-keyed copy back (main parity: no line is deleted, the end state is the one before the journal). The client takes the re-read's token for the manuscript slice only (`learnSliceRevisions(…, ['manuscript'])`), so a retried cast or state save is still refused as stale when another tab changed that slice. Covered by `server/src/routes/chapters-restructure.edits-journal.test.ts`, `server/src/workspace/restructure-edits-journal.test.ts`, `server/src/workspace/restructure-edits-journal.boot.test.ts` and `src/views/restructure.edits-moved.test.tsx`.

- **Script Review anchors now resolve after a character that changes under NFC** (#4221, closes #4219). `resolveAnchorOffset` normalised the anchor per code point but built its offset map per UTF-16 unit, so an anchor that itself contained an astral character that NFC rewrites (a CJK compatibility ideograph such as U+2F800) was unresolvable and the suggestion was skipped as unappliable. `projectToChars` (`server/src/analyzer/attribution-eval/char-project.ts`) built the same map per UTF-16 unit and dropped any unit that contained such a character; it is fixed too. - **Script Review anchors match canonically equivalent spellings and never split a user-perceived character** (#4312, closes #4226). Matching now applies NFC per run, where a run is one extended grapheme cluster (`Intl.Segmenter`, granularity `grapheme`) instead of one code point, so a composed and a decomposed spelling of the same text match. The offset map has an entry only at run boundaries, so an anchor whose end falls inside a run is refused (`null`), never rounded; that covers ending just before a combining mark (`Mn`, `Mc` and `Me`), inside a decomposed Hangul syllable, between an emoji and its skin-tone modifier, inside a ZWJ sequence or a regional-indicator flag, part-way through the `…` → `...` fold, and between the halves of an astral character (`('Wait… no', 'Wait.')`, for example, used to resolve to 5). - **Paragraph recovery now applies its split points in UTF-16 space, so an emoji or other astral character no longer shifts them** (#4204, closes #4165). ## 🔌 Sync & server infrastructure

- **The server now writes a Node diagnostic report when it dies of a V8 fatal error,** into `logs/node-reports/` (`<APP_LOG_DIR>/node-reports/` when set), with Node's default timestamp-and-pid file name. It is enabled in-process at the start of boot, but only when node runs with `--report-exclude-env --report-exclude-network`, which every launcher now passes (`npm start`, `npm run dev`, `dev:lan`, `start:lan`, `start:prod`, Pinokio). The boot logs `[server] diagnostic report on a fatal error -> <dir>`, or an `OFF` line saying why when the folder can't be created or the flags are missing; boot continues either way. The check requires `process.report.excludeEnv` and `excludeNetwork` to already be true, i.e. that node itself parsed the flags (from its command line or `NODE_OPTIONS`), so a `NODE_OPTIONS` that `server/.env` sets after node started does not count. The flags keep the environment variables and the network interface list out of the main thread's report and out of the sub-report of every worker that inherits `execArgv`, since it is meant for a public issue. A `Worker` started with its own `execArgv` parses that plus the `NODE_OPTIONS` in its env instead, never the parent's command line, and in dev tsx's esbuild starts one with `execArgv: []` (its sync API), whose sub-report in an old-generation OOM would otherwise carry the whole environment and the interface list. So the dev launcher (`server/package.json` `dev`, now `node ../scripts/dev-server.mjs`, behind `npm start`, `npm run dev`, `dev:mock` and `dev:lan`) also starts tsx with both flags appended to `NODE_OPTIONS` (`scripts/lib/report-exclusion.mjs`, never clobbering the user's), and `start-app-prod.mjs` does the same for its server child; the prod server starts no Worker today. The runtime `excludeEnv`/`excludeNetwork` setters alone do not reach a young-generation OOM's report or a worker's sub-report. The report still carries the machine name (`header.host`), paths, the CPU model and the address of every open socket (`libuv[]` `localEndpoint`/`remoteEndpoint`: `host`, `ip4`, `ip6`). Evidence capture for the unexplained silent server deaths; a native crash (0xC0000409) writes no report, so read the folder together with the sidecar's exit-code line. On-box row A124. (#4054)
