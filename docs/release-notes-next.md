## 🔊 Generation quality & engine health

- **MP3s encoded by ffmpeg 9.1 no longer carry a wrong encoder delay: Audio-QA repair, chapter splicing and exports stay sample-aligned (#4573).** ffmpeg 9.1's libmp3lame *encoder* stamps the Xing/LAME tag with an encoder delay of 47 (`576 - 529`) instead of LAME's 576, but only on MPEG-2 / MPEG-2.5 streams (24 kHz and below, so every chapter we render; 44.1 and 48 kHz keep the right value). Every decoder, 8.x included, then trims 529 samples (~22 ms at 24 kHz) too few from the front, and `ffprobe` reports the file ~22 ms long. `encodePcmToAudio` (`server/src/tts/mp3.ts`) now rewrites a delay in (0, 576) to 576 and recomputes the tag CRC (`fixLameEncoderDelay`), and `applyId3v24Tags` does the same on the `-c:a copy` remux that builds the MP3 zip/folder export (the remux carries the wrong delay over and rewrites the encoder string to `Lavf`), so every file we write is right for every player; it is keyed on the tag's content, so a correct tag is left byte-identical. Chapters rendered before the fix keep the wrong tag, so `decodeAudioToPcm` / `decodeAudioFileToPcm` also read it (`mp3StartPadShortfall`: `Xing`/`Info`, encoder string `LAME`/`Lavc`/`Lavf`, behind an ID3v2 block of any size) and drop the missing lead-in, scaled from the MP3's own rate to the decode's output rate, so per-segment windows land on their own audio again and `evaluateSegmentPcm` flags a dead segment instead of seeing the neighbouring take bleed into it. Fixes the 27 `chapter-qa-repair.test.ts` failures on Windows CI with Chocolatey ffmpeg 9.1.0. A pre-fix chapter keeps its wrong tag in the workspace: only the MP3 zip/folder export (and the sync folder built from it) corrects it, in the exported copy. The m4b export bakes the ~22 ms lead-in in (it re-encodes from ffmpeg's own decode), the portable bundle copies the workspace bytes as they are, and `build-m4b`, `clip` and the browser player keep reading the wrong tag until the chapter is re-rendered.
- **A capacity-denied op no longer unloads a Qwen model another live voice design or variant mint is using (#4533).** `evictIdleQwenBase` freed both Qwen bases for a non-Qwen op (a Coqui preview denied capacity), and the 1.7B unload (`unload_base17()` at its default `wait_seconds=0`) does not wait for an in-flight mint, which then raised. The lever now reads the in-flight design and mint counts from `gpu/active-generation-gate.ts` (`inFlightDesignMintCounts`) and subtracts the caller's own (design-voice-core increments before it asks): another live mint keeps the 1.7B base, and another live design keeps the 0.6B base (`/unload {engine:'qwen'}` nulls VoiceDesign with it) — for a design, mint or Quality caller only when that design is resident on the sidecar, for any other caller (a preview) whenever one is counted live. A model neither uses is freed as before. A hold-back answers `'declined'` so the waiting op asks again once the other ends, and a re-ask while something is still held back frees only that, and once the other op ends the next ask frees whatever it no longer uses (a mint reloads its 0.6B in its own phases). The give-up error now names another live design or mint holding a base on the denied card, never the caller's own. #4066's "auto-free, then design" still holds for the caller. Register row A133.
- **Learned VRAM footprints count only a cold load's own allocation (#4163).** `_reset_peak_mb` reset the CUDA peak to the memory already allocated. As a result, `_observed_mb` learned every tensor resident on the card, other engines' weights included, as the op's footprint, and the learned bookings for `qwen*`, `coqui`, `kokoro` and `spk` drifted up whenever another engine was co-resident. Each reservation now records `memory_allocated` at the reset as its own baseline and learns `max_memory_allocated - baseline` (floored at 0; no baseline, no sample). It does this only when the engine had no model resident at admission (for Qwen, none of its four models; new `any_model_resident` predicate). Warm ops record nothing, so warm synths can no longer shrink the cold-load booking that shares their key, and co-resident engines can no longer inflate it. An engine whose model is loaded counts as warm whatever device it sits on, so a `kokoro` synth on the CPU provider records nothing either. Two residuals remain: (1) torch's peak counter is per device, so an overlapping op on the same card can still truncate or inflate a sample; (2) memory another op frees during the window can push a sample below the op's own weights (down to 0), which `main` could not do because its sample always included the op's own resident allocation. ASR (device-wide free delta, #3266) is unchanged. Learned values are held in memory only, so nothing is migrated; the over-booking has been present since learned footprints shipped, so it affected v1.15.0.


- **A chapter render that fails after its audio was encoded no longer leaves a chapter-sized temp file in the book's audio folder.** `finalizeChapterAudioWrite` wrote `<slug>.<ext>.tmp-<pid>-<ts>` before its fallible steps and only renamed it at the end, so any throw in between (the temp write itself, embeddings or segments write, the rename) leaked the file. The exported function is now a wrapper that removes the temp file on any exit before a successful rename, logs and swallows a failed removal, and rethrows the original error. Covered by `finalize-chapter-write.tmp-cleanup.test.ts`. Temp files leaked by earlier failures are not swept; that is #3456's boot sweep, not this fix (#4211, closes #4167).
- **Reopening an Opus book no longer shows every chapter as unmade, and a chapter with only an earlier take no longer shows as done.** The book-state GET's `completedSlugs` used a `.mp3/.m4a/.opus` regex plus `startsWith(slug)`, so Opus (`.ogg`) books never showed a chapter as done and a lone `<slug>.previous.mp3` counted as done; it now asks `chapterAudioExists` (the same live-take finder exports use), which also stops `ch-1` matching `ch-10.mp3`. The library scan's `completedChapters` had the same regex and counted files rather than chapters, so a fully rendered Opus book sat at `voices_pending` (the "Cast ready" badge, 0 of 2 counted) on its Library card, and opening it from the Library went to Cast instead of Listen; it now counts non-excluded chapters with a live take. Covered by `server/src/routes/book-state.completed-slugs.test.ts` and `server/src/workspace/scan.test.ts` (#4166).

- **A GPU Whisper or Qwen on the second card is no longer fit-checked against the first (#4456).** A CT2 (faster-whisper) model and the `qwen_tts` wrapper have no torch `.parameters()`, so `_engine_actual_card` gave them `index: None` and `_is_resident` read that as `cuda:0`. With `ASR_DEVICE=cuda:1` a warm `/transcribe` (or, with a Qwen 0.6B on `cuda:1`, a warm `/synthesize`) therefore fit-checked, ladder-evicted and reported `noCapacity.deviceKey` against `cuda:0`, and a cold 1.7B pinned to `cuda:1` was admitted to `cuda:0`; `/health` `gpus[]` filed the model under the synthetic idx -1 "unindexed" entry rather than its card. `_engine_actual_card` now takes the index from `_device` for every engine on that no-index path (Whisper and Qwen, whose `_device` is the admitted placement; SPK's ECAPA model has torch `.parameters()` and never reaches it); Kokoro (ORT) has `_resolved_device`, never reaches it, and keeps its family-only answer. On-box row A131. Also changed, found in passing: `_write_restart_breadcrumb` builds its `residentEngines` from the same `_resident_engines_by_card`, so a per-card code-43 trip on a non-zero card now reports `qwen` and `asr` where it used to report neither. `runAutoRevert` (`auto-revert.ts`) therefore can now write a `tts.qwen.device` override (the other card if it has at least 6500 MB free, else `cpu`) and respawn, where it used to answer "unrevertable" with a false "no TTS engine was resident" toast. This is auto-revert's designed behaviour, but no production run has exercised it for Qwen; it is covered by the on-box row A131 only for the card placement, not the revert.
- **Admission no longer evicts the model the admitting request itself needs (#4079 follow-up: mint, design, GPU ASR, GPU SPK).** Four cases still threw away and reloaded their own resident model through the GPU admission ladder. A `mint` with the 1.7B-Base resident now keeps it: the `qwen.base17` step is protected, the request is restricted to the card the base is on, and the resident base's weights (measured at load, fallback 3400 MB) are credited in its own fit check only, while the ledger books the FULL `qwen.1.7b.mint` peak (as for the plain synth), so a second admission nested inside a mint is refused. A `design` with VoiceDesign resident protects `qwen.design` the same way, and also credits the resident 0.6B audition base that every design leaves loaded (measured at load, fallback 1200 MB; a mint gets the same credit, #4237), so back-to-back base-voice designs on an 8 GB card with little else on it (at most about 1.2 GB in use besides the sidecar's own models) are admitted without reloading VoiceDesign or waiting for the idle watchdog; with more in use, up to about 1.6 GB, the design waits for the watchdog (~120-150 s at the default idle TTL). A credited model freed during an admission ladder step is no longer counted twice in the later re-probes. Node's capacity lever gets a `mint` purpose that keeps the 1.7B tier, so a mint's capacity retry never posts `/unload {model:'1.7b'}`. GPU ASR and GPU SPK with their model resident likewise protect their own ladder step, target the resident card for the ladder, the reclaim and the `noCapacity` `deviceKey`, and book the warm amount: `asr.warm` (128 MB, existing) and the new `spk.warm` (128 MB, an unmeasured prior that is not learned, because #4163's cold-only gate records nothing for a warm op). On an 8 GB card, minting emotion takes with the 1.7B-Base loaded no longer unloads and reloads it per take, and with `ASR_DEVICE`/`SPK_DEVICE` set to `cuda` a busy card answers `noCapacity` (and the server retries) instead of evicting the check's own model (#4102).

- **A mint on an 8 GB card now credits its resident 0.6B audition base in its own fit check (#4237).** A mint's peak co-loads the Qwen 0.6B-Base audition model with the 1.7B-Base, but its fit check credited only the 1.7B-Base, so a second voice variant (take 2) on an 8 GB card with little else on it was refused for memory the mint itself was already holding. The mint now credits the resident 0.6B (weights measured at load, fallback 1200 MB) in its own fit check only, mirroring the design credit in #4208 and the #4102 note above. The ledger still books the FULL `qwen.1.7b.mint` peak (6144 MB), so a second admission nested inside a mint is refused as before. A design made right after minting (VoiceDesign cold, the 0.6B still resident) credits the resident 0.6B the same way, with no ladder step protected (c0a0ff02), so it is no longer refused (before, the design was refused, Node's design lever unloaded the 0.6B, and the retry admitted the design and reloaded it) and does not unload and reload the 0.6B; a cold VoiceDesign is never credited. Covered by the admission tests in `server/tts-sidecar/tests/test_17b_tier_lifecycle.py`.

- **Admission frees room on the card the request is restricted to, not the roomiest GPU (#4164).** `PlacementController.admit()` and `_resolve_admission()` aimed the idle-evict ladder at `credit_card` when a credit existed, and otherwise at `_worst_device_key`, the card with the most free memory. A resident Coqui or 0.6B base engine, or an op pinned to a card, can only run on that card, so on a multi-GPU box the ladder evicted idle engines from the wrong card and the op still did not fit. The ladder now targets the `constraint` card (credited, then resident, then pinned) and falls back to `_worst_device_key` only when the op is unrestricted. Covered by `test_admission_ladder_card.py`. The sidecar now also logs `admission ladder (<engine>): evicted step <step> on <card>` at INFO after each ladder step that really freed something (not for a step that freed nothing or raised), and the `_parse_device_hint` docstring and the two placement spec docs no longer claim the ladder targets the roomiest card.

- **The generation path now keeps only the Qwen tiers a book's unfinished chapters will use (#1393, plan 293).** The idle-tier reconcile used to keep every tier the whole cast could need, so a silent 0.6B character pinned the 0.6B on a pure Quality book, and a character that fell back to Kokoro still pinned a tier. It now plans from the speakers of the chapters still to render (fallback-aware, via the pure `chapterQwenTierNeeds`), unioned with the book's pending queue entries and its live same-book jobs; the run-start reconcile runs after the job registers, reads the keep after the sidecar health probe, and the post-score reconcile recomputes the book's needs when it runs. A queued chapter keeps the voice model it was queued under, even if you switch the session model before it runs, and the browser that enqueued the chapter decides its tier, not the one that later picks it up (queue entries are stamped with the TTS model at enqueue; an entry queued before the app has loaded your saved model is left unstamped and behaves as before). A pending entry is evaluated at its own stamp's engine as well as its Qwen tier, and every pending entry of a chapter counts, including a re-queue of the chapter being rendered or just finished (only the POST's own entry, or the just-finished job's own entry, is left out, matched by entry id), so a re-queue at another tier keeps both. After a book's last chapter the post-score reconcile falls back to the run-start keep instead of skipping, so a tier only the scoring audition pulled in is still freed. Transport guards G1/G2 check that every voice design and mint is counted. #4497's skip-while-other-work-is-live is unchanged. On-box row A134.

## 🎭 Cast and re-analysis

- **A re-analysis no longer leaves a book without a narrator row when `cast.json` was rewritten during the run** (a first-upload job that was never registered, a tab without an analysis era, a hand edit on disk): the persist re-creates the narrator from the run's roster (no voice restored) and keeps its lines on it, drift-refused persists included. Every other row deleted mid-run still stays deleted (rule 13). (#4196)
- **An analysis no longer orphans the audio of a rendered chapter whose title changed.** A chapter-title parser version bump retitles a rendered chapter in `state.json` while keeping its slug; the next analysis persist (main and subset job) then recomputed the slug from the new title. The persist now keeps a chapter's existing slug whenever a live take (`<slug>.mp3`, `.m4a` or `.ogg`) exists at it, so only the title changes and the chapter still reads as rendered with its audio, segments and peaks at the original slug; a chapter with no take still gets the recomputed slug. Previously `state.json` pointed at a slug with nothing under it and the take was left behind (#4306, closes #4230).
- **Start fresh no longer gets a displaced run's last chapters written back over it** (#3437). Every analysis run now carries a per-manuscript run epoch, bumped when a job registers; a cache save/patch/clear, manuscript-edits roll, fold or dedup merge-journal write, cast.json write or state.json write from a run whose epoch is stale is dropped inside its serialised section and logged (`dropped stale-run write`), and the superseded run ends as `aborted`. cast-id-history retirements are never dropped.

- **Render and analysis on one book are mutually exclusive (#3436).** `POST .../generation`, `.../chapters/:id/splice` with `mode: 'rerecord'` and `.../chapters/:id/audio-qa-repair` with `dryRun: false` answer 409 `book_busy` (plain JSON, before any SSE header) while an `analysis` job is registered, because those are the modes that rebuild the analysis cache; a splice `remix` and a dry-run scan are unaffected, in both directions: they register under their own `audio-fix` job kind, which an analysis start ignores (they still make the book busy for rename / delete). The other way round, an analysis start (main and subset POST) answers 409 `book_busy` while the book has a `render` job registered: an early check before the stream opens, plus a late one atomic with the analysis's own registration (`runBookJob`'s `refuseIfLive`, inside book-op; an SSE `error` frame with code `book_busy`, since the headers are flushed). A join of a live run, another book and any other job kind are never refused. An analysis-start `book_busy` is a quiet refusal at all four client sites that start one (Generate Re-analyse, Analysing view main start and per-chapter Retry, stream middleware subscribe): the sentence is shown, with no failure text, gap, halted snapshot or red toast. Out of scope by owner ruling: the cast-alias / library cast-override writers (profile data, kept allowed by R55) and `samples.ts` (only creates a new book).
- **The queue holds a book's chapters while it is analysed (#3436).** The dispatcher skips a book whose analysis is running and resumes it when it ends, so its queued chapters stay `queued` instead of failing; other books keep rendering. A `book_busy` render refusal that still arrives (an analysis registered between the claim and the POST: one started from another device, or a paused run still draining) is tagged `book-busy` client-side; the server requeues the entry atomically (`POST /api/queue/:entryId/complete` with `outcome: 'requeued'`, `in_progress` to `queued` in one write, so `failed` is never written to `.queue.json`; the entry is never left `failed`), the viewed book's chapter row is restored and no change-log line is added, and the book is held off for 5 s and is exempt from the srv-11 failure streak, so it can no longer pause the queue for every book. The Generate view disables Resume, Regenerate, Retry and the per-chapter and per-character starts for any analysis run of the book (not only an include) with "Analysing this book. Available when it finishes."
- **Including a chapter is refused while the book is being analysed (#3436).** `POST .../chapters/:id/exclude` with `excluded: false` now answers 409 `book_busy` while an analysis job (main or subset, live or still stopping) is registered, because an include rewrites the chapter hints that run reads. Any other job kind still lets an include through; an exclude is still refused while any long job is registered (#3774). Nothing is written on a refusal, and the Generate view shows the server's sentence on the row instead of reporting a failed analysis.

## ⚙️ Setup, prerequisites & dependencies

- **Node 22 is dropped and the Node floor is now 24.16.0, because every Node release below 24.16.0 carries the Windows loopback-connect crash (#4443).** On Windows, libuv's `uv__is_fast_loopback_fail_supported()` calls `RtlGetVersion` on an `OSVERSIONINFOW` whose `dwOSVersionInfoSize` is never set (libuv#5106, fixed by libuv#5107). The first TCP connect to 127.0.0.1 can then fail-fast with exit 0xC0000409. The `export.test.ts` worker crash in #4442 is related but is not closed by this change: its recorded crash ran on Node v24.22.3, a release with the libuv fix, so it has a different or additional cause. Source reads at 20.19.5, 21.7.3, 22.22.0 to 22.23.5, 23.0.0, 23.6.0 and 23.11.1 all show it, and no fixed 20.x to 23.x exists, so those lines are dropped. `package.json` `engines.node` is now exactly `>=24.16.0`, a plain floor with no union and no upper bound. The owner accepted that this floor admits Node 25.0 to 25.9 and 26.0.0, which are still affected; on Windows the start-up guard (#4492) still refuses them. The guard reads the ranges `{0.0.0→24.16.0}` and `{25.0.0→26.1.0}` from `package.json` `castwright.node.windowsLoopbackCrash` and refuses to start with a message naming the running version and the one minimum that works, `engines.node` (24.16.0), whichever range matched. Pinokio's conda pin changes from `nodejs=24` to `nodejs>=24.16.0,<25` in `pinokio-scripts/install.js` and `pinokio-scripts/update.js` (conda-forge publishes affected builds 24.3 to 24.14 and a fixed win-64 build, 24.22.3); existing installs converge on the Update after the one that brings this release in: that first Update runs the previous release's `update.js`, whose `nodejs=24` is already satisfied by an affected 24.3 to 24.14 build, so conda leaves it. The guard then refuses to start with a message that tells a conda-env Node (`CONDA_PREFIX` set and `process.execPath` inside it) to run Update again, and keeps the nodejs.org advice for any other Node. INSTALL.md and the wiki install page now say "Node.js 24.16 or newer". The refusal is also written to `logs/node-refused.log` (under `APP_LOG_DIR` when set) before the launcher exits, because the in-app "Upgrade & restart" path from a release older than this one runs the new release's `restart-after-upgrade.mjs` and `launch.mjs` with stdio ignored: the user sees the "app is restarting" page forever with nothing on screen, and the old release is already stopped with `.current-version` pointing at the new one. On that path the new release's `restart-after-upgrade.mjs` now runs the same guard first: on a Node the new release would refuse (or when the check itself cannot run) it points `.current-version` back at the previous release, relaunches it, and writes the reason into `.upgrade-staging/state.json` so `GET /api/upgrade/state` returns `phase: error` and the upgrade card shows it (#4443). This holds back on Windows only, and only to a release that is complete (launch entry, `package.json`, finished `npm ci` at the root and in `server/`) and whose own range list admits the Node; when none qualifies nothing is rewritten and the new release launches anyway. `flipPointer` (the commit point of every upgrade) and the restarter now replace `.current-version` by rename without deleting it first, clearing a read-only bit and retrying on EPERM/EACCES/EBUSY. The restarter's failure lines are appended to `logs/upgrade-restart.log` (under `APP_LOG_DIR` when set), because it runs with stdio ignored. Plan: `docs/features/294-node-loopback-crash-guard.md`.

## 🐛 Other fixes

- **The QA report no longer offers to resume a voice check that is switched off (#4454).** With Render-integrity QA (voice match) disabled, `voiceDrift` now carries `speakerCheckEnabled: false`, and also carries a required `chaptersWithVerdicts` (how many of the current eligible chapters hold a voice-match verdict row), the card classifies it as `gateOff` when that is 0 and no mismatch or inconclusive chapter stands, and shows "Render-integrity QA (voice match) is off" with no Resume button (a past result, including a standing mismatch, stays visible with a "now off" note and a "partly checked before the check was turned off, N mismatches so far" line, with no chapter ratio, since a chapter counts as checked only when every character in it was; with the check on, the pending row reads "N of M eligible chapters fully checked, more pending" beside Resume scoring, and the same row on a book that was only partly scored no longer counts chapters that were checked for some characters only). It reads the verdict files rather than `charactersPending`, because the book-level centroids file outlives a chapter merge or split, so a restructured book re-rendered with the check off no longer reads as checked, and `POST /resume-scoring` answers 409 instead of starting a run that could never score. The text export gets a matching line.
- **Server error bodies no longer echo absolute paths** (#3702, PR #4527). Three mechanisms, by what the real producer emits. (1) `DeviceStoreDegradedError`'s message no longer embeds the absolute `device-tokens.json` path (it reached LAN clients in the `pairing` / `devices` 503 bodies); the path is logged by the store's own warning, both when the file is first read and when a write re-reads it. (2) Child-process output that reaches a body is path-scrubbed with the existing `scrubPaths` (`tts/ffmpeg-failure.ts`, now exported; owner decision 2026-11-21): `lan-cert`'s script stderr and its `Command failed: <abs paths>` fallback, `worktrees`' git stderr, and `models-inventory`'s `ollama rm` stderr (carried in an `execFile` error's `.message`), each line by line (`scrubChildOutput`) so a path costs only the rest of its own line. - **A malformed EPUB no longer crashes the server** (#4241, closes #4239). epub2's `getChapter` rewrites every `href` in a chapter from inside the zip's async inflate callback and throws `linkparts.shift is not a function` on `<a href="">`; a throw there is an uncaughtException no `try`/`await` can catch, so `crash-logging.ts` exited the process on import (or any other path that parses the source: re-parse, restructure, opening a book after a restart). `tryEpub2Parse` (`server/src/parsers/epub.ts`, the one seam every `parseManuscript` caller reaches) now reads each chapter with `getChapterRaw` and runs epub2's own `getChapter` transform over that text through a proxy whose `getChapterRaw` answers synchronously, so the throw lands in a `try` instead of the zip callback, and it is left uncaught there so it reaches `tryEpub2Parse`'s existing catch: the whole book is then read by `parseEpubRawZip`, the way the older code already read it whenever that throw was catchable (a book stored uncompressed). A book that crashed now imports, or, if the raw-zip reader cannot read it either (for example chapter files with `&` in their names, whose `&amp;` that reader never decodes, #4217), fails with a clean error instead of crashing; `/api/import` answers 415 (`UnusableMediaError`, as `/api/manuscripts` already did) rather than 500 for such a book. A book with no throwing chapter keeps exactly the text `getChapter` produced (including its quirks, which persisted sentence offsets depend on); books that imported before read exactly as before. Covered by the synthetic empty-href EPUB and a `getChapter`-parity fixture (`src/test-utils/empty-href-epub.ts`) in `parsers/epub.test.ts`, and by `routes/import.test.ts`.

- **Import warns about merged dialogue paragraphs** (#2254). - **A malformed EPUB or MOBI/AZW3 can no longer take the server down, whatever epub2 throws** (#4325, closes #4242, follows #4241). #4241 fixed one throw from an `epub2` async callback; any other throw there (container, OPF or NCX parsing) is still an uncaughtException that `crash-logging.ts` turns into an exit. EPUB and MOBI/AZW3 parsing now runs in a `node:worker_threads` worker, one per parse and terminated when it settles (`server/src/parsers/parse-in-worker.ts` spawns it, `parse-worker.ts` is the entry), behind `parseManuscript` in `parsers/index.ts`, the one seam every caller reaches: import, the manuscripts route, re-parse, replace-manuscript, the title refresh, restructure, samples and opening a book after a restart (`hydrateFromDisk`). Text and PDF stay in-process. A throw inside the worker, including one from an `epub2` callback, becomes a rejected promise in the caller and never reaches the main thread's `uncaughtException` handler; the unusable-book path answers 415 with a fixed, path-free sentence (`UnusableEpubError` / `UnusableMediaError`), as `/api/manuscripts` and `/api/import` already do. A hung parse is stopped after 120 s (`PARSE_WORKER_TIMEOUT_MS`, exported from `parse-in-worker.ts`, overridable per call for tests): the caller gets its 415 at the deadline and is not held up by the worker's in-flight I/O, while the per-parse scratch dir is removed in the background once the worker has exited. The buffer is copied into the worker, never transferred, because `routes/import.ts` writes the original buffer to disk after the parse. Extraction output is unchanged: the worker wraps `parseEpub` / `parseMobi` with the arguments `index.ts` passed before (plus a per-parse `scratchDir` the parsers write their temp files into, which the main thread removes after the worker exits, and an empty buffer when `sourcePath` is set, since the parser reads the file itself) and changes no extraction logic, the caller's `extractorVersion` (#4217) is passed through the worker request and never defaulted, so the worker extracts exactly as the in-process parser would at version 1 and at version 2, a parity test compares worker and in-process output over every fixture at both versions (plus an EPUB and a MOBI with a `</div>` closer), and parser error classes, messages and fs error codes cross the thread intact. Parity over the real library on the box is owed as register row A128 (`docs/testing/onbox-acceptance-register.md`). Covered by `parse-in-worker.test.ts`, `parse-in-worker.parity.test.ts`, `parse-in-worker.malformed.test.ts`, `parse-in-worker.crash-isolation.test.ts`, `parse-in-worker.seam.test.ts`, `parse-in-worker.execargv.test.ts` and `parse-in-worker.source-path.test.ts`.

- **EPUB/MOBI paragraphs no longer merge on non-`</p>` block closers** (#4217). `stripHtml` broke paragraphs only on `</p>`, `<br>` and `<hr>`, so books whose paragraphs or dialogue sit in `<div>`, `<blockquote>`, `<li>`, `<h1>`–`<h6>`, `<dd>`/`<dt>` or `<section>`/`<article>` imported with paragraphs run together. Covered by `parsers/extractor-version.parity.test.ts` (the version-1 golden), the version-2 cases in `html-utils`/`epub`/`mobi` tests, and the pin tests in `store/manuscripts.extractor-pin.test.ts`, `routes/book-state.extractor-pin.test.ts`, `routes/chapters-restructure.extractor-pin.test.ts` and `routes/samples.extractor-pin.test.ts`. - **`POST /api/books/:bookId/resume-scoring` refuses with 409 while a chapter splice or QA repair runs (#4235).** The route's only guard was `isGenerationActive`, but a splice or repair runs as a `render` book job and is invisible to it. `triggerScoring` then ran `scoreBook` and the post-audition `reconcileResidentQwenTiers` against `scoreBook`'s `usedQwenTiers`, which could evict the tier the splice or repair was synthesising under (a cold reload, or two tiers co-resident on an 8 GB card). The route now also checks `isSpliceOrRepairActive(bookId)` and answers a fixed-sentence 409 (never an error message), scoped per book. The tier eviction itself is shared-sidecar state, so `triggerScoring` skips the resume-route reconcile whenever any render, splice, repair or another book's `scoringInFlight` pass is active, decided at the moment it would run rather than at request time (the generation path's reconcile is skipped on the same rule, with the run's own book excluded, #4445). Residual windows, each at most one cold reload: the `GET /health` round trip before `/unload`, and the gap between a Fix-audio batch's per-chapter splice POSTs. The QA card now shows the server's refusal sentence beside Resume scoring (`resume-scoring-refused`); a network error shows nothing.
- **The generation path's Qwen tier reconciles skip their eviction while other GPU work is active (#4445).** Both reconciles on the generation path ran `reconcileResidentQwenTiers`, which can unload a Qwen tier that other work is using, whatever else was running: the post-audition one (`afterChapterFinalized` → `triggerScoring` with `keep`) after each chapter's audition, and the run-start one before a chapter's first POST. Each now skips while work other than the run's own book is active (`otherTierWorkActive`): a render on another book (new `isOtherGenerationActive` in the leaf gate), any splice or QA repair on any book, any voice design or variant mint on any book (new `isDesignOrMintActive` in the leaf gate, fed by counters `tts/design-voice-core.ts` registers around `postDesignAndCacheAudition`, the one choke point both designs and mints go through), or another book's `scoringInFlight` score pass. The resume-scoring route's own reconcile skips on designs and mints too. The run-start one logs `[generation] run-start tier reconcile skipped: other GPU work is active`. The run's own book is excluded in both, because its tier target (`ctx.keep` / `keepForRunStart`) protects its own chapters, so same-book sibling chapters still reconcile as before. That target is computed per chapter POST, so after a mid-run tier change it can be stale: both reconciles therefore also never drop the 1.7B while a Quality render is live (`keepQualityResident`, from `isQualityRenderKnownActive()`; owner decision on #4497). A 0.6B can still be evicted under a sibling by two paths, each costing a reload and retry and accepted: at run start with 2+ workers, when a character is raised to Quality (the new POST's keep is `keep06:false` while a sibling still renders on the 0.6B); and in the score pass with one worker and `qa.speaker.enabled`, when a character is lowered (ch5's keep is `{keep06:false, keep17:true}`, ch6 renders that character on the 0.6B, ch5's job has already deregistered, and its score-pass reconcile unloads the 0.6B). Designs and mints must count: the reconcile's `/unload {engine:'qwen'}` nulls the VoiceDesign model along with the base, and `/unload {model:'1.7b'}` calls `unload_base17()` at its default `wait_seconds=0`, which nulls the 1.7B Base without waiting for an in-flight mint (`mint_variant` then raises). User-visible: a voice design used to fail with "VoiceDesign model was unloaded before this design could render", and an emotion variant with "Qwen 1.7B-Base model was unloaded before this mint's anchoring forward started", when another book's chapter finished, and the same reconcile could drop the 0.6B too (for example under a Standard repair while another book rendered at Quality). The resume-scoring route's own reconcile is covered by the entry above (#4235).

- **Host paths in API responses collapse the home directory to `~` for non-loopback clients (#4446).** A phone or tablet on the LAN used to receive absolute paths that carry the OS username. For non-loopback requests the home directory is now collapsed to `~` and the rest of the path is kept, in: `GET /api/workspace` (`root`, `booksRoot`), the model inventory `diskPath` (`GET /api/models/inventory` and the removal response's `item`), `workspaceRoot`, `workspaceDirOverride` and `exportSyncFolder` in the user-settings responses, export job `syncPath`, the import `targetPath`, the book-create `paths` (`bookDir`, `manuscript`, `dotAudiobook`), `skipped[].bookDir` on the linked voice-override routes, the worktree rows' `path`, the `probed` paths in the `GET /cert/root.crt` not-found response (that route needs no pairing), the analysis, diagnostics, worktree and lan-cert messages that embed a path (the mid-persist halt message no longer carries paths at all; they go to the server log), the install, bootstrap and Ollama pull job `step`, `error` and `manualInstallerPath`, and the voice-library clone error. A path not under the home directory (for example `D:\books` or the install directory) is passed through unchanged. The home directory is matched however the path spells it: doubled backslashes (a Python repr), forward slashes, and, on Windows, the user's own 8.3 short profile name (`C:\Users\LONGUS~1`, `C:\Users\FIRSTN~1.LAS`, or `C:\Users\JOS~1` for a non-ASCII or short name). The server takes the short spelling from its own temp/AppData paths and confirms on disk that it resolves to the resolved home folder before it collapses it, as a whole-prefix spelling (so a relocated profile, such as a junctioned `C:\Users`, still collapses); a sibling's short name, or one the server never sees, is left as written. The device-store 503 on `/api/devices` and `/api/pair/redeem*` is a fixed path-free sentence for every client (#3702), so it needs no collapse. Loopback requests keep full paths. Because a LAN client now only sees the `~` form, a leading `~` is expanded to the home directory on write for non-loopback requests to `PUT /api/user/settings` (`workspaceDirOverride`, `exportSyncFolder`) and `POST /api/user/settings/sync-folder/test` (`path`), so the values round-trip; loopback writes are stored as sent. OpenAPI descriptions updated; no schema types changed. The stored values and the on-disk paths are unchanged.

## 🔌 Sync & server infrastructure

- **The server now writes a Node diagnostic report when it dies of a V8 fatal error,** into `logs/node-reports/` (`<APP_LOG_DIR>/node-reports/` when set), with Node's default timestamp-and-pid file name. It is enabled in-process at the start of boot, but only when node runs with `--report-exclude-env --report-exclude-network`, which every launcher now passes (`npm start`, `npm run dev`, `dev:lan`, `start:lan`, `start:prod`, Pinokio). The boot logs `[server] diagnostic report on a fatal error -> <dir>`, or an `OFF` line saying why when the folder can't be created or the flags are missing; boot continues either way. The check requires `process.report.excludeEnv` and `excludeNetwork` to already be true, i.e. that node itself parsed the flags (from its command line or `NODE_OPTIONS`), so a `NODE_OPTIONS` that `server/.env` sets after node started does not count. The flags keep the environment variables and the network interface list out of the main thread's report and out of the sub-report of every worker that inherits `execArgv`, since it is meant for a public issue. A `Worker` started with its own `execArgv` parses that plus the `NODE_OPTIONS` in its env instead, never the parent's command line, and in dev tsx's esbuild starts one with `execArgv: []` (its sync API), whose sub-report in an old-generation OOM would otherwise carry the whole environment and the interface list. So the dev launcher (`server/package.json` `dev`, now `node ../scripts/dev-server.mjs`, behind `npm start`, `npm run dev`, `dev:mock` and `dev:lan`) also starts tsx with both flags appended to `NODE_OPTIONS` (`scripts/lib/report-exclusion.mjs`, never clobbering the user's), and `start-app-prod.mjs` does the same for its server child; the prod server starts no Worker today. The runtime `excludeEnv`/`excludeNetwork` setters alone do not reach a young-generation OOM's report or a worker's sub-report. The report still carries the machine name (`header.host`), paths, the CPU model and the address of every open socket (`libuv[]` `localEndpoint`/`remoteEndpoint`: `host`, `ip4`, `ip6`). Evidence capture for the unexplained silent server deaths; a native crash (0xC0000409) writes no report, so read the folder together with the sidecar's exit-code line. On-box row A124. (#4054)
