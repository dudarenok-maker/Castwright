# On-box acceptance register

Shipped behaviour that can only be proven on real hardware (a live GPU, a real sidecar, a real analyzer, a real book, a real phone) and that was **not** proven at PR time.

A row here is a debt: the code is merged and users have it, but nobody has watched it work. Empty register = done.

Complex work routinely cannot be accepted inside its own PR. The box is often contended, an acceptance run can take hours, and a PR should not sit open waiting for one. **Owed acceptance never blocks a merge. It converts into a row here.** Recording it does block: the row, the run sheet and the live view move in the PR that ships the behaviour.

## How this register works

The governing rule is in [`CLAUDE.md`](../../CLAUDE.md), "Testing discipline" and Before-shipping checklist step 3.

- **Add a row** in the same PR that ships the unverified behaviour. Not later.
- **Remove a row** only when the acceptance was **run on the box** and the result recorded, or **the repo owner explicitly confirms** it was exercised on a live book during normal use. "Tests pass, so it's presumably fine" never removes a row.
- **Record the outcome where it will be found**: the run sheet, a results folder under `docs/testing/`, or the issue. Say what was observed, by whom and when.
- **A row states the current position only.** Why hardware is needed, what is still owed, what is already proven (one line, with the evidence path), the setup, and where the criteria live. Run transcripts, the story of how the row changed and the detail of items that passed belong in the run sheet or the results folder, not here.
- **A partly run row is edited down, not annotated.** Delete the bullets that passed and add one line under "Proven so far".
- **All three surfaces move in the same PR**: this file, the per-feature run sheet where one exists, and the live view.
- **Row IDs are allocate-once.** Take the new row's ID from its group's `<!-- next-id: … -->` marker and bump the marker in the same commit. Never reuse an ID, even one whose row is long gone. A new group needs its own marker. Blocked (`BLK`) and Unconfirmed (`UNC`) rows allocate the same way. Adding or removing a row also means updating that group's count in "At a glance" by hand, and the owed total.
- **Rows are grouped by hardware prerequisite**, not by feature, so one uncontested session can discharge everything that shares a setup.
- **Rows go stale.** Plan prose and issue bodies are often not updated after later work discharges them. Before scheduling a session, check each row against the closed issues and merged PRs on the same subject. A stale row is worse than a missing one: it sends you to run something already done.
- **"Not available to this run" is not "does not exist".** An isolated worktree carries no secrets and no books. A missing `GEMINI_API_KEY` or an empty workspace there says nothing about the real box, so never record a row as blocked on that evidence.

`npm run check:onbox-register` (CI: `verify.yml`'s `lint-and-checks` job) checks this file's structure: unique row IDs, each group's `next-id` marker, and each group's count in "At a glance" against the rows in its section. It cannot tell you a row is missing or that a row's wording is stale. `npm run check:register-row-citations` and `npm run check:register-citations` check that row IDs cited elsewhere in the repo still exist.

The change log that used to sit in this file is in [`onbox-acceptance-register-history.md`](onbox-acceptance-register-history.md), together with the reason for every row removed in the 2026-11-28 cleanup (#4883).

<!-- next-id: H101 -->

Not a hardware prerequisite: the blocker is a real-book fixture this repo's corpus does not have, a full-length all-kana Japanese manuscript. `detectManuscriptLanguageFromChapters` needs no GPU, sidecar or analyzer.

### H1 · Kana-trigram richness gate holds at real-book scale for an all-kana (no kanji) Japanese manuscript (#2256 round 3, finding 3(b)/C5)

`server/src/tts/prose-units.ts`'s kana tokenizer (overlapping character trigrams) is verified only against a hand-authored synthetic fixture (30 distinct hiragana base words composed into 1,500 sentences, the `finding 3(b)` fixture in `detect-language.test.ts`) and a 1,572-character real fixture. The original #2256 finding was a real book at about 4,843 characters that the old per-character scheme measured at R=1.72 and refused; this repo cannot reproduce that book. The margin is vocabulary-dependent and thinner than for Han-based CJK.

**Owed:** Once a real, legally usable all-kana (no kanji) Japanese manuscript at book scale (thousands to tens of thousands of kana characters) is available:

- Run its chapters through `detectManuscriptLanguageFromChapters` (or a full `POST /api/import`) and record the result. Expected: `{ language: 'ja', supported: true, fallback: false }`.
- Call `guiraudR` on the same deduped (`dedupeProseUnits`) winning sample and record the value against `LEXICAL_RICHNESS_FLOOR` (3), together with the observed `digitTokenShare`.
- For a multi-chapter book, record the total combined character count the richness gate saw (no cap applies since #2256 round 3).
- The row clears when the result and observed `R` are recorded and either the trigram fix is confirmed sufficient at real scale or a follow-up issue is filed with the real numbers.

**Proven so far:** On 2026-09-19 the fixture `server/src/__fixtures__/hyakunin-isshu-1-50.ja.md` (the first 50 Ogura Hyakunin Isshu poems, public domain, all hiragana, in 5 chapters of 10 poems) detected as `ja` with `guiraudR` about 29.015 at 1,572 kana characters. That sample is too small to answer this row: switching `KANA_NGRAM_SIZE` from 3 to 2 fails the older finding-3(b) test while this fixture's test stays green.

**Setup:** No GPU, sidecar or analyzer. Blocked on the manuscript: the two Coalfall Commission translations at `C:\AudiobookWorkspace\books\Castwright\Standalones\{煤落的委托, コールフォールの依頼}\manuscript.md` are mixed kanji and kana and do not count.

**Criteria:** The bullets above; issue [#2256](https://github.com/dudarenok-maker/Castwright/issues/2256) (closed).

### BLK102 · ORT pip-consistency marker — AMD box ([#2192](https://github.com/dudarenok-maker/Castwright/issues/2192), plan [282](../features/282-ort-pip-consistency-marker.md))

Design doc §On-box acceptance, criterion 5: "no marker is written" on AMD. The AMD profile takes the same marker-delete branch as cpu and apple, which this box can exercise. What is unverified is the ordering that branch protects: the AMD to ROCm-failure to CPU fallback inside `bootstrap-venv.mjs`'s `installForProfile`. `cpu.txt` carries an explicit `onnxruntime` line the fallback needs to actually install, and a stale marker present at that moment would make pip silently skip it. That ordering is unit-tested through the injected `runPip` and marker seam, but has never run against a real ROCm-to-CPU fallback.

**Owed:**

- On AMD/ROCm hardware, force the fallback (for example by pointing the ROCm wheel index at an unreachable URL), confirm the marker is deleted before the fallback's `pip install -r <cpu overlay>` runs, and confirm the fallback's explicit `onnxruntime` line from `cpu.txt` actually installs and is not skipped. Confirm no marker is ever written on this profile.

**Setup:** Blocked on AMD/ROCm hardware, which this dual-NVIDIA box does not have.

**Criteria:** [`ort-marker-onbox-acceptance.md` §7](ort-marker-onbox-acceptance.md) holds the recipe. Issue [#2192](https://github.com/dudarenok-maker/Castwright/issues/2192) (closed), plan [282](../features/282-ort-pip-consistency-marker.md).

### BLK103 · CPU-only `RAM_HEAVY_MODELS` clamp (plan 263, B2 step 7)

Formerly step 7 of B2 (per-model analyzer keep-alive). A `RAM_HEAVY_MODELS`

dual-NVIDIA; this will not move until a CPU-only box exists, or one where
GPU visibility can safely be disabled.

### BLK104 · ops-36 golden-assembly on a second ffmpeg build ([#1880](https://github.com/dudarenok-maker/Castwright/issues/1880), plan [272](../features/272-golden-assembly-comparison.md))

The cross-build half of the ops-36 design is dormant: whether the hard assertions of levels L1, L2 and L3 survive a genuinely different ffmpeg build, and what L4-loose's RMS error actually is when the encoder really differs. The loose branch itself is proven: the ops-36 demonstration forced it with a synthetic banner mismatch plus 2.0 LU of drift and it rejected at 24.79% RMS error against a 16% tolerance. Only the genuinely different encoder case is unproven.

**Owed:**

- Run the golden-assembly tier on a second machine with a different ffmpeg build (for example a BtbN Windows build against this box's gyan.dev `8.1.1-full_build-www.gyan.dev`, or a clearly different version), or on a CI runner whose ffmpeg differs from this box's. Record whether L1, L2 and L3 hold and the L4-loose RMS error.

**Setup:** Blocked. This box has no Docker, no WSL and no container runtime, and its only other `ffmpeg.exe` (the WinGet package) is the same gyan.dev build already on PATH. The tier is outside `verify.yml`, so CI never runs it. The owner ruled on 2026-08-21 that a portable ffmpeg prepended to PATH for one command does not satisfy the row: it means a different environment, not a different binary on the same one.

**Criteria:** [`onbox-wave3-results/step-7-e7-e8.md`](onbox-wave3-results/step-7-e7-e8.md). Issue [#1880](https://github.com/dudarenok-maker/Castwright/issues/1880) (closed), plan [272](../features/272-golden-assembly-comparison.md).

### BLK105 · ops-35 ffmpeg floor — below-floor + Re-check walkthrough ([#1877](https://github.com/dudarenok-maker/Castwright/issues/1877), plan [269](../features/269-ffmpeg-version-floor.md))

### BLK106 · ROCm/AMD admitted device-key normalisation — real GPU engine load, pinned/resident, and idle-eviction ([#2813](https://github.com/dudarenok-maker/Castwright/issues/2813), branch `fix/sidecar-rocm-device-normalisation`, PR review passes 1–2)

On a ROCm/AMD box the VRAM-ledger admission layer (`PlacementController.admit()`) hands engines a device key like `"rocm:N"`, but a ROCm/HIP torch build only understands `"cuda:N"`, and CTranslate2 and speechbrain have no `"rocm"` device. `server/tts-sidecar/main.py` now converts the key forward to `"cuda:N"` at every device call (`_normalise_rocm_device_key`), re-tags a pinned or resident engine's device back to `"rocm:N"` before `admit()` compares it (`_report_rocm_device_key`), and normalises both sides in `_same_card` so the idle-eviction ladder works. The unit tests (`test_qwen_device.py`, `test_coqui_device.py`, `test_device_parse.py`, `test_devices.py`, `test_placement.py`, `test_transcribe_embed_admission.py`) prove each conversion against stubbed `torch` and `_cuda_is_rocm`. They do not prove that a real ROCm/HIP torch build, CTranslate2 and speechbrain accept the converted values, load real models onto a real AMD card, and evict an idle one to make room.

**Owed:** With `SEG_CAPACITY_ADMISSION` on (the default), on ROCm/AMD hardware:

- Trigger a GPU engine load on each of the five engines the admission layer places on a ROCm card (Qwen Base, Coqui/XTTS, Whisper `/transcribe`, the SPK `/embed` speaker embed, and Kokoro if it ever gains a GPU placement). Each succeeds (model resident, synth, transcribe or embed completes) rather than crashing on an unconverted `"rocm:N"`.
- Repeat with an explicit `*_DEVICE=cuda:N` pin on at least one engine (for example `COQUI_DEVICE=cuda:0`). It admits onto that card rather than reporting permanent `noCapacity`.
- Fill the card with an idle-but-resident engine, then admit a different, heavier engine that needs the freed VRAM. The eviction ladder runs and frees it, rather than reporting `noCapacity` with an idle model sitting unused on the same card.

**Setup:** Blocked on AMD/ROCm hardware, which this dual-NVIDIA box does not have (same constraint as BLK101 and BLK102).

**Criteria:** Issue [#2813](https://github.com/dudarenok-maker/Castwright/issues/2813) (closed) and this row.
