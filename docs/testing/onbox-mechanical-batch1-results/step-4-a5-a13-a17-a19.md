### Bullet 4 — the real render, and the bug it found

**This is the acceptance row's actual point** ("what mocked tests cannot
reach… the real render-time Coqui fallback… has not been exercised on an
8 GB box"), and on first attempt it **failed** — not because the fallback
mechanism itself is broken, but because a *different, earlier* gate in the
same request path hard-blocks every non-English book regardless of Coqui
eligibility, before the fallback mechanism is ever reached.

**The bug.** `server/src/routes/generation.ts`'s per-chapter "loud-fallback
gate" (the queue-driven pre-check that decides whether to park a chapter for
user confirmation or fail it outright) computes `coquiEligible` correctly
(line ~831) and threads it correctly into `synthesiseChapter` two hundred
lines later (line ~1681) — but the **hard-fail branch in between**
(`if (nonEnglishBook) { …fail immediately, no park… }`, added 2026-07-04 for
issue #1263, a **week before** fs-60/plan 249 added the Coqui-fallback
mechanism on 2026-07-11) never got updated to check `coquiEligible`. The
result: clicking "Generate this chapter" on the Russian book immediately
failed with `errorCode: "voice-not-designed"` and the message *"No designed
Qwen voice for Анна, Иван Петрович, Незнакомый Парень — design them (and the
narrator) in the cast view before generating. **English Kokoro voices cannot
read ru text.**"* — the literal pre-fs-60 hard-block copy, contradicting both
the voice-readiness gate's own "Proceed anyway" promise (bullet 3, confirmed
working) and `synthesiseChapter`'s already-correct Coqui substitution, which
this gate never let the request reach. Confirmed via `git blame`
(`8d2b6ebed`, 2026-07-04, pre-dates `045aff85`, 2026-07-11, fs-60's own first
commit) that this is exactly a case of a later feature (fs-60) never
back-porting its own eligibility check into an earlier gate.

**The fix.** One-line condition change,
`if (nonEnglishBook)` → `if (nonEnglishBook && !coquiEligible)`, so a
Coqui-eligible non-English book falls through to the SAME park-and-confirm
path an English/Kokoro-fallback book already uses — the existing confirm flow
(`fallbackConfirmed: true` on re-dispatch) then reaches `synthesiseChapter`
with `forbidKokoroFallback: true, coquiEligible: true`, which was always
correct. Only the genuinely-unsupported-language case (no registered language
today — see below) keeps the immediate hard-fail, matching its own original
#1263 intent.

**Test fallout, and why it's a real update, not weakening coverage.** Four
existing tests in `generation-fallback-gate.test.ts`
(`#1263: fails fast…` / `…persists the failure…` / `…pluralizes…` / `…omits
the redundant "(and the narrator)"…`) all exercised this exact gate using a
**Russian**-language fixture book, asserting the immediate-hard-fail behavior
— i.e. they were pinning the *bug* as correct, because Russian has been
Coqui-eligible since before any of them were written. Confirmed this isn't a
one-off: the file's own comment block (lines 517-530, pre-existing) already
documents the **sibling** hard-fail branch
(`qwenUnavailable && nonEnglishBook && !coquiEligible`, a separate,
untouched code path) as **dormant** for the identical reason — "every
currently-registered language (en/ru/es/fr/de/zh/ja) is Coqui-eligible… an
unregistered code like 'ko' hits an earlier throw first" — so there is
provably no way to drive either hard-fail branch with any language this app
can currently create a book in. Replaced the four stale tests with one that
exercises the CORRECT behavior end-to-end: park (not fail) on the
cross-language-reused-voice case, then a confirmed re-dispatch reaching
`synthesiseChapter` with `forbidKokoroFallback: true` /
`bookLanguage: "ru"`. Verified: `tsc --noEmit` clean on `server/`;
`generation-fallback-gate.test.ts` 8/8 green; broader regression pass
(`generation.test.ts` excluded by this repo's own vitest config — a
pre-existing, deliberate exclusion, not something this step caused —
`generation-fallback-gate.test.ts` + `synthesise-chapter.test.ts` +
`synthesise-chapter-coqui-fallback.test.ts` = 126/126 green).

**Live confirmation, after rebuilding (`npm --prefix server run build`) and
restarting the pinned server.** Cleared a stale queue entry, retried the
chapter fresh. This time: **parked** (not failed) —

Незнакомый Парень. Confirm or skip it in the generation queue."* — confirmed

## A17 — `/health` stays live through a contended eviction on the default
Qwen path (plan 273, #1919)

**MIXED — real admission success and a genuinely low-overhead measurement,
but the measured numbers do not clear the row's own target, and forcing the
race pushed this 8 GB card into a real OOM.**

Warmed Qwen VoiceDesign for real (a non-persisting `preview: true` redesign of
a minor Coalfall Commission character, "Hart", via
`POST .../cast/hart/design-voice/stream`) — confirmed `qwenDesignResident:
true` on the raw sidecar `/health` while it ran. Started a real chapter render
(Chapter 4, "The Pour" — 159 lines, 13 speakers, all-Qwen cast) via a direct
SSE `POST /api/books/.../generation` call. Confirmed a genuine Qwen forward
in flight (`inflight_synth: 1`) before firing the second admission
(`POST /api/sidecar/load {"engine":"coqui"}`) from a separate client. A
dedicated low-overhead poller (`health_poller.py` — a persistent
`http.client.HTTPSConnection`, reused across all 692 requests, NOT a fresh
`curl` subprocess per iteration, which wave 6's own note flagged as unable to
cleanly attribute its measured gap) polled `GET /api/sidecar/health` every
~250ms for the full window.

**By the time the second admission actually fired, `qwenDesignResident` had
already reverted to `false`** (its own short idle window had elapsed) — so
the *exact* race #1919 describes (VoiceDesign warm **and** a Base forward
in flight **and** a concurrent second admission, all three at once) was not
hit byte-for-byte. What WAS hit is arguably the harder case: a live Qwen 1.7B
**Base** forward actively synthesising, evicted-against by a concurrent Coqui
admission.

**Results, both directions honestly reported:**
- The second admission **succeeded** (`{"status":"ready"}`) — the evict
  genuinely freed capacity rather than 503-ing `noCapacity`. Confirms bullet 4.
- `/health` never went fully unresponsive: **0 errors across 692 polls** over
  the ~170s window.
- **Max single-request latency: 2092.92 ms** — this is the number that
  actually reflects blocking (how long one `/health` call itself took to
  answer), and it is **worse** than wave 6's own already-over-target 987 ms,
  and far above the row's ~500 ms target.
- The (less meaningful) max **inter-response-start gap** was 241.29 ms — which
  in isolation would look like a clean pass under the ~500ms target, but it
  is the wrong metric for "did `/health` block": it measures time between
  successive request *starts*, not how long any single request was stuck.
  Reporting both numbers rather than only the flattering one.
- The render **itself then failed** with a genuine, real `errorCode:
  "vram-spill"` (*"The GPU ran out of video memory (VRAM) mid-render — too
  many models were resident at once."*) — both Qwen 1.7B and Coqui XTTS
  resident together on this 8 GB card genuinely exceeded its ceiling. The
  sidecar itself recovered cleanly afterward (not poisoned, no crash loop
  once idle).

**Net verdict**: the eviction mechanism is not a silent no-op — real admission
success, no hung `/health` connection — but on this box, actually forcing the
concurrent-admission race this row describes does not stay inside the ~500 ms
budget and can genuinely OOM the card. This is real, useful, load-bearing
evidence about the current headroom math on an 8 GB card with two heavy
engines, not a clean PASS.

**Bonus, cross-referenced to A10 (step 3)**: this same event organically
forced a genuine `vram-spill` — A10's second failure mode, which step 3
explicitly left as "NOT ATTEMPTED… deliberately, not a time-budget failure,"

## A19 — Stranded VRAM pool reclaimed on the admission-failure path (#1976,
PR #1993)

**Bullet 1: third negative result (after wave 6's two).** Immediately after
A17's genuine `vram-spill` crash, sidecar `/health` showed
`vram_reserved_mb: 3852.47` — strikingly close to #1976's own measured ~3.9 GB
shape, and initially looked like exactly the reproduction wave 6 asked for.
**It was not**: explicitly unloading both engines
(`POST /api/sidecar/unload {"engine":"coqui"}` then `{"engine":"qwen"}`)
dropped `vram_reserved_mb` cleanly to **132.12 MB** with `resident: []` — i.e.
the 3.85 GB was legitimate in-use reservation for two co-resident heavy
engines, not a pool that survives an explicit unload. Even a genuine mid-
render OOM crash on this box reclaims cleanly once asked to. This is a third
data point (after wave 6's two clean-completion measurements of 0 MB and
243.3 MB) all pointing the same direction: this box's ordinary — and now
also crash — paths do not organically strand VRAM the way #1976's original
report did.

**Bullets 2-3: not exercised** — both need a genuinely stranded pool to exist
first, and none was produced. **Still owed**, same as wave 6 left it — the
~3.9 GB shape may need a trigger this campaign hasn't hit yet (a `/recycle`
mid-render specifically, rather than an unforced crash; an ASR-QA re-record
cycle; or simply a different box).
