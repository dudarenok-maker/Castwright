On-box acceptance register

Shipped behaviour that only real hardware can prove — a live GPU, a real sidecar, a real analyzer, a real book, a real phone — and that was not proven at PR time. A row here is a debt: the code is merged and users have it, but nobody has watched it work.

Grouped by hardware prerequisite, not by feature — one uncontested session should discharge everything that shares a setup.

Owed acceptance never blocks a merge — it converts into a row here. But recording it does: since 2026-07-28 a PR that ships unproven behaviour, or discharges acceptance without writing down the outcome, is not finishable. A row comes out only when the acceptance was run on the box and recorded, or the repo owner confirms it was exercised on a live book. “Tests pass, so it's presumably fine” never removes a row.
How this register goes stale. Its first version read plan headers and issue bodies at face value, and three entries were wrong within a day — a prerequisite named as a blocker that was already satisfied, a “still draft” PR that had merged six weeks earlier, and a step count stale since before the register was written. Plan prose is frequently not updated after later work discharges it. Spot-check rows against closed issues before scheduling. A stale row is worse than a missing one: it sends you to run something already done.

A18Device-pin resolution survives a respawn2-card · the point of the fix›

buildSidecarEnv now hands the sidecar the raw cuda-uuid: literal instead of a translated cuda:N, so the sidecar re-resolves the pin against live torch enumeration on every spawn. CI can prove the right string is emitted; it cannot prove the right card is selected.

  • Pin Qwen to a card, restart the server, force a supervisor respawn — the engine lands on the pinned card both times.
  • Then change the enumeration order (swap the cards, or set CUDA_DEVICE_ORDER) and confirm a respawn still finds it by UUID rather than failing _validate_cuda_index or landing on the wrong card.
  • Pin tts.qwen.codecDevice to a card — the codec is actually placed there. Before #1870 the pin was silently ignored: the literal failed inside torch's .to() and rolled back to CPU.
  • Point the codec pin at an absent card — the sidecar logs QWEN_CODEC_DEVICE=… did not match any visible GPU and leaves the codec on cpu, not on the model's card (which is what auto would have done).
Row 2 is the whole reason the change exists. Before #1870 the spawn env depended on whether Advanced settings had been opened that session — a warm cache froze a cuda:N that every respawn re-emitted.
