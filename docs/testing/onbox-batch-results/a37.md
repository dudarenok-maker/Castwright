# A37 · Russian doubled-comma collapse pause measurement — evidence

Register row A37 (`docs/testing/onbox-acceptance-register.md`, search `### A37
· Russian dash-attributed dialogue`), issue #2059, PR #2688. PR #2688 fixed
`softenDashes` (`server/src/tts/text-normalize.ts`) producing a doubled comma
in dash-attributed Russian/French/Spanish dialogue (e.g.
`"— Привет, — сказал Антон."` previously carried `,,` in the TTS wire text).
This row confirms whether collapsing the doubled comma to one changes the
audible pause on real synthesized speech.

Run against the resident Coqui/XTTS v2 engine in this worktree's sidecar
(`server/tts-sidecar`, already-warm from batch step 2/A31), driven directly
via `POST /synthesize` (`engine: "coqui"`, `model: "xtts_v2"`, `voice:
"Damien Black"`, `language: "ru"`) rather than through the Node app — real GPU
inference throughout (RTX 4070 Laptop GPU, `cuda:0`), no mocks. Sidecar
version `1.14.0`, `coqui_version: "0.27.5"`.

**Methodology note, same as A31:** `/synthesize` is the raw sidecar endpoint
— it does **not** run `softenDashes` (that transform lives on the Node side).
To compare the actual post-fix production behaviour against the pre-fix
defect, the reference line `"— Привет, — сказал Антон."` was **hand-normalized**
to exactly what `softenDashes` produces today (leading dash → `"... "`,
interior dash → `", "`, doubled comma collapsed to one), and separately to
what it would have produced **before** PR #2688 (doubled comma left
uncollapsed) — a one-off probe text sent directly to `/synthesize`, **not**
by editing the shipped `softenDashes` function. A no-punctuation control at
the same word break was also rendered as a baseline, following the same
recipe A31 used for its leading/interior-dash comparison.

All three variants render the same underlying words (`Привет` / `сказал
Антон`), differing only in what sits at the break:

## Artifact check (waveform-level, not by ear)

`ffmpeg -af astats` on the full clip and on the 0.5–1.0 s window spanning the
clause break, for both the post-fix and pre-fix renders:

- **Post-fix** (`a37-postfix-single-comma.wav`): peak level -0.34 dB (no
  clipping — never reaches 0 dB), flat factor 0.000000 (no clipped/flat
  sample runs), full 16-bit dynamic range in use (bit depth 15/16/16/16).
- **Pre-fix probe** (`a37-prefix-doubled-comma.wav`): peak level -0.38 dB,
  flat factor 0.000000, same full dynamic range.

Neither clip shows clipping, flat-lining, or an abnormal peak at the
collapsed-comma point — no click, glitch, or unnatural cutoff artifact at the
break in either render.

## Verdict: agent-confirmed

The pause **survives** the comma collapse. The post-fix single comma still
produces a real, measurable break (0.194 s) that is 2.5× larger than the
no-punctuation control's largest micro-pause (0.076 s) — this is not noise,
it is a genuine clause-boundary pause, just as the doubled comma produced
before PR #2688. Collapsing the doubled comma to one **did reduce the pause's
magnitude** (0.495 s → 0.194 s, roughly 2.5× smaller) but did not eliminate
it or make it indistinguishable from no-punctuation prose — the two
punctuated variants (0.194 s, 0.495 s) both sit clearly above the no-comma
baseline's micro-pause band (0.05–0.08 s), while only the doubled comma
exaggerated it further. No audio artifact was introduced at the collapse
point in either variant.

This directly answers the row's question: the doubled-comma fix (#2059/PR
#2688) traded an over-long pause for a more natural one, not for no pause at
all — the fix improved wire-text correctness (no visible `,,`) without
regressing the intended clause-break prosody. Not staged for human review —
the numeric separation between all three conditions (no-comma baseline vs.
post-fix vs. pre-fix) is clean and monotonic, and the artifact check found
nothing ambiguous for a listener to adjudicate.
