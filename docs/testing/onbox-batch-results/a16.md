## Step 1 — clone a fresh voice, cast it on Одуван (real API, real GPU)

Source clip: `C:\AudiobookWorkspace\voice-library\0abceba4-.../master.wav`
("LibriVox Fixture Speaker A", English, 20 s, 24 kHz) — the same consented
fixture clip Одуван's *original* (now workspace-local-missing) clone was

```
POST /api/voice-library/clone-sample  (multipart, real Whisper ingest)
→ 202 {"candidateId":"a23c5621-...","transcript":"ocean, and then the rover
  boys in the jungle...","detectedLanguage":"en", ...}

POST /api/voice-library/clone
  {candidateId, name:"A16 Fixture Speaker (EN clone)",
   consent:{personName:"LibriVox Fixture Speaker A", relationship:"self",
   permittedUse:"personal"}}
→ 200 {"voiceUuid":"ddbbecac-b943-4bdd-8415-272608b45158", "engines":
  {"qwen":{"status":"ready", ...}}, "sampleMeta":{"qualityChecks":
  {"cloneCosine":0.9193}}}   ← real GPU Qwen distillation + real ECAPA self-check
```

```

  {bookId:"castwright__standalones__заказ-коалфолла", characterId:"одуван"}
```

## Bullet 3 — Whisper auto-detect transcription, pass criterion

## Bullet 7 — QA report, `voice-mismatch` rows for the cloned character

**This bullet surfaced a real methodological trap, documented in full
because it nearly produced a false result.**

The book was copied from `C:\AudiobookWorkspace`, which had its own
multi-week production history (cast-id-history shows Одуван renamed from
the ASCII id `oduvan` on 2026-08-21) — including a **pre-existing**
`02-глава-первая-стук.render-integrity.json` / `.embeddings.json`, dated
**2026-08-26**, computed against Одуван's *original* (workspace-local-missing)
coqui clone. `qa.speaker.enabled` (the flag gating the whole
render-integrity/voice-drift pipeline) defaults to **`false`** in this dev
environment (confirmed via `GET /api/config` → `values['qa.speaker.enabled']
== {effective:false, source:'default'}`), so **none of runs 1–3 above ever
touched that file** — the embeddings.json's mtime stayed frozen at
2026-08-26 through three full chapter renders. Querying `GET
/:bookId/qa-report` after run 2 showed **4 severe `voice-mismatch` rows for
Одуван** with `expectedEngine: "coqui"` (cast.json says `qwen`) —
100% stale copy-artifact contamination from the source workspace's own
history, not a live measurement of anything in this session. Calling
`POST /:bookId/resume-scoring` did not fix this either — it wraps the same
`qa.speaker.enabled`-gated `scoreBook`, which no-ops silently while the
flag is off (the route still replies `{"started":true}`).

**Correction applied:** deleted the stale `render-integrity.json`,
`render-integrity-attempted.json`, `render-integrity.centroids.json`,
`pending-attempts.json` and `embeddings.json` for this chapter, then
enabled the gate for real (`PUT /api/config {"qa.speaker.enabled":true}` →
confirmed `source:"override"`), then rendered the chapter a fourth time
(**run 4**) so the per-sentence ECAPA embed pass (which runs *inside*
`synthesiseChapter`, not inside `resume-scoring`) actually populated a
fresh `embeddings.json` for the first time all session.

Real, live, uncontaminated result for Одуван (8 of his 20 dialogue
sentence-groups were scored — the audition-fallback path renders the
character's own reference **from his current voice**, real GPU, and
ECAPA-embeds every group):

| sentence | verdict | cosine |
|---|---|---|
| 5 | voice-match | 0.873 |
| 8 | voice-match | 0.879 |
| 47 | voice-match | 0.834 |
| **50** | **voice-mismatch (severe)** | **0.764** |
| 54 | voice-match | 0.860 |
| 55 | voice-match | 0.837 |
| 71 | voice-match | 0.901 |
| 76 | voice-match | 0.855 |

`expectedEngine` and `renderedEngine` both now correctly read **`qwen`**
(matching cast.json) — confirming the earlier `"coqui"` reading really was
stale-file contamination, not a live #1969 regression: the reference
resolution correctly tracks the *current* voice assignment once given a
fair, uncontaminated run. The persisted centroid
(`render-integrity.centroids.json`) for Одуван: `cleanMean 0.850, pSevere
0.793, pBand 0.813` — sentence 50's 0.764 falls below `pSevere` by the
score.ts percentile rule, which is what actually produced the one flag; it
is a real, if borderline, single-line acoustic outlier (12.5% of scored
lines, cosine 0.09 below the character's own mean), not a
language/engine/identity mismatch — every other scored line clusters
tightly at 0.83–0.90.

**Verdict: STAGED FOR HUMAN REVIEW, not a clean pass.** The row's literal
bar ("zero `voice-mismatch` rows") is not met — one real row remains after
removing the contamination. But the mechanism the row is actually
worried about (`#1969`'s "an English/stale reference centroid flags a
correctly-rendered non-English chapter") is demonstrably **not** what
produced it: `expectedEngine`/`renderedEngine` correctly resolve to `qwen`,
the reference is built from Одуван's *own current* Russian audition render,
and the flagged line's cosine (0.764) is a modest, plausible single-line
dip relative to a tight 0.83–0.90 cluster — the shape of ordinary
percentile-based QA-gate noise, not a systematic identity or language
failure. A human listen to sentence 50's clip specifically (`chapter2-final.mp3`,
segment for `sentenceIds:[50]`, timestamps in `chapter2-final.segments.json`)
would settle whether it's a genuine synthesis glitch worth `qa.speaker.autoRepair`
catching, or a false positive from the 6th-percentile cutoff being tight for
a small (8-sample) per-character distribution — either way, it is not
evidence against the #1969/#1972 fixes this row is re-testing.

**Side finding worth flagging separately:** `qa.speaker.enabled` defaulting
to `false` in a fresh dev checkout means the render-integrity/voice-drift
QA system — and therefore #1969's own fix — is **silently inert** unless an
operator opts in via Settings or `SEG_SPK_ENABLED`. `POST
/resume-scoring`'s `{"started":true}` response while the gate is off is
misleading (it always replies success, whether or not `scoreBook` actually
ran anything) — worth a follow-up issue, not fixed here per this task's own
"don't re-derive #1972/#1969" boundary.
