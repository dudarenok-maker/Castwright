## Step 3 — what's actually driving the >0.4 tail (residual-risk investigation)

The row names two specific residual risks to check. Inspecting every
above-threshold (`drift`/`inconclusive`) line's real Whisper transcript
against its reference, in all four languages:

**Neither named risk is what's driving this run's elevated WER.** Every
`drift`/`inconclusive` transcript inspected is one of two shapes:

1. **Whisper hallucinating a trailing filler fragment on a short line.**
   E.g. German idx 5 (ref "Es könnte ein Kunde sein.", 5 words) transcribed
   as `"Es könnte ein Kunde sein. Now, on this to day, Nando geco. Nidhi."`
   — the reference is heard correctly, then ~8 extra hallucinated/bled-in
   tokens are appended, driving `wer` to 1.6 via **insertions**, not
   substitutions. The same shape recurs across all four languages (French
   idx 13 `"Eugot en vrai ? Yo !"`, Russian idx 18 `"Я конья от дитя,
   нарисованный."`, Spanish idx 49 `"Euna campanado."`) — short reference,
   correct core content, one or two extra trailing syllables. This looks
   like segment-boundary bleed (the next line's onset leaking into the
   current cut) compounded by Whisper's known tendency to hallucinate a
   short continuation on an already-quiet tail. It is symmetric across all
   four languages — not a language-specific content defect, and not covered
   by the existing `minRefWords` short-line backstop (that backstop targets
   **substitution** ambiguity on short references, not insertions).
2. **Genuinely untrustworthy transcripts** (`avg_logprob` below −1, mostly
   on longer Coqui lines that partially collapsed into non-linguistic
   babble, e.g. German idx 61 `"Ich will eine Glocke, oh,
   Dingdossigedokisame, Indo hundraundraundrade tatsi..."`) — these already
   correctly route to `inconclusive`, not `drift`, per the gate's own
   untrustworthy-transcript design; not a calibration target.

**Gendered-number mismatch (es/fr/ru "one", ru "two").** Scanned every
transcript in all four chapters for a number/article word (`es: un/una/uno`,
`fr: un/une`, `de: ein/eine/einer/eins`, `ru:
один/одна/одно/два/две`): 18 hits (de), 17 (es), 14 (fr), **0 (ru)**. Manual
read of every es/fr/de hit shows correct grammatical gender/number agreement
in every case observed (e.g. Spanish "¿Uno de verdad?" — correctly masculine
for the referent, not a "una" swap; French "un client", "un dragon" all
correctly agreeing). **Not falsified, but also not exercised for Russian** —
this chapter's dialogue simply contains no spoken "one"/"two" line in
Russian, so the risk remains untested by this specific run's data, not
cleared.

**Russian oblique-case declension mismatches.** All 16 Russian
`drift`/`inconclusive` lines were read by eye against their reference: none
shows a case-ending swap on a real noun (the pattern the risk describes,
e.g. nominative bleeding into a wrong oblique case). The errors present are
either the trailing-filler-insertion shape above or ordinary
content-word substitution (e.g. idx 18 "нарисованный" ("painted",
adjective/participle correctly declined) substituted in for a different
word) — real ASR/TTS noise, but not the specific declension defect named.

**German compound-number single-fused-token assumption.** This chapter's
dialogue contains no multi-digit or compound number spoken aloud (the
closest is chapter 3's "einundzwanzig" territory, out of this row's
one-chapter scope) — **could not be exercised this run**; flagged for a
future data point rather than answered here.

## Step 4 — a real defect found and fixed: calibrated defaults were inert

Before picking numbers, I verified the mechanism that would apply them.
`segment-asr-qa.ts`'s `perLanguageMaxWer()` (pre-existing #1084 scaffold)
read:

```ts
const state = resolveKnob(knob);
return state.source === 'default' ? undefined : (state.effective as number);
```

`resolveKnob` reports `source: 'default'` whenever no env var or app
override is set for that knob — **regardless of what literal number the
knob's own `default` field holds**. I proved this empirically: with
`qa.asr.maxWer.es`'s registry default changed to `0.5` (no env/override set),
`resolveAsrThresholds(undefined, 'es').maxWer` still returned the **global**
`0.4`, and the pre-existing test `defaults every language to the global
maxWer` still passed unchanged. **Editing the four registry defaults alone,
as the row's own task text literally asks for, would have been a silent
no-op** — the calibration would never reach `classifyTranscript` at runtime.

Fixed `perLanguageMaxWer()` to treat a per-language knob whose registry
`default` has been deliberately set away from the global knob's own default
as itself the calibration signal (an explicit env/app override still always
wins, unchanged):

```ts
if (state.source !== 'default') return state.effective as number;
const globalKnob = allKnobs().find((k) => k.key === 'qa.asr.maxWer');
if (globalKnob && knob.default !== globalKnob.default) return knob.default as number;
return undefined;
```

An uncalibrated language (no knob at all, e.g. zh/ja per D2, or a knob whose
default was never moved off 0.4) still cascades the global knob's *live*
value — including the global's own override — exactly as before. Updated
`resolveAsrThresholds per-language maxWer (#1084 scaffold)`'s three tests in
`segment-asr-qa.test.ts` to assert the new calibrated values instead of the
stale "everything defaults to 0.4" behaviour, and added a `zh` (uncalibrated)
case to the first test proving the cascade-to-global path still works.

## Step 5 — the threshold pick, and why it's the same number for all four

Naively picking each language's own p90 (de 0.75, es 0.5, fr 0.6, ru 0.667)
**breaks real safety-net coverage**: `segment-asr-qa.test.ts` already pins
two synthetic German cases as invariants —

- `'Bleib im Haus, mein Freund!'` → `'Renne im Park, mein Feind!'` (3 of 5
  words wrong) → `wer = 0.6`, must stay `'drift'`.
- `'Ging sie von dem?'` → `'Ging sie irgendwo hin?'` (2 of 4 words wrong) →
  `wer = 0.5`, must stay `'drift'`.

These are genuine, language-agnostic evidence that a WER of 0.5–0.6 can
represent real, serious content substitution (half a short sentence
replaced with unrelated words) — exactly the shape a content-QA gate exists
to catch. Confirmed live: setting `maxWer.de` to the raw p90 (0.75) flips
both of these from `'drift'` to `'ok'` — the two vitest cases failed
immediately on the first attempt. Raising the cap to chase this run's
insertion-noise tail would have bought fewer nuisance flags at the cost of
missing exactly the failure mode #1527/#1084 exist to catch.

**Final pick: `0.45` for all four languages** (es/fr/de/ru) — up from the
0.4 global default, but held strictly below the 0.5 floor the pinned tests
require, and comfortably below the independent `qa.asr.catastrophicWer`
floor (0.85, unchanged, so `Math.max(catastrophicWer, maxWer)` still gives
every language the same catastrophic-mismatch backstop as before). 0.45
sits within or just above each language's own p75–p80 band (de 0.27–0.33,
es 0.20–0.29, fr 0.40–0.40, ru 0.33–0.50), so it absorbs a real, data-backed
slice of the observed short-line insertion-noise tail without approaching
the substitution-detection floor. Given the dominant driver of the >0.4 tail
is the same symmetric cross-language artifact (Step 3), a uniform value is
the honest conclusion from this data — there was no language-specific signal
strong enough, once bounded by the 0.5 floor, to justify meaningfully
different numbers per language from a single chapter's worth of data.

The trailing-filler-token insertion artifact itself is a real side finding
worth a future targeted fix (e.g. extending the existing short-line
substitution backstop to cover insertion-dominated short lines), not
addressed here — that would be gate-logic work, not a threshold pick, and
out of this row's scope ("not a general per-language WER auto-tuner").
